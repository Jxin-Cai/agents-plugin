# 覆盖率分析原则

本文档定义了覆盖率分析阶段必须遵循的原则。用这些原则评估测试覆盖的有效性。

---

## 1. 覆盖率层次模型

测试覆盖率是分层的，不同层次揭示不同维度的质量信息：

### 语句覆盖（Statement Coverage）
- 最基础的覆盖指标，衡量代码行被执行的比例
- 行业基准：>= 80%，高标准 >= 90%
- **局限性**：无法发现逻辑分支中的缺陷

### 分支覆盖（Branch Coverage）
- 衡量条件判断的每个分支是否被测试
- 行业基准：>= 70%，高标准 >= 85%
- **比语句覆盖更有价值**：能发现未测试的逻辑路径
- 重点关注：if/else、switch/case、try/catch、三元运算符

### 条件覆盖（Condition Coverage）
- 衡量复合条件中每个子条件的真假值是否都被测试
- 适用于复杂业务规则和权限判断逻辑
- 如 `if (A && B || C)` 需测试 A/B/C 各自为 true/false 的组合

### 路径覆盖（Path Coverage）
- 衡量代码中所有可能执行路径是否被测试
- 理论上最完备，实践中由于路径爆炸通常只关注关键路径
- 优先覆盖：核心业务流程、支付路径、数据持久化路径

---

## 2. 新代码 vs 存量代码策略

### 新代码覆盖率（New Code Coverage）
- 对新增/变更代码执行更严格的覆盖率门控
- 推荐阈值：>= 80%（严格项目 >= 90%）
- **核心思想**：不要让质量债务继续增长

### 存量代码覆盖率
- 渐进式提升，设定季度改进目标
- 优先提升高风险模块（高圈复杂度、高缺陷密度）的覆盖率
- 不建议为了数字而补充无意义的测试

### 排除策略
- 自动生成的代码（DTO、Protobuf、ORM 映射）应排除在覆盖率统计之外
- 配置类、常量类、简单 getter/setter 不纳入核心覆盖率考核
- 第三方库封装层根据实际风险决定是否覆盖

---

## 3. 覆盖率盲区识别

### 高风险盲区清单
常见的覆盖率盲区，需重点检查：

| 盲区类型 | 示例 | 风险等级 |
|---------|------|---------|
| 异常处理路径 | catch 块、fallback 逻辑 | 高 |
| 边界条件 | 空值、零值、最大值、溢出 | 高 |
| 并发代码 | 锁、线程池、异步回调 | 高 |
| 集成点 | API 调用、数据库操作、消息队列 | 高 |
| 配置驱动逻辑 | 特性开关、环境变量分支 | 中 |
| 定时任务 | Cron Job、调度器 | 中 |
| 数据迁移 | Schema 变更、数据转换 | 中 |
| 日志与监控 | 日志格式、告警触发 | 低 |

### 识别方法
1. **覆盖率报告热力图**：红色区域（未覆盖）+ 高圈复杂度 = 最高优先级
2. **变更频率分析**：频繁变更但覆盖率低的文件是定时炸弹
3. **缺陷回溯**：历史缺陷对应的代码区域是否有足够覆盖

---

## 4. 质量门控配置

### 推荐质量门控配置

| 门控项 | 阻断级别 | 推荐阈值 |
|--------|---------|---------|
| 整体行覆盖率 | 警告 | >= 80% |
| 整体分支覆盖率 | 警告 | >= 70% |
| 新代码行覆盖率 | 阻断 | >= 80% |
| 新代码分支覆盖率 | 阻断 | >= 70% |
| 关键模块覆盖率 | 阻断 | >= 90% |
| 覆盖率下降 | 阻断 | 不允许下降 |

### 渐进式提升策略
- 第一阶段：设立基线，记录当前覆盖率
- 第二阶段：新代码强制门控，存量代码设改进目标
- 第三阶段：逐步提高整体阈值（每季度 +5%）
- 第四阶段：引入分支覆盖和变异测试

---

## 5. 覆盖率反模式

### 需要警惕的反模式

- **数字游戏**：写只执行但不断言的测试，提升覆盖率但不提升质量
- **一刀切阈值**：对所有模块使用相同的覆盖率要求
- **忽略集成测试**：只看单元测试覆盖率，遗漏组件交互的问题
- **覆盖率焦虑**：追求 100% 覆盖率导致投入产出比极低
- **静态快照**：只看当前值不看趋势，无法判断质量是在改善还是恶化

### 检验方法
- 对比覆盖率和缺陷密度：覆盖率高但缺陷密度也高 → 测试质量有问题
- 变异测试分数：如果变异测试杀死率低于覆盖率 → 存在弱断言

---

## 6. 工具链覆盖率报告解读

### 通用解读要点
- **文件粒度**：哪些文件覆盖率最低？是否为核心业务文件？
- **函数粒度**：哪些函数完全未覆盖？是否为关键逻辑？
- **分支粒度**：哪些条件分支未被测试？是否为异常路径？
- **差异报告**：本次变更引入了多少未覆盖的新代码？

### 报告中的关键信号
- 覆盖率突然下降 → 大量新代码未配测试
- 某模块覆盖率远低于平均 → 可能是技术债务集中区
- 分支覆盖率远低于行覆盖率 → 缺乏边界条件测试
