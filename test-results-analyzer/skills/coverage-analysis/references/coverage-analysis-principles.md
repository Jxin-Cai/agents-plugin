# 覆盖率分析原则

---

## 1. 覆盖率层次模型

| 层次 | 含义 | 基准 | 重点 |
|------|------|------|------|
| 语句覆盖 | 代码行执行比例 | >= 80% | 最基础，无法发现分支缺陷 |
| 分支覆盖 | 条件分支测试比例 | >= 70% | 比语句覆盖更有价值，关注 if/else、switch、try/catch |
| 条件覆盖 | 复合条件子条件真假值 | 适用于复杂规则 | 如 `if (A && B || C)` 需测试各子条件组合 |
| 路径覆盖 | 所有可能执行路径 | 关注关键路径 | 优先覆盖核心业务、支付、数据持久化路径 |

---

## 2. 新代码 vs 存量代码策略

| 类型 | 策略 | 推荐阈值 |
|------|------|---------|
| 新代码 | 严格门控，不让质量债务增长 | >= 80%（严格项目 >= 90%） |
| 存量代码 | 渐进提升，优先高风险模块 | 季度改进目标 |
| 排除项 | 自动生成代码（DTO/Protobuf/ORM）、配置类、常量类、简单 getter/setter | 不纳入覆盖率考核 |

---

## 3. 覆盖率盲区识别

### 高风险盲区清单

| 盲区类型 | 示例 | 风险 |
|---------|------|------|
| 异常处理路径 | catch 块、fallback 逻辑 | 高 |
| 边界条件 | 空值、零值、最大值、溢出 | 高 |
| 并发代码 | 锁、线程池、异步回调 | 高 |
| 集成点 | API 调用、数据库操作、消息队列 | 高 |
| 配置驱动逻辑 | 特性开关、环境变量分支 | 中 |
| 定时任务 | Cron Job、调度器 | 中 |
| 数据迁移 | Schema 变更、数据转换 | 中 |

### 识别方法
- 覆盖率报告红色区域 + 高圈复杂度 = 最高优先级
- 频繁变更但覆盖率低的文件 = 定时炸弹
- 历史缺陷对应代码区域是否有足够覆盖

---

## 4. 质量门控配置

| 门控项 | 级别 | 推荐阈值 |
|--------|------|---------|
| 整体行覆盖率 | 警告 | >= 80% |
| 整体分支覆盖率 | 警告 | >= 70% |
| 新代码行覆盖率 | 阻断 | >= 80% |
| 新代码分支覆盖率 | 阻断 | >= 70% |
| 关键模块覆盖率 | 阻断 | >= 90% |
| 覆盖率下降 | 阻断 | 不允许 |

渐进式提升：设立基线 → 新代码强制门控 → 逐步提高整体阈值（每季度 +5%）→ 引入变异测试。

---

## 5. 覆盖率反模式

| 反模式 | 表现 | 检验方法 |
|--------|------|---------|
| 数字游戏 | 只执行不断言，提升数字不提升质量 | 对比覆盖率和缺陷密度 |
| 一刀切阈值 | 对所有模块使用相同要求 | 按模块风险分级 |
| 忽略集成测试 | 只看单元测试覆盖率 | 检查组件交互覆盖 |
| 覆盖率焦虑 | 追求 100% 导致投入产出比极低 | 评估边际收益 |
| 静态快照 | 只看当前值不看趋势 | 引入历史对比 |

变异测试杀死率低于覆盖率 → 存在弱断言。

---

## 6. 报告解读要点

- **文件粒度**：覆盖率最低的文件是否为核心业务文件
- **函数粒度**：完全未覆盖的函数是否为关键逻辑
- **分支粒度**：未测试的条件分支是否为异常路径
- **差异报告**：本次变更引入了多少未覆盖新代码
- **关键信号**：覆盖率突降 → 新代码未配测试；分支覆盖率远低于行覆盖率 → 缺乏边界测试
