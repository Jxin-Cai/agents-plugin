## Step 1: 数据收集与识别

引导用户提供覆盖率数据。使用 `AskUserQuestion` 工具询问数据来源：

- **覆盖率报告文件** — 提供报告文件路径（如 JaCoCo XML/HTML、Istanbul JSON、Coverage.py 报告）
- **CI/CD 产出** — 提供 CI 构建的覆盖率摘要
- **手动输入** — 口述关键覆盖率数字

收到数据后：
1. 使用 Read 读取用户提供的报告文件，识别技术栈和覆盖率工具类型
2. 使用 Grep 在报告中搜索关键指标关键词（如 `line`、`branch`、`function`、`statement`），提取整体行覆盖率、分支覆盖率、函数覆盖率
3. 使用 Grep 按模块/包名搜索，提取模块粒度的覆盖率分布
4. 使用 Write 将原始数据摘要保存到 `{工作目录}/context/coverage-data-summary.md`

向用户展示提取的关键数据，确认准确性。

**⏸️ 等待用户确认后继续。**

## Step 2: 覆盖率全景评估

基于收集的数据，进行多维度评估：

### 2.1 整体健康度评分

对照行业基准给出评分：

| 指标 | 当前值 | 行业基准 | 评级 |
|------|--------|---------|------|
| 行覆盖率 | ? | >= 80% | ✅/⚠️/❌ |
| 分支覆盖率 | ? | >= 70% | ✅/⚠️/❌ |
| 函数覆盖率 | ? | >= 85% | ✅/⚠️/❌ |
| 新代码覆盖率 | ? | >= 80% | ✅/⚠️/❌ |

### 2.2 模块热力图

按模块列出覆盖率分布，标注：
- 🔴 红区（< 50%）——严重不足
- 🟡 黄区（50%-80%）——需改进
- 🟢 绿区（> 80%）——达标

### 2.3 覆盖率趋势

如果有历史数据，分析趋势：
- 整体趋势是上升还是下降？
- 哪些模块在恶化？
- 新代码的覆盖率是否达标？

向用户展示评估结果。

**⏸️ 等待用户确认后继续。**

## Step 3: 盲区深度诊断

基于引用文件中的高风险盲区清单，逐项检查：

1. **异常处理路径**：catch 块、fallback 逻辑是否被测试？
2. **边界条件**：空值、零值、最大值场景是否覆盖？
3. **并发代码**：多线程、异步逻辑是否有对应测试？
4. **集成点**：外部 API 调用、数据库操作是否被 mock 测试？
5. **配置驱动逻辑**：特性开关的各分支是否都被测试？

对每个盲区给出：
- 风险等级（高/中/低）
- 影响范围（涉及哪些业务功能）
- 改进建议（需要补充什么类型的测试）

## Step 4: 改进优先级排序

综合以下因素对改进项排序：

| 因素 | 权重 |
|------|------|
| 业务风险（核心业务 vs 边缘功能） | 40% |
| 当前覆盖率与目标的差距 | 25% |
| 变更频率（频繁变更的模块优先） | 20% |
| 改进成本（补测难度） | 15% |

产出一份优先级排序的改进清单：

```
优先级 P0: [模块名] — 当前覆盖率 X%，目标 Y%，需补充 [测试类型]
优先级 P1: [模块名] — ...
优先级 P2: [模块名] — ...
```

## Step 5: 保存产出

使用 Write 将覆盖率分析报告保存到 `{工作目录}/coverage/coverage-{日期}.md`，内容包含 Step 2-4 的所有评估结果和改进清单。

使用 `AskUserQuestion` 工具向用户展示以下选项（不要用文本菜单让用户输入序号）：

- **进入失败分析（推荐）** — 诊断测试失败的根本原因和模式
- **深入某个模块** — 对特定模块做更细粒度的覆盖率分析
- **直接生成质量报告** — 如果覆盖率分析已经足够

## 成功/失败指标

### ✅ 成功
- 区分了行覆盖率和分支覆盖率的评估
- 区分了新代码和存量代码的覆盖策略
- 按模块展示覆盖率分布，而非仅看整体数字
- 改进建议按优先级排序，附带权重说明

### ❌ 失败
- 只看整体数字不看模块分布
- 忽略分支覆盖率只看行覆盖率
- 把覆盖率数字当目标而非信号
- 替用户下结论而不是引导分析

<IMPORTANT>
必须区分行覆盖率和分支覆盖率，不可只看一种。
必须区分新代码和存量代码的覆盖策略。
覆盖率数字是信号不是目标，必须分析覆盖质量。
本技能完成后，展示菜单并等待用户选择下一步。不要自动执行后续技能。
</IMPORTANT>
