## Step 1: 失败数据收集

引导用户提供测试失败数据。使用 `AskUserQuestion` 工具询问数据来源：

- **测试报告文件** — 提供 JUnit XML、pytest 报告、Jest 输出等
- **CI/CD 日志** — 提供 CI 构建失败日志
- **手动描述** — 口述失败的测试用例和错误信息

收到数据后：
1. 统计失败总数和通过率
2. 按模块/文件分类失败分布
3. 按错误类型分类（断言失败、异常抛出、超时、编译错误等）
4. 识别是否存在 Flaky 测试（同一测试反复出现在失败列表）
5. 将失败摘要保存到 `{工作目录}/context/` 下

向用户展示失败数据概览，确认数据完整性。

**⏸️ 等待用户确认后继续。**

### 2.3 Pareto 分析

统计失败按模块的分布，识别"头部模块"：
- 哪 20% 的模块产生了 80% 的失败？
- 这些模块有什么共同特征？

向用户展示分类结果，讨论是否有遗漏或误分类。

**⏸️ 等待用户确认后继续。**

## Step 3: 根因深度诊断

对 P0 和 P1 级别的失败进行深度根因分析。对每个重点失败，至少使用一种方法：

### 方法 A：5 Whys 追问

对每个关键失败执行 5 Whys：

```
失败：[测试名称] — [错误信息]
→ 为什么？[第一层原因]
→ 为什么？[第二层原因]
→ 为什么？[第三层原因]
→ 为什么？[第四层原因]
→ 为什么？[根本原因]
→ 纠正措施：[建议的修复方案]
→ 预防措施：[防止同类问题再发生的方案]
```

### 方法 B：鱼骨图分析

对失败聚集的模块进行六维度分析：
- 人员：是否是理解偏差导致？
- 流程：是否是流程漏洞导致？
- 代码：是否是逻辑缺陷？
- 环境：是否是环境差异？
- 数据：是否是数据问题？
- 工具：是否是工具限制？

每个根因诊断向用户展示分析过程，征求用户的领域知识补充。

**⏸️ 每完成一个关键失败的分析，等待用户确认。**

## Step 4: 缺陷聚集与趋势分析

### 4.1 缺陷热点地图

计算各模块的缺陷密度，标注热点：
- 🔴 高密度（> 5 个/KLOC）
- 🟡 中密度（2-5 个/KLOC）
- 🟢 低密度（< 2 个/KLOC）

### 4.2 趋势信号

识别关键趋势信号（如有历史数据）：
- 失败率是上升还是下降？
- 是否有反复出现的同类失败？
- Flaky 测试比例是否在增长？

### 4.3 预警标注

对照引用文件中的预警信号清单，标注当前状态。

## Step 5: 修复建议生成

使用引用文件中的 影响 x 频率 矩阵，对每个根因生成修复建议：

```
[P0] [根因描述]
  修复方案：[具体修复步骤]
  预防措施：[防止再发生的流程改进]
  预计工作量：[小/中/大]
  
[P1] [根因描述]
  修复方案：...
```

## Step 6: 保存产出

将失败分析报告保存到 `{工作目录}/failures/failure-{日期}.md`

- **生成质量报告（推荐）** — 综合覆盖率和失败分析，生成完整质量报告
- **深入 Flaky 测试治理** — 对间歇性失败做专项分析
- **对特定模块做 5 Whys 深度分析** — 选择一个高缺陷密度模块深入诊断

## 成功/失败指标

### ✅ 成功
- 按确定性和根因两个维度完成了失败分类
- 执行了 Pareto 分析，识别头部失败模块
- 对关键失败使用了结构化根因分析方法（5 Whys 或鱼骨图）
- Flaky 测试被单独识别和标注

### ❌ 失败
- 只看表面错误信息不追问根因
- 忽略 Flaky 测试
- 没有做 Pareto 分析
- 替用户判断根因而不是引导分析

<IMPORTANT>
必须使用至少一种结构化根因分析方法（5 Whys 或鱼骨图）。
必须区分确定性失败和 Flaky 测试。
修复建议必须按影响 x 频率矩阵排优先级。
本技能完成后，展示菜单并等待用户选择下一步。不要自动执行后续技能。
</IMPORTANT>
