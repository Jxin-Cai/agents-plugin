# 失败分析原则

---

## 1. 根因分析方法论

### 5 Whys 法
连续追问"为什么"穿透表面症状：测试失败 → 断言不匹配 → 返回值变了 → 上游接口改了 → 缺少契约测试 → 没有集成测试规范（根因）。

**规则**：至少 5 层；每层必须有事实支撑；出现多分支原因则分别追踪。

### 鱼骨图（石川图）

| 维度 | 典型原因 |
|------|---------|
| 人员 | 理解偏差、审查遗漏、测试设计不当 |
| 流程 | 需求变更未同步、测试用例未更新、发布漏洞 |
| 代码 | 逻辑缺陷、边界处理不当、竞态条件、内存泄漏 |
| 环境 | 环境不一致、依赖版本不匹配、资源不足 |
| 数据 | 数据过期、状态不一致、schema 变更 |
| 工具 | 框架 bug、CI 配置错误、mock 工具限制 |

### Pareto 分析
统计失败分布（按模块/类型/开发者），找到 20% 的原因造成 80% 的失败，优先修复高频根因。

---

## 2. 失败模式分类

### 按确定性

| 类型 | 特征 | 常见原因 |
|------|------|---------|
| 确定性失败 | 每次都失败 | 代码逻辑错误、接口变更 |
| 间歇性（Flaky） | 时过时不过 | 竞态条件、时序依赖、资源竞争 |
| 环境依赖 | 特定环境失败 | 配置差异、OS 差异 |
| 数据依赖 | 特定数据失败 | 数据污染、数据边界 |

### 按根因

| 根因 | 修复策略 |
|------|---------|
| 代码缺陷 | 修复代码 + 回归测试 |
| 测试缺陷 | 修复测试 + 审查设计 |
| 环境问题 | 统一环境配置 + 容器化 |
| 设计变更 | 更新测试 + 契约测试 |
| 基础设施 | 基础设施优化 + 重试 |

---

## 3. Flaky 测试治理

**常见根因**：
- 时序依赖：使用 sleep 而非显式等待、异步未同步
- 测试间耦合：共享全局状态未重置、执行顺序依赖
- 资源竞争：端口冲突、文件系统并发、连接池耗尽
- 外部依赖：网络请求未 mock、第三方服务不稳定

**治理策略**：隔离（标记移出主流水线）→ 监控（统计 flaky 率，目标 < 1%）→ 按频率和影响排序修复 → 制定编写规范预防。

---

## 4. 缺陷聚集分析

- **缺陷密度** = 缺陷数 / KLOC；基准 < 5（普通）、< 1（高标准）
- **聚集原因**：高圈复杂度（> 10）、频繁变更、多人协作交界、历史遗留、技术债务
- **热点排序**：高密度 + 高变更频率 → 最优先重构；高密度 + 低变更频率 → 计划性重构

---

## 5. 失败趋势与预警

| 维度 | 关注点 |
|------|--------|
| 时间 | 特定时段失败率升高、迭代间变化、发布前后 |
| 关联 | 与特定提交关联、与特定开发者关联、模块间级联 |

**预警信号**：
- 失败率突升 → 重大代码变更未配测试
- Flaky 率攀升 → 测试基础设施恶化
- 同类失败反复 → 根因未被真正修复
- 新增失败聚集某模块 → 该模块需重点关注

---

## 6. 修复优先级矩阵

|  | 高频率 | 低频率 |
|--|--------|--------|
| **高影响** | P0 立即修复 | P1 本迭代修复 |
| **低影响** | P2 计划修复 | P3 可接受风险 |
