# 失败分析原则

本文档定义了测试失败分析阶段必须遵循的原则。用这些原则进行结构化的根因诊断。

---

## 1. 根因分析方法论

### 5 Whys 法
连续追问"为什么"直到穿透表面症状到达根本原因：

```
测试失败 → 为什么？→ 断言不匹配
断言不匹配 → 为什么？→ 返回值变了
返回值变了 → 为什么？→ 上游接口改了
上游接口改了 → 为什么没发现？→ 缺少契约测试
缺少契约测试 → 为什么？→ 没有集成测试规范 ← 根因
```

**关键规则**：
- 至少追问 5 层，但不要机械地恰好 5 次
- 每一层的"为什么"必须有事实支撑，不凭猜测
- 如果出现多个分支原因，分别追踪

### 鱼骨图（石川图）分析法
从六个维度分析失败根因：

| 维度 | 典型原因 |
|------|---------|
| **人员（People）** | 开发者理解偏差、代码审查遗漏、测试设计不当 |
| **流程（Process）** | 需求变更未同步、测试用例未更新、发布流程漏洞 |
| **代码（Code）** | 逻辑缺陷、边界处理不当、竞态条件、内存泄漏 |
| **环境（Environment）** | 测试环境与生产不一致、依赖版本不匹配、资源不足 |
| **数据（Data）** | 测试数据过期、数据状态不一致、数据库 schema 变更 |
| **工具（Tools）** | 测试框架 bug、CI 配置错误、mock 工具限制 |

### Pareto 分析法（80/20 法则）
- 统计失败分布：按模块、按失败类型、按开发者
- 找到 20% 的原因造成 80% 的失败
- 优先修复高频根因，产出/投入比最高

## 2. 失败模式分类

### 按确定性分类

| 类型 | 特征 | 常见原因 |
|------|------|---------|
| **确定性失败** | 每次运行都失败 | 代码逻辑错误、接口变更、断言错误 |
| **间歇性失败（Flaky）** | 有时通过有时失败 | 竞态条件、时序依赖、环境差异、资源竞争 |
| **环境依赖失败** | 特定环境才失败 | 配置差异、依赖版本、操作系统差异 |
| **数据依赖失败** | 特定数据才失败 | 测试数据污染、数据库状态、数据边界 |

### 按根因分类

| 根因类别 | 描述 | 修复策略 |
|---------|------|---------|
| **代码缺陷** | 被测代码有 bug | 修复代码，补充回归测试 |
| **测试缺陷** | 测试本身写错了 | 修复测试，审查测试设计 |
| **环境问题** | 测试环境配置不当 | 统一环境配置，容器化 |
| **设计变更** | 需求/接口变更导致测试过时 | 更新测试，引入契约测试 |
| **基础设施** | CI/CD 资源不足、网络抖动 | 基础设施优化，增加重试 |

## 3. Flaky 测试专项分析

Flaky 测试是测试套件中最有害的问题之一，会侵蚀团队对测试的信任。

### Flaky 测试的常见根因

1. **时序依赖**
   - 使用 `sleep` 而非显式等待
   - 异步操作没有正确同步
   - 时区/夏令时敏感逻辑

2. **测试间耦合**
   - 共享的全局状态未正确重置
   - 测试执行顺序依赖
   - 共享数据库/缓存未清理

3. **资源竞争**
   - 端口占用冲突
   - 文件系统并发写入
   - 数据库连接池耗尽

4. **外部依赖**
   - 网络请求未 mock
   - 第三方服务不稳定
   - DNS 解析超时

### Flaky 测试治理策略
- **隔离**：标记为 flaky，移出主流水线
- **监控**：统计 flaky 率，设定治理目标（< 1%）
- **修复**：按频率和影响排序修复
- **预防**：制定测试编写规范，禁止常见反模式

## 4. 缺陷聚集分析

### 缺陷密度计算
- **缺陷密度** = 缺陷数 / 代码规模（通常按千行代码 KLOC）
- 按模块计算，找出缺陷聚集区
- 行业基准：< 5 个/KLOC（普通），< 1 个/KLOC（高标准）

### 缺陷聚集的常见原因
1. **高复杂度模块**：圈复杂度 > 10 的函数容易出错
2. **频繁变更区域**：修改越多越容易引入回归
3. **多人协作交界**：接口边界和职责不清的区域
4. **历史遗留代码**：未重构的老代码，缺乏测试保护
5. **技术债务集中**：快速交付期积累的妥协

### 热点分析方法
- 将缺陷密度与变更频率交叉分析
- 高缺陷密度 + 高变更频率 = 最优先重构目标
- 高缺陷密度 + 低变更频率 = 可安排计划性重构

## 5. 失败趋势分析

### 时间维度
- **日趋势**：是否有特定时段失败率升高（如下班前的匆忙提交）
- **迭代趋势**：各迭代的失败率变化，是否在改善
- **发布前后**：发布前的失败率是否符合质量门控

### 关联维度
- **变更关联**：失败是否与特定提交关联
- **开发者关联**：是否有特定开发者的代码失败率更高
- **模块关联**：是否有模块间依赖导致的级联失败

### 预警信号
- 失败率突然上升 → 可能有重大代码变更未配测试
- Flaky 率持续攀升 → 测试基础设施恶化
- 同类失败反复出现 → 根因未被真正修复
- 新增失败集中在某模块 → 该模块需要重点关注

## 6. 修复优先级矩阵

使用 影响 x 频率 矩阵确定修复优先级：

```
          高影响
            │
     P0     │    P1
  (立即修复) │ (本迭代修复)
────────────┼────────────
     P2     │    P3
  (计划修复) │ (可接受风险)
            │
          低影响
    高频率          低频率
```

- **P0（高影响 + 高频率）**：阻断发布的严重问题，立即修复
- **P1（高影响 + 低频率）**：严重但罕见，本迭代内修复
- **P2（低影响 + 高频率）**：烦人但不致命，计划修复
- **P3（低影响 + 低频率）**：记录但可暂时接受
