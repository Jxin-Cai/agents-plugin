# 质量报告原则

---

## 1. 质量度量体系

### 核心 KPI

| 类别 | 指标 | 计算方法 | 基准 |
|------|------|---------|------|
| 覆盖率 | 行覆盖率 | 已覆盖行 / 总行数 | >= 80% |
| 覆盖率 | 分支覆盖率 | 已覆盖分支 / 总分支 | >= 70% |
| 覆盖率 | 新代码覆盖率 | 新代码已覆盖行 / 新代码总行 | >= 80% |
| 缺陷 | 缺陷密度 | 缺陷数 / KLOC | < 5 |
| 缺陷 | 缺陷移除效率 (DRE) | 发布前发现缺陷 / 总缺陷 | >= 85% |
| 缺陷 | 缺陷泄漏率 | 发布后发现缺陷 / 总缺陷 | < 10% |
| 效率 | 通过率 | 通过数 / 执行总数 | >= 95% |
| 效率 | MTTD | 缺陷引入到发现的平均时间 | < 2 天 |
| 效率 | MTTR | 缺陷发现到修复的平均时间 | < 3 天 |
| 稳定性 | Flaky 比例 | Flaky 测试数 / 总测试数 | < 1% |

### 衍生指标

| 指标 | 计算方法 | 意义 |
|------|---------|------|
| 测试有效性 | 真缺陷 / 总失败 x 100% | 发现真实问题的比例 |
| 自动化率 | 自动化测试 / 总测试 | 自动化程度 |
| 回归缺陷率 | 回归缺陷 / 总缺陷 | 修复引入新问题的频率 |

---

## 2. 质量门控判定

| 级别 | 含义 | 后果 |
|------|------|------|
| 通过（PASS） | 所有指标达标 | 可发布 |
| 有条件通过 | 核心达标，非核心部分未达标 | 需负责人确认风险后发布 |
| 阻断（BLOCK） | 核心指标未达标 | 不可发布，必须修复 |

**阻断条件（任一触发）**：未修复 P0 缺陷、新代码覆盖率 < 阈值、通过率 < 95%、阻断级安全漏洞、核心业务路径未覆盖。

---

## 3. 报告结构规范

必须包含章节：执行摘要 → 质量仪表盘 → 质量门控判定 → 覆盖率分析摘要 → 失败分析摘要 → 风险清单 → 改进建议 → 附录。

**执行摘要写法**：第一句给结论（良好/需关注/有风险）→ 2-3 句关键数据支撑 → 最后 1 句最重要的行动建议。总长不超过 5 句。

---

## 4. 趋势分析

- **对比维度**：与上次报告、与上一迭代、与基线
- **关键解读**：上升不一定好（可能是数字游戏）；下降需立即找原因；波动说明流程不稳定

---

## 5. 改进建议 SMART 原则

每条建议必须：具体（明确模块和操作）、可度量（目标数字）、可实现（迭代内可完成）、相关（与当前最突出问题相关）、有时限（明确截止时间）。

| 类别 | 时间 | 示例 |
|------|------|------|
| 快速修复 | 1-2 天 | 效果明显的小改进 |
| 迭代改进 | 一个迭代 | 需团队配合 |
| 长期治理 | 跨迭代 | 系统性改进 |

每条需预估：投入工作量、改善幅度、见效时间。

---

## 6. 受众适配

| 受众 | 关注重点 | 详细程度 | 语言 |
|------|---------|---------|------|
| 管理层 | 趋势、风险、Go/No-Go | 摘要级 | 业务语言 |
| 技术负责人 | 缺陷分布、覆盖盲区、改进优先级 | 模块级 | 技术语言 |
| 开发团队 | 具体失败、修复建议 | 代码级 | 技术细节 |
| QA 团队 | 测试有效性、Flaky、测试策略 | 用例级 | 测试语言 |

默认产出技术负责人级别，按需调整。
