# 质量报告原则

本文档定义了质量报告阶段必须遵循的原则。用这些原则确保报告的专业性和可操作性。

---

## 1. 质量度量体系

### 核心 KPI 指标

质量报告必须包含以下核心指标，每个指标需标注当前值、目标值和趋势：

| 类别 | 指标 | 计算方法 | 行业基准 |
|------|------|---------|---------|
| **覆盖率** | 行覆盖率 | 已覆盖行数 / 总行数 | >= 80% |
| **覆盖率** | 分支覆盖率 | 已覆盖分支数 / 总分支数 | >= 70% |
| **覆盖率** | 新代码覆盖率 | 新代码已覆盖行数 / 新代码总行数 | >= 80% |
| **缺陷** | 缺陷密度 | 缺陷数 / KLOC | < 5 |
| **缺陷** | 缺陷移除效率 (DRE) | 发布前发现缺陷 / 总缺陷 | >= 85% |
| **缺陷** | 缺陷泄漏率 | 发布后发现缺陷 / 总缺陷 | < 10% |
| **效率** | 测试用例通过率 | 通过数 / 执行总数 | >= 95% |
| **效率** | 平均检测时间 (MTTD) | 缺陷引入到发现的平均时间 | < 2 天 |
| **效率** | 平均修复时间 (MTTR) | 缺陷发现到修复的平均时间 | < 3 天 |
| **稳定性** | Flaky 测试比例 | Flaky 测试数 / 总测试数 | < 1% |
| **稳定性** | 测试套件执行时间 | 完整测试套件运行时长 | 因项目而异 |

### 衍生指标

| 指标 | 计算方法 | 意义 |
|------|---------|------|
| 测试有效性 | (真缺陷 / 总失败) x 100% | 测试发现真实问题的比例 |
| 自动化率 | 自动化测试数 / 总测试数 | 自动化程度 |
| 测试 ROI | 拦截缺陷价值 / 测试投入成本 | 测试投资回报 |
| 回归缺陷率 | 回归缺陷 / 总缺陷 | 修复引入新问题的频率 |

## 2. 质量门控判定

### 门控级别

| 级别 | 含义 | 后果 |
|------|------|------|
| **通过（PASS）** | 所有质量指标达标 | 可以发布 |
| **有条件通过（CONDITIONAL）** | 核心指标达标，非核心指标部分未达标 | 需要负责人确认风险后发布 |
| **阻断（BLOCK）** | 核心指标未达标 | 不可发布，必须修复 |

### 阻断条件（任一触发即阻断）
- 存在未修复的 P0 缺陷
- 新代码覆盖率 < 阈值
- 测试用例通过率 < 95%
- 存在阻断级别的安全漏洞
- 核心业务路径有未覆盖的测试

### 门控评估流程
1. 收集所有质量指标当前值
2. 对照阈值逐项判定
3. 识别阻断项和警告项
4. 综合判定门控结果
5. 如有条件通过，列出需确认的风险点

## 3. 报告结构规范

### 报告必须包含的章节

1. **执行摘要** — 一段话总结质量状态和关键发现
2. **质量仪表盘** — KPI 指标一览表，含当前值/目标值/趋势
3. **质量门控判定** — 通过/有条件通过/阻断，含判定依据
4. **覆盖率分析摘要** — 关键发现和盲区
5. **失败分析摘要** — 关键根因和修复优先级
6. **风险清单** — 当前已识别的质量风险
7. **改进建议** — 按优先级排序的改进行动项
8. **附录** — 详细数据和原始报告链接

### 执行摘要的写作规范
- 第一句话给出结论：质量状态是良好/需关注/有风险
- 接下来 2-3 句话说明关键数据支撑
- 最后 1 句话给出最重要的行动建议
- 总长度不超过 5 句话

---

## 4. 趋势分析与对比

### 时间对比
- **与上一次报告对比**：哪些指标改善了？哪些恶化了？
- **与上一个迭代对比**：迭代级别的质量趋势
- **与基线对比**：距离目标还有多远

### 趋势可视化建议
- 覆盖率趋势用折线图
- 缺陷分布用柱状图或饼图
- 质量门控用红绿灯仪表盘
- 改进进度用燃尽图

### 趋势解读要点
- 上升趋势 ≠ 一定好（可能是数字游戏）
- 下降趋势需要立即找原因
- 波动趋势说明流程不稳定
- 平稳趋势需要判断是否已达预期

## 5. 改进建议方法论

### SMART 原则
每条改进建议必须符合 SMART：
- **Specific（具体）**：明确说"给 OrderService 补充异常路径测试"，不说"提高覆盖率"
- **Measurable（可度量）**：目标覆盖率从 65% 提升到 80%
- **Achievable（可实现）**：在一个迭代内可完成
- **Relevant（相关）**：与当前最突出的质量问题相关
- **Time-bound（有时限）**：在 Sprint 15 结束前完成

### 改进类别
1. **快速修复（Quick Win）**：1-2 天可完成，效果明显
2. **迭代改进（Sprint Goal）**：一个迭代内完成，需团队配合
3. **长期治理（Strategic）**：跨迭代的系统性改进

### 改进效果预估
每条建议应预估：
- 预计投入工作量
- 预计改善幅度
- 预计见效时间

## 6. 报告受众适配

### 不同受众关注点

| 受众 | 关注重点 | 详细程度 | 语言风格 |
|------|---------|---------|---------|
| **管理层** | 质量趋势、风险、Go/No-Go 决策 | 摘要级 | 业务语言 |
| **技术负责人** | 缺陷分布、覆盖率盲区、改进优先级 | 模块级 | 技术语言 |
| **开发团队** | 具体失败、修复建议、最佳实践 | 代码级 | 技术细节 |
| **QA 团队** | 测试有效性、Flaky 测试、测试策略 | 用例级 | 测试语言 |

### 适配策略
- 默认产出技术负责人级别的报告
- 根据用户需求调整详细程度
- 执行摘要面向所有受众
