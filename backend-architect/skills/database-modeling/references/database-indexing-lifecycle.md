# 数据库建模原则——索引与数据生命周期

本文档定义了索引设计、反范式化策略和数据生命周期管理原则。范式理论与 ER 建模见 `database-modeling-principles.md`。

---

## 1. 索引设计

索引是查询性能的加速器，但不是越多越好。

### 索引选择原则
- **覆盖高频查询**：分析 API 端点，找出 WHERE、JOIN、ORDER BY 中的字段
- **最左前缀原则**：复合索引 `(a, b, c)` 可服务 `WHERE a=?`、`WHERE a=? AND b=?`、`WHERE a=? AND b=? AND c=?`
- **选择性优先**：高选择性字段（用户ID）比低选择性字段（性别）更适合索引
- **覆盖索引**：查询只需索引中的字段时可避免回表

### 索引陷阱
- **过度索引**：每个索引增加写入开销和存储成本，表上不超过 5-6 个索引
- **冗余索引**：`(a)` 和 `(a, b)` 同时存在时，`(a)` 是冗余的
- **低选择性索引**：对布尔字段建索引通常无意义（除非数据分布极度不均）
- **函数索引遗漏**：`WHERE YEAR(created_at) = 2026` 无法命中 `created_at` 索引

### 必建索引清单
- 主键索引（自动创建）
- 唯一业务约束（邮箱、手机号、订单号）
- 外键字段（`user_id`、`order_id`）
- 常用查询条件字段
- 排序字段（`created_at`、`updated_at`）

## 2. 反范式化策略

范式化保证正确性，反范式化换取性能。两者的平衡是数据库设计的艺术。

### 何时反范式化
- 某个联表查询频率极高（QPS > 1000）且联表数据变化不频繁
- 聚合查询成本高（COUNT、SUM），预计算可显著降低延迟
- 读写比极高（读 >> 写），冗余字段的维护成本可接受

### 反范式化手段与代价

| 手段 | 代价 | 一致性保障 |
|------|------|-----------|
| 冗余字段 | 更新时需同步更新 | 事务保证 / 异步补偿 / 定时对账 |
| 预计算字段 | 源数据变化需重新计算 | 事件驱动更新 / 定时重算 |
| 物化视图 | 存储成本 + 刷新延迟 | 数据库引擎自动维护 |
| 宽表合并 | 表结构臃肿、NULL 值增多 | 无额外成本（同一行数据） |

### 决策模板
```
字段/表: {名称}
原因: {为什么需要反范式化}
读写比: {读 QPS} / {写 QPS}
一致性方案: {如何保证冗余数据一致}
回滚方案: {如果效果不好如何恢复范式化}
```

## 3. 数据生命周期管理

数据不是永远存在的，必须设计好创建到销毁的完整生命周期。

### 软删除 vs 硬删除
- **软删除**（`deleted_at` 字段）：适合需要数据恢复、审计追溯的场景。注意唯一约束需排除已删除数据
- **硬删除**：适合无审计要求且存储成本敏感的场景。删除前备份

### 数据归档
- 热数据（近 3 个月）：主库，SSD 存储
- 温数据（3-12 个月）：只读副本或历史表
- 冷数据（> 12 个月）：归档存储（S3 / 对象存储）
- **分区表**：按时间分区（月/季度），方便归档和删除

### 审计字段标准
每张业务表应包含：
```sql
created_at  TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
updated_at  TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
created_by  BIGINT,        -- 创建人 ID
updated_by  BIGINT,        -- 最后更新人 ID
deleted_at  TIMESTAMP NULL  -- 软删除标记（NULL 表示未删除）
```
