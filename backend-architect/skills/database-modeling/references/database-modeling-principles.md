# 数据库建模原则

本文档定义了数据库建模阶段必须遵循的原则。基于关系型数据库理论和行业最佳实践。

---

## 1. 范式理论

范式化是数据库设计的理论基础，目标是消除数据冗余和更新异常。

### 第一范式（1NF）
- 每个字段的值是 **原子的**（不可再分）
- 没有重复的列组（如 `phone1`、`phone2`、`phone3`）
- **违反信号**：字段中存储逗号分隔的列表、JSON 数组作为主要查询字段

### 第二范式（2NF）
- 满足 1NF
- 非主键字段 **完全依赖** 于主键（不存在部分依赖）
- **违反信号**：复合主键的表中，某些字段只依赖主键的一部分
- **修正方法**：将部分依赖的字段拆到独立的表中

### 第三范式（3NF）
- 满足 2NF
- 非主键字段之间 **不存在传递依赖**
- **违反信号**：`订单表` 中同时存储 `客户ID` 和 `客户名称`（客户名称依赖客户ID，不直接依赖订单ID）
- **修正方法**：去除传递依赖字段，通过关联查询获取

### BCNF（Boyce-Codd 范式）
- 满足 3NF
- 每个决定因素都是候选键
- **适用场景**：存在多个候选键且候选键之间有重叠时

### 实践建议
- **默认目标**：达到 3NF
- **何时停在 2NF**：极少数历史遗留系统迁移场景
- **何时追求 BCNF**：核心业务表、数据一致性要求极高的场景

## 2. ER 建模方法

实体-关系（Entity-Relationship）建模是从业务概念到数据结构的桥梁。

### 三层建模法
1. **概念模型**：只关注实体和关系，不涉及属性和数据类型——用于和业务方沟通
2. **逻辑模型**：添加属性、数据类型、约束——用于技术方案评审
3. **物理模型**：考虑具体数据库引擎特性（MySQL/PostgreSQL）、分区、存储引擎——用于实施

### 实体识别原则
- **独立实体**：有自己的生命周期，可以独立存在（用户、商品）
- **依赖实体**：依附于其他实体存在（订单明细依附于订单）
- **关联实体**：N:N 关系的中间表，可以携带额外属性（用户-角色关联表携带授权时间）

### 关系基数标注
- **1:1** — 考虑是否应该合并为一张表（除非有不同的访问频率或安全级别）
- **1:N** — 外键放在 N 端（子表中存储父表 ID）
- **N:N** — 必须通过关联表实现，关联表有自己的主键

### 命名规范
- 表名：小写蛇形、复数（`users`、`order_items`）或单数（团队统一即可）
- 列名：小写蛇形（`created_at`、`user_id`）
- 主键：`id` 或 `{表名}_id`
- 外键：`{关联表名单数}_id`（如 `user_id`、`order_id`）
- 索引：`idx_{表名}_{字段名}`（如 `idx_orders_user_id`）
- 唯一约束：`uk_{表名}_{字段名}`

## 3. 主键策略

主键选择影响性能、分布式扩展和数据迁移。

### 策略对比

| 策略 | 优点 | 缺点 | 适用场景 |
|------|------|------|---------|
| 自增 ID | 有序、紧凑、索引友好 | 分库分表困难、可预测 | 单库单表、内部系统 |
| UUID v4 | 全局唯一、无中心依赖 | 无序、索引碎片、存储大 | 分布式系统、安全要求高 |
| UUID v7 | 时间有序 + 全局唯一 | 存储比自增大 | 分布式系统（推荐） |
| 雪花 ID | 有序、可提取时间、紧凑 | 依赖时钟同步、需部署发号器 | 高并发分布式系统 |

### 实践建议
- **对外暴露的 ID**（API 路径中的 ID）：使用 UUID 或雪花 ID，不暴露自增 ID（防止信息泄露和爬取）
- **内部关联的 ID**（外键）：可以用自增 ID 提升 JOIN 性能
- **双 ID 模式**：内部用自增 `id`，对外用 `public_id`（UUID）

## 4. 索引设计

索引是查询性能的加速器，但不是越多越好。

### 索引选择原则
- **覆盖高频查询**：分析 API 端点，找出 WHERE、JOIN、ORDER BY 中的字段
- **最左前缀原则**：复合索引 `(a, b, c)` 可以服务 `WHERE a=?`、`WHERE a=? AND b=?`、`WHERE a=? AND b=? AND c=?`
- **选择性优先**：高选择性的字段（如用户ID）比低选择性的字段（如性别）更适合索引
- **覆盖索引**：如果查询只需要索引中的字段，可以避免回表

### 索引陷阱
- **过度索引**：每个索引都增加写入开销和存储成本。表上不超过 5-6 个索引
- **冗余索引**：`(a)` 和 `(a, b)` 同时存在时，`(a)` 是冗余的
- **低选择性索引**：对布尔字段建索引通常无意义（除非数据分布极度不均）
- **函数索引遗漏**：`WHERE YEAR(created_at) = 2026` 无法命中 `created_at` 索引，需要函数索引或改写查询

### 必建索引清单
- 主键索引（自动创建）
- 唯一业务约束（邮箱、手机号、订单号）
- 外键字段（`user_id`、`order_id`）
- 常用查询条件字段
- 排序字段（`created_at`、`updated_at`）

## 5. 反范式化策略

范式化保证正确性，反范式化换取性能。两者的平衡是数据库设计的艺术。

### 何时反范式化
- 某个联表查询频率极高（QPS > 1000）且联表数据变化不频繁
- 聚合查询成本高（如统计表的 COUNT、SUM），预计算可以显著降低延迟
- 读写比极高（读 >> 写），冗余字段的维护成本可接受

### 反范式化手段与代价

| 手段 | 代价 | 一致性保障 |
|------|------|-----------|
| 冗余字段 | 更新时需同步更新冗余字段 | 事务保证 / 异步补偿 / 定时对账 |
| 预计算字段 | 每次源数据变化需重新计算 | 事件驱动更新 / 定时重算 |
| 物化视图 | 存储成本 + 刷新延迟 | 数据库引擎自动维护 |
| 宽表合并 | 表结构臃肿、NULL 值增多 | 无额外成本（同一行数据） |

### 反范式化决策模板
```
字段/表: {名称}
原因: {为什么需要反范式化}
读写比: {读 QPS} / {写 QPS}
一致性方案: {如何保证冗余数据一致}
回滚方案: {如果效果不好如何恢复范式化}
```

## 6. 数据生命周期管理

数据不是永远存在的，必须设计好创建到销毁的完整生命周期。

### 软删除 vs 硬删除
- **软删除**（`deleted_at` 字段）：适合需要数据恢复、审计追溯的场景。注意唯一约束需要排除已删除数据
- **硬删除**：适合无审计要求且存储成本敏感的场景。删除前备份

### 数据归档
- 热数据（近 3 个月）：主库，SSD 存储
- 温数据（3-12 个月）：只读副本或历史表
- 冷数据（> 12 个月）：归档存储（S3 / 对象存储）
- **分区表**：按时间分区（月/季度），方便归档和删除

### 审计字段标准
每张业务表应包含：
```sql
created_at  TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
updated_at  TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
created_by  BIGINT,        -- 创建人 ID
updated_by  BIGINT,        -- 最后更新人 ID
deleted_at  TIMESTAMP NULL  -- 软删除标记（NULL 表示未删除）
```
