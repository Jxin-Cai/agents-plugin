# 数据库建模

用户传入的参数：`$ARGUMENTS`

**核心心态：** 数据库是系统的地基，地基不牢地动山摇。先保证数据正确性（范式化），再按实际查询需求做有节制的反范式化。

## Step 1: 识别实体与属性

如果 `$ARGUMENTS` 非空，以此作为初始输入。如果 API 设计已完成，从 API 资源清单中提取实体。

引导用户识别核心实体及其属性：

| 维度 | 需回答 |
|------|--------|
| 实体识别 | 系统需要持久化哪些业务对象？ |
| 属性枚举 | 每个实体有哪些属性？哪些必填？哪些有默认值？ |
| 数据类型 | 每个属性的类型和约束？（字符串长度、数值范围、枚举值） |
| 审计字段 | 是否需要 `created_at`、`updated_at`、`created_by`、`deleted_at`（软删除）？ |

向用户展示实体-属性清单，确认完整性。

**⏸️ 等待用户确认后继续。**

## Step 2: 关系建模（ER 图）

用文本格式绘制 ER 关系图，对每个关系明确：
- **基数**：1:1、1:N、N:N
- **强弱依赖**：删除父实体时子实体如何处理？（CASCADE / SET NULL / RESTRICT）
- **关联表设计**：N:N 关系的中间表需要哪些额外属性？
- **自引用关系**：是否存在树形结构（组织架构、评论回复）？

**⏸️ 等待用户确认后继续。**

## Step 3: 范式化检查

按范式理论逐级检查：

| 范式 | 检查项 | 结果 |
|------|--------|------|
| 1NF | 所有字段原子值？无重复组？ | |
| 2NF | 非主键字段完全依赖主键？ | |
| 3NF | 无传递依赖？ | |

标注每个违反范式的点，向用户解释影响并建议修正方案。

**⏸️ 等待用户确认修正方案后继续。**

## Step 4: 反范式化决策

基于实际查询场景，与用户讨论有节制的反范式化。每个决策必须记录 **原因**、**读写比数据** 和 **数据一致性保障方案**。

| 反范式化手段 | 适用场景 | 代价 |
|-------------|---------|------|
| 冗余字段 | 高频联表查询 | 数据一致性风险 |
| 预计算字段 | 聚合查询 | 更新成本增加 |
| 宽表合并 | 1:1 关系且总是一起查询 | 表结构臃肿 |
| JSON 字段 | 半结构化扩展属性 | 无法索引、难以校验 |

**⏸️ 等待用户逐项确认。**

## Step 5: 索引策略

为每张表设计索引策略，基于 API 的实际查询条件：
- **主键索引**：自增 ID / UUID / 雪花 ID？各自权衡
- **唯一索引**：业务唯一约束（邮箱、手机号、订单号）
- **查询索引**：WHERE、JOIN、ORDER BY 中的字段
- **复合索引**：多字段联合查询的最左前缀原则
- **覆盖索引**：高频查询是否可以只走索引不回表？

向用户展示每张表的索引清单，并解释为什么需要这个索引。

**⏸️ 等待用户确认后继续。**

## Step 6: 保存产出

将数据库模型文档保存到 `{工作目录}/database/db-model-{日期}.md`

内容包括：实体-属性清单（含数据类型和约束）、ER 关系图、范式化检查结果、反范式化决策记录、索引策略清单。

使用 `AskUserQuestion` 工具向用户展示以下选项：

产出摘要：[N] 个实体，[M] 个关系，索引 [K] 个。范式化检查：[X] 项通过，反范式化决策 [Y] 项。

- **进入可扩展性评审（推荐）** — 对数据库模型进行扩展性和性能评审
- **补充实体或关系** — 如果感觉有遗漏
- **回到 API 设计** — 如果发现数据模型与 API 设计不匹配

**⏸️ 停下来等待用户选择。不要自动执行。**
