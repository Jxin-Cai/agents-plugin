# 可扩展性评审

用户传入的参数：`$ARGUMENTS`

**核心心态：** 扩展性问题不是"以后再说"的问题。在设计阶段识别瓶颈，比在线上出事后紧急扩容成本低 100 倍。

---

使用 Read 工具加载以下引用文件，严格遵守其中所有规则：

- `references/scalability-review-principles.md` — CAP 定理、扩展策略、缓存设计
- `references/scalability-async-ha-principles.md` — 异步处理、分库分表、容灾高可用

## Step 1: 规模画像

引导用户建立系统的规模画像：

| 维度 | 需回答 |
|------|--------|
| 用户量 | 注册用户数？DAU/MAU？同时在线峰值？ |
| 数据量 | 核心表预估行数？年增长率？单行数据大小？ |
| 请求量 | 核心 API 的 QPS？读写比？峰值/均值比？ |
| 延迟要求 | P50/P95/P99 延迟目标？ |
| 可用性要求 | SLA 目标？ |
| 一致性要求 | 强一致 / 最终一致？哪些场景不能容忍延迟？ |

如果用户无法给出精确数值，引导估算量级（百/千/万/百万）。

**⏸️ 等待用户提供规模信息后继续。**

## Step 2: 瓶颈分析

基于规模画像，系统性分析每一层的潜在瓶颈：

| 层级 | 检查项 |
|------|--------|
| 应用层 | 单机 QPS 承载、CPU/内存密集操作、长连接上限 |
| 数据层 | 大表查询性能、热点数据、写入量、JOIN 复杂度 |
| 网络层 | 响应体大小、大文件传输、跨区域延迟 |
| 第三方依赖 | 外部 API SLA、限流策略、降级方案 |

向用户展示瓶颈分析结果，标注风险等级（高/中/低）。

**⏸️ 等待用户确认后继续。**

## Step 3: CAP 权衡决策

引导用户对核心业务场景做 CAP 权衡，每个场景必须关联到具体业务：

```
场景: {业务场景名称}
├── 一致性需求: 强一致 / 最终一致 / 因果一致
├── 可用性需求: 必须响应 / 可短暂降级 / 可拒绝服务
├── 分区容错: 是否跨区域部署？
└── CAP 选择: CP / AP
    └── 代价: {放弃了什么、如何补偿}
```

**⏸️ 等待用户逐个场景确认。**

## Step 4: 扩展策略制定

针对识别的瓶颈，制定分层扩展策略。每个策略必须标注实施成本和预期收益：

### 应用层扩展
| 策略 | 做法 | 成本 | 收益 |
|------|------|------|------|
| 水平扩展 | 无状态服务 + 负载均衡 | 中 | 线性提升吞吐 |
| 异步处理 | 消息队列削峰 | 中 | 峰值抗压 |
| 缓存层 | Redis/本地缓存 | 低 | 降低数据库压力 |
| 读写分离 | 读走从库/缓存 | 高 | 读性能提升 |

### 数据层扩展
| 策略 | 做法 | 成本 | 代价 |
|------|------|------|------|
| 读写分离 | 主库写、从库读 | 中 | 主从延迟窗口 |
| 垂直分库 | 按业务域拆库 | 高 | 跨库事务困难 |
| 水平分表 | 按规则分片 | 高 | 跨分片查询复杂 |
| 缓存前置 | Redis 缓存热数据 | 低 | 缓存一致性问题 |

**⏸️ 等待用户确认扩展策略后继续。**

## Step 5: 容灾方案

制定系统的容灾和高可用方案：

| 场景 | 检查项 |
|------|--------|
| 单点故障 | 每个组件是否有冗余？数据库主从切换？应用多实例？ |
| 数据丢失 | 备份策略？RPO（可容忍丢失多少数据）？ |
| 服务降级 | 核心功能和非核心功能的降级策略？熔断器配置？ |
| 灾难恢复 | RTO（恢复时间目标）？异地容灾？ |
| 监控告警 | 关键指标？告警阈值？值班响应流程？ |

**⏸️ 等待用户确认后继续。**

## Step 6: 保存产出

将可扩展性评审文档保存到 `{工作目录}/scalability/scalability-review-{日期}.md`

内容包括：规模画像、瓶颈分析报告（按风险等级排序）、CAP 权衡决策记录、分层扩展策略（含成本和收益）、容灾方案。

## Step 7: 菜单

使用 `AskUserQuestion` 工具向用户展示以下选项：

产出摘要：识别瓶颈 [N] 个（高风险 [H] 个），扩展策略 [M] 项，CAP 决策 [K] 个场景，容灾方案已覆盖 [X] 个场景。

- **导出完整架构方案（推荐）** — 汇总 API + 数据库 + 扩展性评审为完整文档
- **深入某个瓶颈** — 对特定瓶颈做更详细的方案设计
- **回到数据库建模** — 如果评审发现数据模型需要调整

**⏸️ 停下来等待用户选择。不要自动执行。**

<IMPORTANT>
本技能完成后，展示菜单并等待用户选择下一步。不要自动执行后续技能。
每个扩展方案必须同时标注实施成本和预期收益——禁止无代价分析的"银弹"推荐。
CAP 权衡必须关联到具体业务场景，不可笼统选择。
</IMPORTANT>
