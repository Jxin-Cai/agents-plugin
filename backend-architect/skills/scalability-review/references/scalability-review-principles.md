# 可扩展性评审原则——CAP 与扩展策略

本文档定义了 CAP 定理、扩展策略和缓存设计原则。异步处理、分库分表和容灾高可用见 `scalability-async-ha-principles.md`。

---

## 1. CAP 定理与权衡

分布式系统中，一致性（C）、可用性（A）、分区容错性（P）三者不可兼得。

### CAP 三要素

| 属性 | 含义 | 放弃的代价 |
|------|------|-----------|
| 一致性（C） | 所有节点在同一时刻看到相同的数据 | 允许读到旧数据（最终一致） |
| 可用性（A） | 每个请求都能收到非错误响应 | 部分请求可能超时或被拒绝 |
| 分区容错（P） | 网络分区时系统仍能运作 | 实际上不可放弃 |

### 实践选择
- **CP 系统**（ZooKeeper、etcd）：保证一致性，分区时拒绝服务。适合配置管理、分布式锁、金融交易
- **AP 系统**（Cassandra、DynamoDB）：保证可用性，分区时允许不一致。适合社交动态、推荐系统

### PACELC 扩展
- **分区时（PAC）**：选择 A 还是 C？
- **正常时（ELC）**：选择低延迟（L）还是强一致（C）？

## 2. 水平扩展与垂直扩展

### 垂直扩展（Scale Up）
- **做法**：给单台机器加 CPU、内存、SSD
- **优点**：简单，不改架构
- **天花板**：物理硬件有上限，成本指数增长

### 水平扩展（Scale Out）
- **做法**：增加更多机器，负载分摊
- **前提条件**：应用无状态、请求可路由、数据可分片
- **挑战**：数据一致性、分布式事务、运维复杂度

### 扩展决策树
```
当前性能不够？
├── 单机资源未耗尽 → 垂直扩展（快速、低风险）
├── 单机资源已接近上限 → 水平扩展
│   ├── 应用层 → 无状态化 + 负载均衡
│   ├── 数据层 → 读写分离 → 垂直分库 → 水平分表
│   └── 缓存层 → 本地缓存 → 分布式缓存 → 多级缓存
└── 无法判断 → 先做压测，用数据说话
```

## 3. 缓存策略

缓存是性能优化的第一手段，但也是数据一致性问题的主要来源。

### 缓存模式

| 模式 | 读路径 | 写路径 | 一致性 |
|------|--------|--------|--------|
| Cache-Aside | 先读缓存，miss 时读数据库并回填 | 先写数据库，再删缓存 | 最终一致 |
| Read-Through | 缓存自动从数据库加载 | 同 Cache-Aside | 最终一致 |
| Write-Through | 同 Cache-Aside | 同时写缓存和数据库 | 较强一致 |
| Write-Behind | 同 Cache-Aside | 先写缓存，异步写数据库 | 弱一致 |

**推荐**：大多数场景使用 Cache-Aside。

### 缓存三大问题

| 问题 | 描述 | 解决方案 |
|------|------|---------|
| **穿透** | 查询不存在的数据，打到数据库 | 布隆过滤器 / 缓存空值（TTL 短） |
| **击穿** | 热点 Key 过期瞬间大量请求打到数据库 | 互斥锁 / 热点 Key 永不过期 + 异步更新 |
| **雪崩** | 大量 Key 同时过期 | TTL 加随机偏移 / 多级缓存 / 熔断降级 |

### 缓存设计原则
- 缓存的数据必须有 TTL，没有永远不过期的缓存
- 缓存 Key 命名规范：`{业务}:{实体}:{id}`
- 大 Value 拆分（> 1MB 考虑拆分或压缩）
- 监控缓存命中率，低于 90% 需要检查缓存策略
