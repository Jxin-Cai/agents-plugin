# 可扩展性评审原则

本文档定义了可扩展性评审阶段必须遵循的原则。基于分布式系统理论和云原生架构最佳实践。

---

## 1. CAP 定理与权衡

分布式系统中，一致性（Consistency）、可用性（Availability）、分区容错性（Partition Tolerance）三者不可兼得。

### CAP 三要素

| 属性 | 含义 | 放弃的代价 |
|------|------|-----------|
| 一致性（C） | 所有节点在同一时刻看到相同的数据 | 允许读到旧数据（最终一致） |
| 可用性（A） | 每个请求都能收到非错误响应 | 部分请求可能超时或被拒绝 |
| 分区容错（P） | 网络分区时系统仍能运作 | 实际上不可放弃（网络分区是现实） |

### 实践选择

由于网络分区不可避免，实际选择是 **CP vs AP**：
- **CP 系统**（如 ZooKeeper、etcd）：保证一致性，分区时拒绝服务。适合配置管理、分布式锁、金融交易
- **AP 系统**（如 Cassandra、DynamoDB）：保证可用性，分区时允许不一致。适合社交动态、推荐系统、日志

### PACELC 扩展
CAP 定理只讨论分区时的权衡。PACELC 扩展了正常情况下的权衡：
- **分区时（PAC）**：选择 A 还是 C？
- **正常时（ELC）**：选择低延迟（L）还是强一致（C）？
- 例如：DynamoDB 是 PA/EL（分区时选可用，正常时选低延迟）

## 2. 水平扩展与垂直扩展

### 垂直扩展（Scale Up）
- **做法**：给单台机器加 CPU、内存、SSD
- **优点**：简单，不改架构
- **天花板**：物理硬件有上限，成本指数增长
- **适用**：数据库主节点、初期快速扩容

### 水平扩展（Scale Out）
- **做法**：增加更多机器，负载分摊
- **前提条件**：
  - 应用无状态（状态外部化到 Redis/数据库）
  - 请求可路由（负载均衡器）
  - 数据可分片（分片策略）
- **挑战**：数据一致性、分布式事务、运维复杂度

### 扩展决策树
```
当前性能不够？
├── 单机资源未耗尽 → 垂直扩展（快速、低风险）
├── 单机资源已接近上限 → 水平扩展
│   ├── 应用层 → 无状态化 + 负载均衡
│   ├── 数据层 → 读写分离 → 垂直分库 → 水平分表
│   └── 缓存层 → 本地缓存 → 分布式缓存 → 多级缓存
└── 无法判断 → 先做压测，用数据说话
```

## 3. 缓存策略

缓存是性能优化的第一手段，但也是数据一致性问题的主要来源。

### 缓存模式

| 模式 | 读路径 | 写路径 | 一致性 |
|------|--------|--------|--------|
| Cache-Aside | 先读缓存，miss 时读数据库并回填 | 先写数据库，再删缓存 | 最终一致 |
| Read-Through | 缓存自动从数据库加载 | 同 Cache-Aside | 最终一致 |
| Write-Through | 同 Cache-Aside | 同时写缓存和数据库 | 较强一致 |
| Write-Behind | 同 Cache-Aside | 先写缓存，异步写数据库 | 弱一致（可能丢数据） |

**推荐**：大多数场景使用 Cache-Aside。

### 缓存三大问题

| 问题 | 描述 | 解决方案 |
|------|------|---------|
| **穿透** | 查询不存在的数据，每次都打到数据库 | 布隆过滤器 / 缓存空值（TTL 短） |
| **击穿** | 热点 Key 过期瞬间大量请求打到数据库 | 互斥锁 / 热点 Key 永不过期 + 异步更新 |
| **雪崩** | 大量 Key 同时过期 | TTL 加随机偏移 / 多级缓存 / 熔断降级 |

### 缓存设计原则
- 缓存的数据必须有 TTL，没有永远不过期的缓存
- 缓存 Key 命名规范：`{业务}:{实体}:{id}`（如 `order:detail:12345`）
- 大 Value 拆分（> 1MB 的缓存值考虑拆分或压缩）
- 监控缓存命中率，低于 90% 需要检查缓存策略

## 4. 异步处理与消息队列

并非所有操作都需要同步完成。异步处理是削峰填谷的核心手段。

### 适合异步的场景
- 通知发送（短信、邮件、推送）
- 日志写入和审计记录
- 数据同步（搜索引擎索引、数据仓库）
- 文件处理（图片压缩、视频转码）
- 非核心业务逻辑（积分计算、统计更新）

### 消息队列选型考量

| 维度 | Kafka | RabbitMQ | Redis Streams |
|------|-------|----------|--------------|
| 吞吐量 | 极高（百万/秒） | 中等（万/秒） | 高（十万/秒） |
| 延迟 | 毫秒级 | 微秒级 | 毫秒级 |
| 持久化 | 磁盘持久化 | 可配置 | AOF/RDB |
| 消息顺序 | 分区内有序 | 队列内有序 | Stream 内有序 |
| 适用场景 | 大数据流、日志 | 业务消息、RPC | 轻量级异步 |

### 消息可靠性保证
- **至少一次投递**：消费者处理后确认（ACK），失败重投。消费者必须幂等
- **消息积压处理**：监控消费延迟，积压超阈值告警。扩容消费者或临时增加处理线程
- **死信队列**：多次消费失败的消息进入死信队列，人工排查

## 5. 分库分表策略

当单库单表无法承载数据量和请求量时，需要分库分表。

### 分库分表时机
- 单表行数 > 5000 万或单表数据量 > 10GB（经验值，需结合实际查询模式）
- 单库连接数打满或磁盘 IO 瓶颈
- 业务域清晰，可按业务拆分

### 分片策略

| 策略 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| Range 分片 | 按 ID 范围或时间范围 | 范围查询友好 | 热点问题（新数据集中在最新分片） |
| Hash 分片 | 对分片键取模 | 数据均匀分布 | 范围查询需扫描所有分片 |
| 一致性 Hash | 虚拟节点 + Hash 环 | 扩容时只迁移少量数据 | 实现复杂 |

### 分片键选择原则
- 选择 **高基数** 字段（用户 ID 而非性别）
- 选择 **查询最频繁** 的字段（大多数查询都带这个条件）
- 避免 **热点分片**（如按时间分片导致最新分片压力大）
- 分片键一旦选定 **极难更改**，务必慎重

### 分库分表带来的挑战
- 跨分片查询需要聚合层
- 分布式事务（Saga/TCC/本地消息表）
- 全局唯一 ID 生成
- 数据迁移和扩容复杂度

## 6. 容灾与高可用

系统的可用性是用停机时间衡量的，不是用代码质量衡量的。

### SLA 对照表

| SLA | 年宕机时间 | 月宕机时间 | 适用 |
|-----|-----------|-----------|------|
| 99% | 3.65 天 | 7.3 小时 | 内部工具 |
| 99.9% | 8.77 小时 | 43.8 分钟 | 一般业务 |
| 99.95% | 4.38 小时 | 21.9 分钟 | 重要业务 |
| 99.99% | 52.6 分钟 | 4.38 分钟 | 核心业务 |
| 99.999% | 5.26 分钟 | 26.3 秒 | 金融/支付 |

### 容灾层级

| 层级 | 手段 | 保护范围 |
|------|------|---------|
| 应用层 | 多实例 + 负载均衡 + 健康检查 | 单实例故障 |
| 数据层 | 主从复制 + 自动故障转移 | 单节点故障 |
| 机房级 | 同城双活 / 两地三中心 | 单机房故障 |
| 区域级 | 异地多活 / 冷备恢复 | 自然灾害/区域故障 |

### 关键指标
- **RPO（Recovery Point Objective）**：可容忍丢失多少数据？（如最近 5 分钟）
- **RTO（Recovery Time Objective）**：恢复需要多长时间？（如 30 分钟内）
- **MTTR（Mean Time To Recovery）**：平均恢复时间
- **MTBF（Mean Time Between Failures）**：平均无故障时间

### 容灾设计模式
- **熔断器**（Circuit Breaker）：下游故障时快速失败，避免级联故障
- **舱壁隔离**（Bulkhead）：隔离不同业务的资源池，防止一个业务拖垮全部
- **限流降级**：流量超载时降级非核心功能，保护核心链路
- **混沌工程**：主动注入故障（Netflix Chaos Monkey），验证系统韧性
