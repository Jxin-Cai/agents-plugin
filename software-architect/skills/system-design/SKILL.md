## Step 1: 采集架构上下文

如果 `$ARGUMENTS` 非空，以此作为初始输入。

使用 Glob 扫描项目根目录，Read 配置文件（`package.json` / `pom.xml` / `build.gradle` / `go.mod` / `Cargo.toml` / `pyproject.toml` 等），提取以下信息：

| 维度 | 扫描方式 | 产出 |
|------|---------|------|
| 技术栈 | Read 包管理配置文件，识别语言/框架/数据库/中间件 | 技术栈清单 |
| 架构模式 | Glob `**/docker-compose*` `**/Dockerfile` `**/k8s/**`，判断单体/微服务/事件驱动 | 架构模式判断 |
| 部署环境 | Read CI/CD 配置（`.github/workflows/` / `Jenkinsfile` / `.gitlab-ci.yml`） | 部署方式 |
| 技术债务 | Glob `**/TODO` `**/FIXME`，Read 已有架构文档 | 约束清单 |

追问用户确认或补充：

- **业务目标**：这个系统要解决什么业务问题？
- **核心用户**：谁在使用这个系统？（人和外部系统）
- **质量属性优先级**：性能、可用性、安全性、可修改性——哪些最重要？
- **约束条件**：不可改变的技术约束是什么？（已有系统、团队技能、预算、时间）
- **规模预期**：用户量、数据量、并发量的量级？

将上下文保存到 `{工作目录}/context/context-{日期}.md`。

**⏸️ 等待用户确认后继续。**

## Step 2: C4 Level 1 — 系统上下文图

绘制系统上下文图（用文本描述，非图形工具）：

```
[用户角色 A] ---> [目标系统] ---> [外部系统 X]
[用户角色 B] ---> [目标系统] <--- [外部系统 Y]
```

明确标注：
- **系统边界**：目标系统做什么、不做什么
- **用户角色**：谁与系统交互，交互目的是什么
- **外部依赖**：依赖哪些外部系统，依赖方式（API/消息/文件）
- **数据流向**：数据从哪来、到哪去

向用户展示系统上下文图，确认边界和依赖是否完整。

**⏸️ 等待用户确认后继续。**

## Step 3: C4 Level 2 — 容器图

将系统拆分为容器（可独立部署的单元）：

```
[目标系统]
├── [Web 应用] — 技术：React/Vue/...
├── [API 服务] — 技术：Spring Boot/Express/...
├── [数据库] — 技术：PostgreSQL/MongoDB/...
├── [消息队列] — 技术：Kafka/RabbitMQ/...
└── [缓存] — 技术：Redis/...
```

每个容器标注：
- **职责**：这个容器做什么
- **技术选型**：用什么技术实现，为什么选这个
- **通信方式**：容器间怎么通信（REST/gRPC/消息/事件）
- **数据存储**：数据存在哪里

**关键追问**：
- 这些容器的边界是否对齐业务能力？
- 容器间的通信是否足够松耦合？
- 是否有容器承担了过多职责？

向用户展示容器图，确认拆分和技术选型。

**⏸️ 等待用户确认后继续。**

## Step 4: C4 Level 3 — 组件图（核心容器）

选择 1-2 个最核心的容器进行组件级设计：

```
[API 服务]
├── [Controller 层] — 处理 HTTP 请求
├── [Service 层] — 业务逻辑
├── [Domain 层] — 领域模型
├── [Repository 层] — 数据访问
└── [Integration 层] — 外部系统集成
```

每个组件标注：
- **职责**：单一职责描述
- **依赖方向**：依赖哪些其他组件（依赖应向内指向 Domain）
- **接口契约**：对外暴露的接口

**关键追问**：
- 依赖方向是否遵循依赖倒置原则？
- 是否存在循环依赖？
- 组件的可测试性如何？

向用户展示组件图。

**⏸️ 等待用户确认后继续。**

## Step 5: 关键架构决策清单

梳理设计过程中涉及的关键架构决策：

| 编号 | 决策主题 | 选择 | 权衡 | ADR 必要性 |
|------|---------|------|------|-----------|
| D1 | {主题} | {选择} | {代价} | 高/中/低 |
| D2 | {主题} | {选择} | {代价} | 高/中/低 |

标记哪些决策需要写 ADR（通常是难以回退的、影响面大的决策）。

## Step 6: 保存产出

将完整的系统设计文档保存到 `{工作目录}/design/system-design-{日期}.md`

## Step 7: 菜单

使用 `AskUserQuestion` 工具向用户展示以下选项（不要用文本菜单让用户输入序号）：

产出摘要：系统上下文 [N] 个外部依赖，[M] 个容器，[K] 个核心组件。关键决策 [D] 项（[H] 项建议写 ADR）。

- **进入架构评审（推荐）** — 基于 ATAM 方法评审质量属性
- **深入某个容器的组件设计** — 如果还有容器需要下钻
- **直接生成 ADR** — 如果决策已经足够明确

**⏸️ 停下来等待用户选择。不要自动执行。**

---

## 质量自检

- C4 至少完成前三层，且严格由上到下逐层推进
- 每个容器标注了职责、技术选型理由、通信方式
- 关键架构决策被识别并标注 ADR 必要性
- 设计文档已保存到 `{工作目录}/design/`

<IMPORTANT>
严格按 C4 Level 1 → 2 → 3 顺序逐层设计，禁止跳过高层直接进入底层实现细节。
每个技术选型必须给出选择理由和权衡代价，禁止"因为大家都用"式的无理由选型。
容器拆分必须对齐业务能力边界，识别出的每个容器需标注职责、技术、通信方式。
本技能完成后，展示菜单并等待用户选择下一步。不要自动执行后续技能。
</IMPORTANT>
