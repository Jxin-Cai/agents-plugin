# 系统设计原则

---

## 1. C4 模型分层设计

| 层级 | 回答的问题 | 受众 | 常见错误 |
|------|-----------|------|---------|
| **L1 系统上下文** | 构建什么？谁用？依赖什么？ | 所有人 | 遗漏外部依赖；暴露内部细节 |
| **L2 容器** | 哪些可独立部署单元？如何通信？ | 开发+运维 | 组件混入容器层；遗漏数据存储 |
| **L3 组件** | 核心容器内部的模块和依赖？ | 开发者 | 依赖方向混乱；未遵循依赖倒置 |
| **L4 代码** | 关键接口的类结构？ | 开发者 | 架构阶段花太多时间在此层 |

**关键原则**：始终由上到下逐层设计，禁止在未明确系统边界（L1）前讨论技术选型（L2）或代码结构（L4）。

## 2. 质量属性驱动设计

| 属性 | 定义 | 常见度量 |
|------|------|---------|
| 性能 | 给定约束下处理请求的速度 | 响应时间、吞吐量、延迟 |
| 可用性 | 正常运行的时间比例 | SLA、MTTR、MTBF |
| 安全性 | 抵抗未授权访问的能力 | 认证机制、加密标准、审计追踪 |
| 可修改性 | 适应变化的成本 | 修改影响范围、部署频率 |
| 可测试性 | 验证系统行为的难易程度 | 测试覆盖率、测试执行时间 |
| 可伸缩性 | 处理负载增长的能力 | 水平/垂直扩展、弹性伸缩 |

质量属性场景六要素：来源 → 刺激 → 环境 → 制品 → 响应 → 度量。

## 3. 架构风格选择

| 风格 | 适合场景 | 核心优势 | 核心风险 |
|------|---------|---------|---------|
| 单体 | 小团队、紧耦合业务、快速启动 | 简单、调试方便、事务一致性 | 规模增长后编译慢、部署风险高 |
| 微服务 | 大团队、清晰域边界、独立交付 | 独立部署、技术异构、故障隔离 | 分布式复杂性、数据一致性、运维成本 |
| 事件驱动 | 异步处理、解耦、事件溯源 | 松耦合、高吞吐、可追溯 | 最终一致性、事件顺序、调试困难 |
| 分层 | 大多数业务应用内部结构 | 职责清晰、依赖方向明确 | 跨层调用、过度抽象 |

## 4. 约束与权衡

| 约束类别 | 示例 |
|----------|------|
| 技术约束 | 已有系统不可替换、必须使用特定数据库、团队技能限制 |
| 业务约束 | 上线时间、预算、合规要求（GDPR、等保） |
| 组织约束 | 团队规模和技能、跨部门协作、运维能力 |
| 基础设施约束 | 云平台限制、网络拓扑、安全策略 |

权衡记录五要素：选项（≥2-3个） → 评估维度（质量属性） → 决策理由 → 代价 → 回退成本。回退成本高的决策应写 ADR。

## 5. 设计健全性检查

| 检查项 | 说明 |
|--------|------|
| 单点故障 | 系统中是否存在任何单点故障？ |
| 10 倍增长 | 流量增长 10 倍，架构能否承受？ |
| 数据一致性 | 跨容器的数据一致性如何保证？ |
| 部署策略 | 如何做到零停机部署？回滚策略是什么？ |
| 可观测性 | 日志、指标、追踪三根支柱是否覆盖？ |
| 安全边界 | 认证、授权、加密是否分层落地？ |
| 成本估算 | 基础设施成本是否在预算内？ |
| 团队可行性 | 团队是否有能力实施和运维这个架构？ |
