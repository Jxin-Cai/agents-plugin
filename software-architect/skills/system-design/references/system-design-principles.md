# 系统设计原则

本文档定义了系统设计阶段必须遵循的架构设计原则。基于 C4 模型、TOGAF、演进式架构等行业最佳实践。

---

## 1. C4 模型分层设计

遵循 Simon Brown 的 C4 模型，每一层回答不同的问题：

### Level 1: 系统上下文（System Context）
- **回答**：我们在构建什么？谁在使用它？它依赖什么外部系统？
- **受众**：所有人（开发者、产品经理、管理层）
- **要求**：一张图能让非技术人员理解系统的定位
- **常见错误**：遗漏了外部系统依赖，或者把内部细节暴露在这一层

### Level 2: 容器（Container）
- **回答**：系统由哪些可独立部署的单元组成？它们之间如何通信？
- **容器定义**：应用程序、数据存储、消息队列、文件系统等——每个是可独立运行/部署的
- **要求**：标注技术选型和通信协议
- **常见错误**：把组件（Component）混入容器层，或者遗漏了数据存储

### Level 3: 组件（Component）
- **回答**：某个容器内部由哪些模块/组件组成？它们的职责和依赖是什么？
- **要求**：只对核心容器进行组件级设计，不需要对所有容器都展开
- **常见错误**：依赖方向混乱，没有遵循依赖倒置原则

### Level 4: 代码（Code）
- **回答**：某个组件内部的类/接口结构是什么？
- **要求**：通常由代码自动生成，架构设计阶段只在关键接口处使用
- **常见错误**：在架构设计阶段花太多时间在这一层

**关键原则**：始终由上到下逐层设计。不要在没有搞清楚系统边界（Level 1）之前就讨论数据库选型（Level 2）或代码结构（Level 4）。

## 2. 质量属性驱动设计

架构决策由质量属性需求驱动，而非功能需求。功能需求决定系统做什么，质量属性决定系统做得有多好。

### 核心质量属性（ATAM 六属性）

| 属性 | 定义 | 常见度量 |
|------|------|---------|
| **性能** | 系统在给定约束下处理请求的速度 | 响应时间、吞吐量、延迟 |
| **可用性** | 系统正常运行的时间比例 | SLA（99.9%）、MTTR、MTBF |
| **安全性** | 抵抗未授权访问的能力 | 认证机制、加密标准、审计追踪 |
| **可修改性** | 系统适应变化的成本 | 修改影响范围、部署频率 |
| **可测试性** | 验证系统行为的难易程度 | 测试覆盖率、测试执行时间 |
| **可伸缩性** | 处理负载增长的能力 | 水平/垂直扩展能力、弹性伸缩 |

### 质量属性场景模板（ATAM）

每个质量属性需求用场景描述：
- **来源（Source）**：谁/什么触发了这个场景
- **刺激（Stimulus）**：发生了什么事件
- **环境（Environment）**：系统当前处于什么状态
- **制品（Artifact）**：系统的哪个部分受影响
- **响应（Response）**：系统应如何反应
- **度量（Response Measure）**：如何判断响应是否合格

**示例**：在正常负载（环境）下，用户（来源）发起搜索请求（刺激），搜索服务（制品）在 200ms 内（度量）返回结果（响应）。

## 3. 架构风格选择

不同业务场景适合不同的架构风格。选择时考虑以下维度：

### 单体架构（Monolith）
- **适合**：小团队、业务逻辑紧密耦合、快速启动
- **优势**：简单、调试方便、事务一致性容易保证
- **风险**：规模增长后编译慢、部署风险高、团队协作瓶颈
- **演进路径**：模块化单体 → 垂直拆分 → 微服务

### 微服务架构（Microservices）
- **适合**：大团队、业务域边界清晰、独立交付需求
- **优势**：独立部署、技术异构、故障隔离
- **风险**：分布式复杂性、数据一致性、运维成本
- **前提**：需要 DDD 限界上下文分析、完善的 DevOps 基础设施

### 事件驱动架构（Event-Driven）
- **适合**：异步处理、解耦生产者和消费者、事件溯源
- **优势**：松耦合、高吞吐、可追溯
- **风险**：最终一致性、事件顺序、调试困难
- **关键考量**：事件契约管理、幂等消费、死信队列

### 分层架构（Layered）
- **适合**：大多数业务应用的内部结构
- **层次**：表现层 → 应用层 → 领域层 → 基础设施层
- **核心规则**：依赖方向向内（外层依赖内层，内层不依赖外层）
- **变体**：六边形架构（Hexagonal）、洋葱架构（Onion）、整洁架构（Clean）

## 4. 约束与权衡分析

### 约束分类

| 类别 | 示例 |
|------|------|
| **技术约束** | 已有系统不能替换、必须使用特定数据库、团队不熟悉某技术 |
| **业务约束** | 上线时间、预算、合规要求（GDPR、等保） |
| **组织约束** | 团队规模和技能、跨部门协作、运维能力 |
| **基础设施约束** | 云平台限制、网络拓扑、安全策略 |

### 权衡记录方法

对每个关键决策，记录：
- **选项**：至少列出 2-3 个备选方案
- **评估维度**：用质量属性作为评估标准
- **决策理由**：为什么选这个，不选那个
- **代价**：选择这个方案要付出什么代价
- **回退成本**：如果这个决策错了，回退的代价有多大

**关键原则**：回退成本高的决策需要更慎重，应写 ADR 记录。

## 5. 设计健全性检查

完成设计后，用以下清单做最后检查：

| 检查项 | 说明 |
|--------|------|
| 单点故障 | 系统中是否存在任何单点故障？ |
| 10 倍增长 | 流量增长 10 倍，架构能否承受？ |
| 数据一致性 | 跨容器的数据一致性如何保证？ |
| 部署策略 | 如何做到零停机部署？回滚策略是什么？ |
| 可观测性 | 日志、指标、追踪三根支柱是否覆盖？ |
| 安全边界 | 认证、授权、加密是否分层落地？ |
| 成本估算 | 基础设施成本是否在预算内？ |
| 团队可行性 | 团队是否有能力实施和运维这个架构？ |
