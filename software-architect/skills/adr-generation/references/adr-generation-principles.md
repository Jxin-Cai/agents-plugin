# ADR 编写原则

---

## 1. ADR 核心理念

- **轻量级**：每个 ADR 1-2 页，不是长篇设计文档
- **不可变**：接受后不修改；决策变更时写新 ADR 标注 "Supersedes ADR-xxx"
- **版本控制**：存放在代码仓库，和代码一起版本管理
- **时间快照**：记录决策时刻的上下文，不是回溯式补文档
- **决策聚焦**：一个 ADR 只记录一个决策

---

## 2. 状态生命周期

| 状态 | 含义 |
|------|------|
| 提议（Proposed） | 决策正在讨论中，尚未最终确定 |
| 接受（Accepted） | 决策已被团队接受并实施 |
| 弃用（Deprecated） | 决策不再适用，未被新决策取代 |
| 被取代（Superseded） | 已被新 ADR 取代，标注取代者编号 |

流转路径：Proposed → Accepted → Deprecated / Superseded by ADR-xxx

**规则**：永远不要删除或修改已接受的 ADR。

---

## 3. 编写规范

**标题**：使用名词短语（"使用 PostgreSQL 作为主数据库"），不用动词（"选择数据库"）。格式 `ADR-NNN: {名词短语}`。

**上下文**：描述当前状况（非理想状况）；明确约束条件；说明紧迫性；引用相关 ADR。

**备选方案**：至少 2-3 个（含"维持现状"）；每个方案有具体优缺点；避免稻草人方案。

**决策理由**："为什么"比"是什么"更重要；明确权衡点；承认不确定性。

**后果**：正面和负面都要记录；要具体（"需要额外配置 Kafka 监控"优于"增加运维复杂度"）；标注后续行动项。

---

## 4. 编号与管理

- 顺序递增：ADR-001、ADR-002...
- 编号一旦分配不再变更（即使弃用）
- 文件名：`adr-{编号}-{主题简写}.md`
- 取代关系：新 ADR 标注 "Supersedes ADR-xxx"，旧 ADR 状态改为 "Superseded by ADR-yyy"
- 依赖关系：上下文中引用 "参见 ADR-xxx"

---

## 5. 什么决策应该写 ADR

| 应该写 ADR | 不需要写 ADR |
|-----------|-------------|
| 影响系统整体结构 | 局部实现细节 |
| 难以回退的技术选择 | 容易更换的工具 |
| 涉及多个团队/模块 | 单模块内部决策 |
| 有显著权衡 | 无争议的显而易见选择 |
| 引入新技术栈 | 使用已有技术 |
| 偏离行业惯例 | 遵循行业最佳实践 |

**经验法则**：值得花 30 分钟讨论的决策，就值得花 15 分钟写 ADR。
