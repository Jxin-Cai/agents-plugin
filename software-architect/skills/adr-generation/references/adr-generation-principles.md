# ADR 编写原则

本文档定义了架构决策记录（ADR）编写必须遵循的原则。基于 Michael Nygard 的原始 ADR 格式、MADR（Markdown ADR）扩展模板和行业最佳实践。

---

## 1. ADR 核心理念

ADR（Architecture Decision Record）由 Michael Nygard 在 2011 年提出，核心理念：

- **轻量级**：每个 ADR 1-2 页，不是长篇大论的设计文档
- **不可变**：ADR 一旦被接受就不再修改；如果决策变了，写新的 ADR 并标注 "Supersedes ADR-xxx"
- **版本控制**：ADR 存放在代码仓库中，和代码一起版本管理
- **时间快照**：ADR 记录的是决策时刻的上下文，不是回溯式补文档
- **决策聚焦**：一个 ADR 只记录一个决策，不要把多个决策塞在一起

### 为什么需要 ADR

- 新成员加入团队时，能快速理解"为什么系统是这样设计的"
- 避免重复讨论已经做过的决策
- 当需要推翻旧决策时，能清楚知道当初的上下文和权衡
- 让架构决策从"口头共识"变成"可追溯的记录"

## 2. ADR 状态生命周期

```
提议（Proposed）→ 接受（Accepted）→ 弃用（Deprecated）
                                    → 被取代（Superseded by ADR-xxx）
```

| 状态 | 含义 |
|------|------|
| **提议（Proposed）** | 决策正在讨论中，尚未最终确定 |
| **接受（Accepted）** | 决策已被团队接受并实施 |
| **弃用（Deprecated）** | 决策不再适用，但没有被新决策取代 |
| **被取代（Superseded）** | 已被新的 ADR 取代，标注取代者编号 |

**规则**：永远不要删除或修改已接受的 ADR。历史记录的价值在于它的不可变性。

## 3. Nygard 经典模板

最简洁的 ADR 模板，适合大多数场景：

```
# ADR-NNN: {标题}

## 状态
{Proposed | Accepted | Deprecated | Superseded by ADR-xxx}

## 上下文
{描述问题背景和决策驱动力。包括技术约束、业务需求、团队状况等。}

## 决策
{我们决定采用什么方案。用主动语态："我们将使用 PostgreSQL 作为主数据库。"}

## 后果
{这个决策带来的正面和负面影响。诚实记录代价。}
```

## 4. MADR 扩展模板

MADR（Markdown Any Decision Record）是 Nygard 模板的扩展，增加了备选方案对比：

```
# ADR-NNN: {标题}

## 状态
{状态}

## 上下文与问题陈述
{用 1-2 句话描述问题}

## 决策驱动力
- {驱动力 1}
- {驱动力 2}

## 备选方案
### 方案 A: {名称}
{描述}
- 优点：...
- 缺点：...

### 方案 B: {名称}
{描述}
- 优点：...
- 缺点：...

## 决策结果
选择方案：{方案名称}，因为 {核心理由}。

### 正面后果
- {后果 1}

### 负面后果
- {后果 1}
```

## 5. ADR 编写规范

### 标题规范
- 使用名词短语，不用动词："使用 PostgreSQL 作为主数据库"，而不是"选择数据库"
- 标题应能让读者不打开 ADR 就大致知道决策内容
- 格式：`ADR-NNN: {决策内容的名词短语}`

### 上下文编写要点
- 描述当前状况，不是理想状况
- 明确列出约束条件（不可改变的因素）
- 说明决策的紧迫性——为什么现在需要做这个决策
- 引用相关的 ADR（如果有前置决策）

### 备选方案要点
- 至少列出 2-3 个方案（包括"维持现状/不做改变"）
- 每个方案都要有具体的优缺点分析
- 避免稻草人方案（故意列一个明显不好的方案来衬托推荐方案）

### 决策理由要点
- 说"为什么"比说"是什么"更重要
- 明确指出决策基于哪些权衡
- 承认不确定性："我们相信...但需要在 X 之后验证"

### 后果编写要点
- 正面和负面后果都要记录
- 后果要具体——"增加运维复杂度"太模糊，"需要额外配置 Kafka 集群监控和告警"更好
- 标注需要后续跟进的行动项

## 6. ADR 编号与管理

### 编号规则
- 顺序递增：ADR-001、ADR-002、ADR-003...
- 编号一旦分配就不再变更（即使 ADR 被弃用）
- 文件名格式：`adr-{编号}-{主题简写}.md`（如 `adr-001-use-postgresql.md`）

### 文件组织
```
adr/
├── adr-001-use-postgresql.md
├── adr-002-event-driven-communication.md
├── adr-003-jwt-authentication.md
└── adr-004-supersede-001-migrate-to-mongodb.md
```

### 关联与引用
- 新 ADR 取代旧 ADR 时：在新 ADR 中标注 "Supersedes ADR-xxx"，在旧 ADR 状态改为 "Superseded by ADR-yyy"
- ADR 之间有依赖时：在上下文中引用 "参见 ADR-xxx"
- ADR 与设计文档的关联：在 ADR 末尾添加"相关文档"链接

---

## 7. 什么决策应该写 ADR

不是所有决策都需要 ADR。以下情况应该写：

| 应该写 ADR | 不需要写 ADR |
|-----------|-------------|
| 影响系统整体结构的决策 | 局部实现细节 |
| 难以回退的技术选择 | 容易更换的工具选择 |
| 涉及多个团队/模块的决策 | 单个模块内部的决策 |
| 有显著权衡的选择 | 没有争议的显而易见的选择 |
| 引入新技术栈 | 使用团队已有技术 |
| 偏离行业惯例的决策 | 遵循行业最佳实践 |

**经验法则**：如果一个决策值得花 30 分钟讨论，那它就值得花 15 分钟写一个 ADR。
