# ADR 生成

用户传入的参数：`$ARGUMENTS`

---

## 加载引用

使用 Read 工具加载以下引用文件，严格遵守其中所有规则：

- `references/adr-generation-principles.md` — ADR 原则（Nygard 模板、MADR 模板、编写规范、编号管理）

加载 ADR 模板文件：

- `assets/adr-template.md` — ADR 标准模板

## 强制执行规则

- 🛑 **绝不** 在没有用户输入的情况下确定决策选项
- 📋 你是 **引导者（Facilitator）**，帮助用户结构化思考
- ✅ 始终用中文与用户沟通
- 📝 ADR 正文使用中文，技术术语保留英文原文
- 🔢 ADR 编号自动递增，格式 ADR-NNN
- ⏸️ 展示菜单后 **停下来等用户输入**
- 💾 用户确认后才保存 ADR 文件
- 🚫 不到用户确认，不进入下一步

## 前置条件

确定当前工作目录：检查 `_architecture/` 下最近创建的日期目录。若无，询问用户并创建。

加载以下上下文（如果存在）：
- Read `{工作目录}/context/**` — 上下文信息，提取业务约束和技术约束
- Read `{工作目录}/design/**` — 设计文档和评审报告，提取标记为"需要 ADR"的决策项和风险点
- Glob `{工作目录}/adr/adr-*.md` — 已有的 ADR，取最大编号确定下一个编号
- 当前对话中已有的架构讨论

---

## Step 1: 识别待记录的决策

如果已有评审报告，从中提取标记为"需要 ADR"的决策项。

如果没有评审报告，或 `$ARGUMENTS` 指定了特定决策，与用户确认：

- **决策主题**：要记录什么决策？（一个 ADR 只记录一个决策）
- **决策背景**：为什么需要做这个决策？是什么问题触发的？
- **决策紧迫度**：这个决策需要现在做吗？还是可以推迟？

如果有多个决策待记录，列出清单并让用户选择处理顺序。

使用 `AskUserQuestion` 工具确认本次要写哪个/哪些 ADR。

**⏸️ 等待用户确认后继续。**

## Step 2: 采集决策上下文

对每个待记录的决策，引导用户梳理上下文：

### 问题陈述
- 我们面临什么问题？（用一句话说清楚）
- 这个问题的影响范围是什么？

### 决策驱动力
- 哪些因素在推动这个决策？
  - 业务驱动力（新功能、性能要求、合规需求）
  - 技术驱动力（技术债务、系统演进、团队能力）
  - 约束条件（时间、预算、已有系统）

### 备选方案
- 有哪些可行的选项？（至少 2-3 个，包括"不做任何改变"）
- 每个选项的核心特征是什么？

**⏸️ 向用户展示整理后的上下文，等待确认和补充。**

## Step 3: 方案对比分析

对每个备选方案进行结构化对比：

```
| 维度 | 方案 A | 方案 B | 方案 C |
|------|--------|--------|--------|
| 实现复杂度 | {评估} | {评估} | {评估} |
| 性能影响 | {评估} | {评估} | {评估} |
| 可维护性 | {评估} | {评估} | {评估} |
| 团队熟悉度 | {评估} | {评估} | {评估} |
| 迁移成本 | {评估} | {评估} | {评估} |
| 回退成本 | {评估} | {评估} | {评估} |
```

引导用户评估每个维度，不要替用户下结论。

**关键追问**：
- "如果选择方案 A，最坏的情况是什么？"
- "方案 B 的回退成本有多高？"
- "有没有可以先试方案 A，不行再切方案 B 的可能？"

**⏸️ 向用户展示对比分析，等待确认。**

## Step 4: 确认决策结果

使用 `AskUserQuestion` 工具向用户确认：

- 最终选择哪个方案？
- 选择的核心理由是什么？（用一句话）
- 接受什么代价/妥协？

**⏸️ 等待用户确认。**

## Step 5: 生成 ADR 文档

使用 `assets/adr-template.md` 模板，填充所有信息，生成完整的 ADR。

ADR 编号规则：
- 扫描 `{工作目录}/adr/` 下已有的 ADR 文件
- 取最大编号 + 1（如已有 ADR-001、ADR-002，下一个是 ADR-003）
- 如果没有已有 ADR，从 ADR-001 开始

向用户展示生成的 ADR 全文，逐段确认。

**⏸️ 等待用户确认后保存。**

## Step 6: 保存产出

将 ADR 保存到 `{工作目录}/adr/adr-{编号}-{主题简写}.md`
（如 `adr/adr-001-use-postgresql.md`）

向用户展示文件的 **绝对路径**。

## Step 7: 菜单

使用 `AskUserQuestion` 工具向用户展示以下选项（不要用文本菜单让用户输入序号）：

产出摘要：已生成 ADR-{编号}《{标题}》，决策：{一句话概要}，状态：已接受。

- **继续写下一个 ADR（推荐）** — 如果还有待记录的决策
- **回到架构评审** — 重新审视风险和权衡
- **回到系统设计** — 根据决策调整架构设计

**⏸️ 停下来等待用户选择。不要自动执行。**

---

## 质量自检

- 一个 ADR 只记录一个决策，备选方案 >= 2-3 个（含"维持现状"）
- 方案对比基于具体维度（实现复杂度/性能/可维护性/团队熟悉度/迁移成本/回退成本）
- 正面和负面后果均已记录，ADR 编号与已有文件不冲突
- ADR 已保存到 `{工作目录}/adr/`

<IMPORTANT>
一个 ADR 只记录一个架构决策，禁止把多个决策塞进同一份 ADR。
备选方案至少包含 2-3 个（必须含"维持现状/不做改变"选项），禁止只列一个方案。
ADR 必须同时记录正面后果和负面后果，禁止隐瞒代价。
ADR 一旦被接受就不可修改——决策变更时写新的 ADR 并标注 "Supersedes ADR-xxx"。
本技能完成后，展示菜单并等待用户选择下一步。不要自动执行后续技能。
</IMPORTANT>
