# 架构评审原则

本文档定义了架构评审阶段必须遵循的评审原则。基于 ATAM（Architecture Tradeoff Analysis Method）、AWS Well-Architected Framework 等行业最佳实践。

---

## 1. ATAM 评审方法论

ATAM 由 SEI（Carnegie Mellon 软件工程研究所）提出，是业界公认的架构评审方法。其核心思想：架构评审的目标不是判好坏，而是识别风险和权衡。

### 评审四阶段

| 阶段 | 活动 | 产出 |
|------|------|------|
| **呈现** | 介绍评审方法、业务驱动力、架构概览 | 共识对齐 |
| **调查分析** | 识别架构方案、构建效用树、分析关键场景 | 风险、敏感点 |
| **测试** | 头脑风暴场景、优先级排序、重新分析 | 权衡点 |
| **报告** | 汇总发现、分类输出、建议行动 | 评审报告 |

### 四类评审产出

- **风险（Risks）**：可能导致质量属性不达标的架构决策
- **非风险（Non-risks）**：已被验证安全的架构决策（同样重要——确认"这个没问题"）
- **敏感点（Sensitivity Points）**：对某个质量属性有重大影响的架构参数（如缓存 TTL 对性能的影响）
- **权衡点（Tradeoff Points）**：同时影响多个质量属性的决策（如加密强度影响安全性和性能）

## 2. 质量属性效用树

效用树是 ATAM 的核心工具，将抽象的质量需求转化为可评估的具体场景。

### 构建方法

```
系统质量（根节点）
├── 质量属性 A（如性能）
│   ├── [重要性, 风险] 场景 A1（如：搜索响应 < 200ms）
│   └── [重要性, 风险] 场景 A2（如：批量处理 < 30s）
├── 质量属性 B（如可用性）
│   ├── [重要性, 风险] 场景 B1
│   └── [重要性, 风险] 场景 B2
```

### 标注规则

每个场景标注两个维度：
- **重要性**：对业务的重要程度（H/M/L）
- **风险**：当前架构不满足此场景的概率（H/M/L）

### 优先级矩阵

| | 高风险 | 中风险 | 低风险 |
|---|---|---|---|
| **高重要性** | 🔴 最优先分析 | 🟡 重点关注 | 🟢 确认即可 |
| **中重要性** | 🟡 需要分析 | 🟢 关注 | ⚪ 记录 |
| **低重要性** | 🟢 评估 | ⚪ 记录 | ⚪ 跳过 |

## 3. 架构评审检查清单

### 结构完整性

- [ ] 系统边界是否清晰定义？
- [ ] 各模块/服务的职责是否单一？
- [ ] 模块间依赖方向是否合理（向内依赖）？
- [ ] 是否存在循环依赖？
- [ ] 接口契约是否明确？

### 运行时质量

- [ ] 关键路径的性能瓶颈在哪里？
- [ ] 单点故障如何处理？
- [ ] 负载增长 10 倍时的瓶颈在哪里？
- [ ] 异常和错误如何传播？是否有熔断/降级？
- [ ] 并发冲突如何处理？

### 数据架构

- [ ] 数据一致性模型是什么？（强一致/最终一致）
- [ ] 数据分区/分片策略是否可扩展？
- [ ] 数据备份和恢复策略是否充分？
- [ ] 数据生命周期管理（归档、清理）是否考虑？
- [ ] 敏感数据的加密和访问控制是否到位？

### 部署与运维

- [ ] 部署策略是什么？（蓝绿/金丝雀/滚动）
- [ ] 回滚机制是否可靠？
- [ ] 可观测性三支柱（日志/指标/追踪）是否覆盖？
- [ ] 告警策略和值班流程是否清晰？
- [ ] 配置管理是否外部化？

### 安全

- [ ] 认证方式是什么？（OAuth2/JWT/Session）
- [ ] 授权模型是什么？（RBAC/ABAC）
- [ ] API 安全（限流、防重放、输入校验）？
- [ ] 密钥和凭证如何管理？
- [ ] 安全事件如何审计？

## 4. AWS Well-Architected 六大支柱

作为 ATAM 的补充，使用 AWS Well-Architected Framework 的六大支柱做全面检查：

### 卓越运营（Operational Excellence）
- 组织如何支持业务目标？
- 工作负载如何设计、交付和运营？
- 如何持续改进流程和程序？
- **关键实践**：基础设施即代码、小批量变更、预演故障、从故障中学习

### 安全性（Security）
- 如何保护信息、系统和资产？
- **关键实践**：最小权限、深度防御、安全自动化、数据分类保护

### 可靠性（Reliability）
- 工作负载如何正确一致地执行预期功能？
- **关键实践**：自动恢复、水平扩展、容量规划、变更管理

### 性能效率（Performance Efficiency）
- 如何高效使用计算资源满足需求？
- **关键实践**：选择合适的资源类型、监控性能、权衡考量

### 成本优化（Cost Optimization）
- 如何以最低成本交付业务价值？
- **关键实践**：支出意识、按需使用、规模经济、资源合理化

### 可持续性（Sustainability）
- 如何最小化环境影响？
- **关键实践**：最大化利用率、高效编码、数据管理优化

## 5. 评审反模式

在评审过程中，警惕以下反模式：

| 反模式 | 描述 | 纠正方式 |
|--------|------|---------|
| **PPT 架构** | 架构图很漂亮但脱离实际代码 | 对照代码验证架构图的准确性 |
| **银弹思维** | 认为某个技术能解决所有问题 | 追问"这个技术在什么场景下不适用？" |
| **过度设计** | 为假想的未来需求引入复杂性 | 问"现在有具体的业务场景需要这个吗？" |
| **简历驱动** | 因为想学新技术而引入 | 问"团队有能力运维这个技术吗？" |
| **复制粘贴架构** | 照搬其他项目的架构 | 问"你的业务约束和那个项目一样吗？" |
| **忽略运维** | 只关注开发视角 | 问"凌晨三点系统挂了怎么办？" |
