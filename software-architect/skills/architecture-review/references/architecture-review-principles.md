# 架构评审原则

---

## 1. ATAM 评审方法论

| 阶段 | 活动 | 产出 |
|------|------|------|
| 呈现 | 介绍评审方法、业务驱动力、架构概览 | 共识对齐 |
| 调查分析 | 识别架构方案、构建效用树、分析关键场景 | 风险、敏感点 |
| 测试 | 头脑风暴场景、优先级排序、重新分析 | 权衡点 |
| 报告 | 汇总发现、分类输出、建议行动 | 评审报告 |

四类评审产出：
- **风险**：可能导致质量属性不达标的架构决策
- **非风险**：已被验证安全的架构决策（确认"这个没问题"同样重要）
- **敏感点**：对某个质量属性有重大影响的架构参数（如缓存 TTL 对性能的影响）
- **权衡点**：同时影响多个质量属性的决策（如加密强度影响安全性和性能）

---

## 2. 效用树标注规则

每个质量属性场景标注 `[重要性, 风险]`（H/M/L）：

| | 高风险 | 中风险 | 低风险 |
|---|---|---|---|
| **高重要性** | 最优先分析 | 重点关注 | 确认即可 |
| **中重要性** | 需要分析 | 关注 | 记录 |
| **低重要性** | 评估 | 记录 | 跳过 |

---

## 3. 评审检查清单

**结构完整性**：系统边界是否清晰？模块职责是否单一？依赖方向是否合理（向内）？是否存在循环依赖？接口契约是否明确？

**运行时质量**：关键路径性能瓶颈？单点故障处理？10 倍负载瓶颈？异常传播与熔断/降级？并发冲突处理？

**数据架构**：一致性模型（强一致/最终一致）？分区/分片可扩展性？备份恢复策略？数据生命周期管理？敏感数据加密与访问控制？

**部署与运维**：部署策略（蓝绿/金丝雀/滚动）？回滚可靠性？可观测性三支柱（日志/指标/追踪）？告警与值班流程？配置外部化？

**安全**：认证方式（OAuth2/JWT/Session）？授权模型（RBAC/ABAC）？API 安全（限流/防重放/输入校验）？密钥管理？安全审计？

---

## 4. AWS Well-Architected 六大支柱

| 支柱 | 关键实践 |
|------|---------|
| 卓越运营 | 基础设施即代码、小批量变更、预演故障、从故障中学习 |
| 安全性 | 最小权限、深度防御、安全自动化、数据分类保护 |
| 可靠性 | 自动恢复、水平扩展、容量规划、变更管理 |
| 性能效率 | 选择合适资源类型、监控性能、权衡考量 |
| 成本优化 | 支出意识、按需使用、规模经济、资源合理化 |
| 可持续性 | 最大化利用率、高效编码、数据管理优化 |

## 5. 评审反模式

| 反模式 | 纠正追问 |
|--------|---------|
| PPT 架构（脱离实际代码） | "对照代码验证架构图准确性" |
| 银弹思维（某技术解决一切） | "这个技术在什么场景下不适用？" |
| 过度设计（假想未来需求） | "现在有具体业务场景需要这个吗？" |
| 简历驱动（想学新技术而引入） | "团队有能力运维这个技术吗？" |
| 复制粘贴架构（照搬他人） | "你的业务约束和那个项目一样吗？" |
| 忽略运维（只关注开发） | "凌晨三点系统挂了怎么办？" |
