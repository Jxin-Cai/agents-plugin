# Story 分解原则

本文档定义了从 PRD 到 Epic/User Story 的分解标准。

---

## 1. INVEST 原则

每个 User Story 必须满足 INVEST 标准：

| 原则 | 含义 | 检验方法 |
|------|------|---------|
| **I**ndependent | 可独立开发、测试、部署 | 删掉这个 Story，其他 Story 还能工作吗？ |
| **N**egotiable | 描述能力而非实现方式 | 能用 3 种以上技术方案实现吗？ |
| **V**aluable | 用户可感知的价值 | 用户能说出"这对我有什么用"吗？ |
| **E**stimable | 团队可估算工作量 | 开发者读完能给出 Story Points 吗？ |
| **S**mall | 1 个 Sprint 内可完成 | 预计 1-3 天（含测试）能做完吗？ |
| **T**estable | 验收标准可测试 | QA 能写出测试用例吗？ |

**反模式：**
- "技术 Story"：如"搭建数据库"、"实现缓存层"——违反 Valuable
- "史诗 Story"：如"用户管理系统"——违反 Small
- "模糊 Story"：如"优化用户体验"——违反 Testable

---

## 2. 垂直切片

### 原则

每个 Story 穿透所有技术层（前端 → 后端 → 数据库），交付一个完整的用户能力。

**好的切片（垂直）：**
```
Story: 用户可以用邮箱注册
├── 前端：注册表单
├── 后端：验证 + 存储
└── 数据库：用户表
→ 用户可以真正注册！
```

**坏的切片（水平）：**
```
Story 1: 创建用户表（数据库层）
Story 2: 实现注册 API（后端层）
Story 3: 开发注册页面（前端层）
→ Story 1 和 2 完成后用户什么都做不了
```

### 复杂功能的切片策略

| 场景 | 切片方式 |
|------|---------|
| 多角色功能（管理员+用户） | 按角色切——"管理员可以创建"、"用户可以查看" |
| 多步骤流程（申请→审批→执行） | 按步骤切——每步是一个 Story |
| CRUD 功能 | 先 C+R（最小可用），再 U+D |
| 批量操作 | 先单个操作 Story，再批量 Story |
| 正向+异常路径 | 先 Happy Path Story，再异常处理 Story |

## 3. 验收标准写作

### Given/When/Then 格式

```
Given [前置条件/上下文],
When [用户执行的操作],
Then [系统的预期行为/结果]
```

### 从 PRD 七列表格推导

| PRD 列 | → AC 模板 |
|--------|----------|
| 正向路径 | Given 用户满足前置条件, When 执行操作, Then 得到预期结果 |
| 异常路径 | Given 异常条件发生, When 执行操作, Then 系统显示错误并提供恢复方式 |
| 逆向路径 | Given 用户已完成操作, When 执行撤销, Then 状态回退到操作前 |
| 边界条件 | Given 输入达到边界值, When 执行操作, Then 系统按边界规则处理 |

### AC 质量标准

- 每条 AC 必须可判断"通过/不通过"
- 不使用模糊词："正确地"、"合理地"、"及时地"
- 量化所有指标："3 秒内响应"而非"快速响应"
- P0 Story 至少 3 条 AC（1 正向 + 1 异常 + 1 边界/逆向）

### 示例

PRD 行：
```
| F3 | 管理员可以批量导入用户 | 上传 CSV，系统解析并创建用户 | 格式错误时显示错误行号，已成功的不回滚 | 导入后 30 分钟内可批量撤销 | CSV 格式，单次上限 10000 行 | P0 |
```

推导的 AC：
```
- AC1: Given 管理员上传一个格式正确的 CSV（≤10000 行）, When 点击导入, Then 所有用户被创建并显示成功数量
- AC2: Given CSV 中第 5 行格式错误, When 导入, Then 系统跳过错误行，导入其余行，并报告错误行号和原因
- AC3: Given 管理员在导入后 20 分钟内, When 点击批量撤销, Then 本批次导入的所有用户被删除
- AC4: Given CSV 超过 10000 行, When 上传, Then 系统拒绝并提示行数限制
```

## 4. Story 粒度判断

### 太大的信号
- 无法在 1 个 Sprint 内完成
- 包含多个不同的用户角色
- 验收标准超过 8 条
- 团队无法估算 Story Points

### 太小的信号
- 只改了一个按钮文案
- 开发时间 < 2 小时
- 无法独立交付用户价值

### 适中的信号
- 1-3 天可完成（含测试）
- 3-5 条验收标准
- 一个角色的一个完整能力
- 团队能自信地估算

## 5. Epic 组织

### Epic 命名

```
[能力领域] — [用户价值一句话]
```

示例：
- 用户认证 — 用户可以安全地注册和登录
- 内容管理 — 管理员可以发布和管理内容
- 数据导出 — 用户可以导出自己的数据

### Epic 与 PRD 模块的关系

- 通常 1:1 映射（PRD 功能模块 = Epic）
- 如果 PRD 模块太大（>10 个功能点），可拆分为多个 Epic
- 如果 PRD 模块太小（1-2 个功能点），可合并到相关 Epic
