# 上线复盘原则

本文档定义了产品上线后复盘的标准和方法。

---

## 1. 无责复盘

### 核心原则

- **聚焦系统，不聚焦个人**：问"什么环节出了问题"而不是"谁出了问题"
- **学习导向**：目标是提取可复用的经验，不是分配责任
- **事实为基**：用数据说话，不凭感觉总结

### 语言规范

| 避免的表达 | 使用的表达 |
|-----------|-----------|
| "XX 没有做好" | "XX 环节的结果未达预期" |
| "谁的责任" | "哪个环节可以改进" |
| "失败了" | "结果与预期有偏差，原因是" |
| "早就说过" | "下次可以在更早阶段关注" |

---

## 2. 对比评估框架

### 功能交付评估

对每个 PRD 功能点进行三分类：

| 状态 | 定义 |
|------|------|
| ✅ 已交付 | 按 PRD 描述完整交付 |
| ⚠️ 有改动 | 交付了但与 PRD 有差异（需要记录差异原因） |
| ❌ 未交付 | 因各种原因未交付（需要记录原因和后续计划） |

差异原因分类：
- 技术限制（PRD 要求超出技术能力）
- 时间约束（来不及做）
- 需求偏差（做的过程中发现 PRD 理解有误）
- 用户反馈（开发过程中收到新反馈调整了方向）
- 范围裁剪（主动降低范围以保证交付）

### 指标达标评估

对每个成功指标做对照：
- 目标值 vs 实际值
- 达标则分析原因（是否可复制）
- 不达标则分析差距原因

---

## 3. 决策质量审计

### 审计维度

对每个记录在案的产品决策，评估：

1. **信息充分性**：做决策时掌握的信息是否足够？
2. **替代方案评估**：是否充分评估了替代方案？
3. **结果符合预期**：决策带来的结果与预期是否一致？
4. **可改进点**：如果重来，有什么可以做得更好？

### 审计结论分类

| 结论 | 处理 |
|------|------|
| 正确决策 | 记录为正面经验——"在 [条件] 下，选择 [方案] 是正确的" |
| 可改进决策 | 标记经验教训——"下次遇到 [类似条件]，应该 [改进方向]" |
| 中性 | 记录——"结果与决策无强关联，受外部因素影响" |

---

## 4. 模式提取

### 什么值得抽象为模式

- 这种类型的功能之前做过或将来可能再做
- 有明确的功能点结构可以复用
- 有踩过的坑值得记录

### 模式质量标准

好的模式包含：
1. **模式名称**：简洁的通用名称
2. **适用场景**：什么时候使用这个模式
3. **核心功能点**：通常包含哪些功能
4. **常见陷阱**：之前踩过的坑
5. **参考案例**：指向本次需求周期

### 不要过度抽象

- 只做过一次的功能通常不需要抽象为模式
- 模式应该是"大概率会再遇到"的功能类型
- 如果不确定，可以先不抽象，等第二次遇到时再沉淀

---

## 5. 复盘节奏

### 推荐时机

- 功能上线后 2-4 周（等数据稳定）
- 不超过上线后 2 个月（记忆还新鲜）

### 参与者建议

- 产品经理（必须）
- 技术负责人（建议）
- 设计师（如有重大 UX 变更）
