# PRD 写作规范

## 信息密度

- 每句话删掉后如果不影响理解，说明是废话
- 形容词必须可量化，否则删除。禁止"直观""易用""友好""灵活""强大"
- FR 回答"做什么(WHAT)"不是"怎么做(HOW)"
- 格式：`[角色] 可以 [能力] [约束/边界]`

反模式：主观形容词、实现泄露、模糊量词、缺失测试标准。

## 七列功能清单

```markdown
| # | 功能点 | 正向路径 | 异常路径 | 逆向路径 | 边界条件 | 优先级 |
```

- 每列 1-2 句话，不写实现细节
- P0 功能的异常和逆向路径不能留空
- 按用户能力领域分模块（✅ 用户管理，❌ 认证系统），目标 5-8 个

## 可追溯性

```text
核心价值 → 成功标准 → 功能模块 → 功能点 → 验收标准
```

## 章节顺序

1. 概述（目标用户、核心价值、成功标准）
2. 功能清单
3. 全局约束（边界 + 非功能 + 治理/合规）
4. 验收标准摘要
5. 补充分析摘要（只写已选维度）
6. 开放问题
7. 后续 PM 工作

## 非功能约束写法

模板：`系统应 [指标] [条件] [度量方式]`  
只写与当前需求相关的，不堆砌通用模板。

## 验收标准

从七列表格推导：正向→核心验收、异常→失败验收、逆向→回退验收、边界→边界值验收。

- PRD 中用摘要格式，Given/When/Then 留到 Story 分解
- P0 至少 2 条 AC，P1/P2 至少 1 条
- AC 必须可判断通过/不通过

## 质量自检

### 完整性
- [ ] 所有角色都有对应功能点
- [ ] P0 异常/逆向/边界无空白
- [ ] 已选治理/NFR 已纳入

### 密度
- [ ] 无废话、无主观形容词、无实现泄露

### 追溯
- [ ] 功能点可追溯到核心价值
- [ ] 编号连续唯一
- [ ] 已选维度与正文摘要一致

### MECE
- [ ] 功能点无重叠、无遗漏

## Spec Quality Gate

PRD 保存前必须生成独立的规格质量门结论。质量门不是润色检查，而是判断规格能否进入 Story 切片和发布准备。

### Gate 维度

| 维度 | 通过标准 | 失败信号 |
|------|----------|----------|
| 完整性 | 目标用户、核心价值、P0 功能三链路、边界条件完整 | P0 异常/逆向/边界为空，角色无功能点 |
| 可测性 | 每个关键功能都有可判断通过/不通过的验收摘要 | 使用“友好、合理、快速”等不可测表述 |
| 一致性 | 术语、NFR、治理、指标与已选维度一致 | 同一概念多种叫法，治理/NFR 摘要遗漏 |
| 可追溯性 | 核心价值 → 功能点 → 验收摘要可追溯 | 功能点找不到价值来源或编号断裂 |
| 风险透明度 | 开放问题被列出并标注影响范围 | 关键决策缺失但没有开放问题 |

### 判定规则

- 所有维度通过 → `quality_gate.status: passed`，PRD `status` 可进入 `approved`
- 任一维度失败 → `quality_gate.status: failed`，PRD 保持 `draft`
- 失败项必须写出修复建议，并停下来让用户选择：修订 PRD / 保留草稿 / 取消保存
