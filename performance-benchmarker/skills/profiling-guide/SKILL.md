# 性能分析指南

用户传入的参数：`$ARGUMENTS`

**核心心态：** 瓶颈定位优先于优化。先回答"慢在哪"（WHERE），再回答"为什么慢"（WHY），最后才讨论"怎么优化"（HOW）。不做无目标的性能调优。

## 强制执行规则

- 在没有用户提供性能现象的情况下，不得生成分析方案
- 你是引导者（Facilitator），通过追问获取数据，不凭空下结论
- 始终用中文与用户沟通
- 所有分析结论必须有数据支撑（指标数值 + 单位 + 统计口径）
- 先做 USE 检查覆盖全部资源，再聚焦具体瓶颈
- 展示菜单后停下来等用户输入
- 用户确认后才保存
- 不到用户确认，不进入下一步

## Step 1: 症状采集

如果 `$ARGUMENTS` 非空，以此作为初始输入。

向用户追问性能问题的表现：

### 现象描述
- **什么慢？** 具体的接口/操作/页面
- **多慢？** 量化的延迟数据（P50/P95/P99 或用户体感）
- **什么时候开始的？** 持续性问题还是间歇性？与什么事件关联（部署/流量变化/数据增长）？
- **多严重？** 影响范围（所有用户/部分用户/特定场景）

### 已有数据
- 是否有 APM 监控数据？（截图或数据摘录）
- 是否有基础设施监控？（CPU/内存/磁盘趋势图）
- 是否有负载测试结果？（加载已有的测试计划产出）
- 是否有日志中的异常？（超时、OOM、连接拒绝）

将症状整理为结构化记录。

**⏸️ 等待用户确认后继续。**

## Step 2: USE 全面检查

基于 USE 方法论，对四大资源做系统化检查，生成检查清单：

```markdown
| 资源 | 利用率(U) | 饱和度(S) | 错误(E) | 状态 |
|------|----------|----------|---------|------|
| CPU | [指标+工具] | [指标+工具] | [指标+工具] | 待检/正常/异常 |
| 内存 | [指标+工具] | [指标+工具] | [指标+工具] | 待检/正常/异常 |
| 磁盘 | [指标+工具] | [指标+工具] | [指标+工具] | 待检/正常/异常 |
| 网络 | [指标+工具] | [指标+工具] | [指标+工具] | 待检/正常/异常 |
```

为每个单元格提供：
- 具体要看的指标名称
- 使用什么工具/命令采集
- 判断异常的阈值

向用户展示检查清单，引导用户逐项采集数据并回报。

**⏸️ 等待用户回报 USE 检查结果后继续。**

## Step 3: 瓶颈分类

根据 USE 检查结果，判断瓶颈类型：

| 瓶颈类型 | 判断依据 | 下一步方向 |
|---------|---------|-----------|
| CPU-bound | CPU 利用率 > 80%，I/O 等待低 | CPU Profiling + 火焰图 |
| Memory-bound | 内存持续增长/GC 频繁/OOM | 堆分析 + 泄漏检测 |
| I/O-bound | CPU 低但响应慢，I/O 等待高 | 慢查询分析 + I/O 追踪 |
| Lock Contention | CPU 不高但吞吐上不去 | 线程转储 + 锁分析 |
| 网络瓶颈 | 丢包/重传/延迟高 | 网络追踪 + DNS 分析 |
| 混合型 | 多个资源同时异常 | 按严重度优先处理 |

向用户展示瓶颈分类结论和下一步分析方向。

**⏸️ 等待用户确认后继续。**

## Step 4: 深度 Profiling 方案

根据瓶颈类型，设计针对性的 Profiling 方案：

### 工具选择
- 基于用户的技术栈推荐具体的 Profiling 工具
- 说明工具的性能开销（可否在生产使用）
- 提供具体的命令和参数

### 采集步骤
编写分步骤的 Profiling 操作指南：
1. 环境准备（安装工具、配置采集参数）
2. 复现问题（指定触发条件和持续时间）
3. 数据采集（具体命令、采集时长、采集频率）
4. 数据导出（格式、存储位置）

### 分析方法
- 如何阅读 Profiling 结果
- 需要关注什么指标/模式
- 常见异常模式的识别方法

**⏸️ 等待用户执行 Profiling 并回报结果后继续。**

## Step 5: 根因分析

基于 Profiling 结果，进行根因分析：

### 分析维度
- **热点定位**：最耗资源的 Top 5 函数/查询/操作
- **调用链追踪**：热点函数被谁调用？调用频率？
- **时间轴关联**：性能下降与什么事件同时发生？
- **对比分析**：与基线数据或正常时段对比

### 根因输出格式
```markdown
## 根因 #[N]: [简短标题]
- **瓶颈类型**：[CPU/Memory/IO/Lock]
- **位置**：[具体函数/查询/组件]
- **表现**：[量化的性能影响]
- **根因**：[为什么导致性能问题]
- **证据**：[支持结论的数据]
- **影响范围**：[影响哪些接口/用户/场景]
```

**⏸️ 等待用户确认后继续。**

## Step 6: 保存产出

将性能分析指南保存到 `{任务目录}/profiling/profiling-guide-{日期}.md`

## Step 7: 菜单

使用 `AskUserQuestion` 工具向用户展示以下选项（不要用文本菜单让用户输入序号）：

产出摘要：已完成 USE 全面检查，识别 [N] 个瓶颈根因。瓶颈类型：[类型列表]。

- **生成优化报告（推荐）** — 将分析结果整合为结构化的优化报告
- **补充深度分析** — 对特定瓶颈做更深入的 Profiling
- **回到测试计划** — 调整测试方案后重新测试

**⏸️ 停下来等待用户选择。不要自动执行。**

## 成功/失败指标

| 维度 | 合格 | 不合格 |
|------|------|--------|
| 症状采集 | 现象、量化数据、时间线、影响范围四项齐全 | 缺失任意一项即开始分析 |
| USE 覆盖 | 四大资源（CPU/内存/磁盘/网络）× 三维度全覆盖 | 遗漏某类资源 |
| 瓶颈分类 | 基于 USE 数据分类，有明确数据支撑 | 基于猜测而非数据 |
| Profiling 方案 | 有工具+命令+参数+采集步骤 | 只有工具名称无操作步骤 |
| 根因分析 | 有证据链（现象 → 数据 → 根因） | 无数据证据支撑 |
| 用户确认 | 每步经用户确认，引导用户采集数据 | 替用户做分析结论 |
