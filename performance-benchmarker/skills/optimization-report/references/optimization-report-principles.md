# 优化报告原则

本文档定义了性能优化报告阶段必须遵循的原则。基于 Google SRE 方法论、行业性能报告规范和 SLO 驱动的优化策略。

---

## 1. 报告结构标准

### 面向双受众设计
性能优化报告同时服务两类读者：

**技术受众（开发/SRE/架构师）**：
- 需要精确的性能数据和根因分析
- 关注具体的优化方案和实施步骤
- 用技术指标衡量优化效果

**管理受众（技术经理/CTO/产品负责人）**：
- 需要业务影响和风险评估
- 关注 SLO 达标状态和成本影响
- 用业务指标衡量投入产出比

### 信息密度标准
- 每个数据点必须标注单位和统计口径
- 使用表格而非长段落展示对比数据
- 图表说明必须包含：指标名称、时间范围、采样频率
- 避免"性能有所提升"——必须写"P99 延迟从 850ms 降至 120ms，改善 85.9%"

## 2. SLO 达标评估框架

### 评估维度

| 维度 | 评估内容 | 展示方式 |
|------|---------|---------|
| 达标率 | 各 SLO 指标当前值 vs 目标值 | 对比表格 |
| 错误预算 | 剩余错误预算百分比 | 消耗趋势 |
| 趋势 | 近 7/30/90 天的趋势变化 | 趋势方向 |
| 风险 | 接近阈值的 SLO 指标 | 红黄绿状态 |

### 达标状态定义

| 状态 | 条件 | 行动 |
|------|------|------|
| 健康（绿） | SLI > SLO 且错误预算 > 50% | 正常迭代 |
| 警告（黄） | SLI > SLO 但错误预算 < 30% | 增加可靠性投入 |
| 违约（红） | SLI < SLO 或错误预算耗尽 | 冻结功能开发，专注修复 |

### 错误预算计算
```
错误预算 = 1 - SLO 目标
已消耗预算 = 实际不可用时间 / 允许不可用时间
剩余预算 = 1 - 已消耗预算
```

示例：SLO = 99.9%，月度错误预算 = 0.1% = 43.2 分钟
本月已发生 20 分钟不可用 → 已消耗 46.3% → 剩余 53.7%

## 3. 优化方案评估矩阵

### 四象限分析

按「收益」和「成本」两个维度将优化项分为四类：

| | 低成本 | 高成本 |
|------|---------|---------|
| **高收益** | Quick Win（立即做） | 战略投资（评估后做） |
| **低收益** | 顺手改（低优先级） | 不做（ROI 不合理） |

### 优化项评估模板

每个优化建议必须包含：

```markdown
## 优化项 #[N]: [标题]

### 问题
- **根因**：[来自 Profiling 阶段的根因分析]
- **影响**：[量化的性能影响——延迟增加 X ms / 吞吐下降 Y%]
- **影响范围**：[受影响的接口/用户/场景]

### 方案
- **优化策略**：[具体的技术方案]
- **预期收益**：[量化的预期改善——P99 预计从 X 降至 Y]
- **实施成本**：[人天估算 + 风险评估]
- **验证方式**：[如何验证优化效果]

### 分类
- **象限**：Quick Win / 战略投资 / 顺手改 / 不做
- **优先级**：P0 / P1 / P2
- **依赖**：[前置条件或与其他优化项的依赖关系]
```

## 4. 性能基线对比

### 对比维度

| 指标类别 | 基线值 | 当前值 | 变化 | SLO 目标 | 状态 |
|---------|--------|--------|------|---------|------|
| P50 延迟 | [X]ms | [Y]ms | [+/-Z%] | [T]ms | ✅/❌ |
| P95 延迟 | [X]ms | [Y]ms | [+/-Z%] | [T]ms | ✅/❌ |
| P99 延迟 | [X]ms | [Y]ms | [+/-Z%] | [T]ms | ✅/❌ |
| 吞吐量 | [X]RPS | [Y]RPS | [+/-Z%] | [T]RPS | ✅/❌ |
| 错误率 | [X]% | [Y]% | [+/-Z%] | [T]% | ✅/❌ |
| CPU 利用率 | [X]% | [Y]% | [+/-Z%] | <[T]% | ✅/❌ |
| 内存利用率 | [X]% | [Y]% | [+/-Z%] | <[T]% | ✅/❌ |

### 对比原则
- 基线和当前值必须在相同条件下测得（相同负载、相同环境）
- 标注测试条件：并发数、持续时间、数据量级
- 使用百分位而非均值做延迟对比
- 相对变化和绝对变化都要展示

## 5. 容量规划建议

### 容量模型
- 当前系统容量上限（从 Stress 测试获得）
- 业务增长预测（月增长率 / 季度增长率）
- 容量耗尽时间线（按增长率推算）
- 扩容触发阈值（利用率达到 X% 时触发扩容）

### 扩容策略
| 策略 | 适用场景 | 成本模型 |
|------|---------|---------|
| 垂直扩展 | 单节点瓶颈、数据库 | 阶梯成本 |
| 水平扩展 | 无状态服务 | 线性成本 |
| 弹性伸缩 | 流量波动大 | 按需成本 |
| 缓存优化 | 读多写少 | 固定成本 |
| 架构重构 | 根本性瓶颈 | 高前期投入 |

## 6. 报告质量自检清单

### 数据完整性
- [ ] 所有性能数据标注了单位和统计口径？
- [ ] 基线对比在相同条件下进行？
- [ ] SLO 达标评估覆盖所有已定义的 SLO？
- [ ] 每个瓶颈都有根因分析的数据证据？

### 方案可操作性
- [ ] 每个优化项有具体的技术方案（不只是"优化 X"）？
- [ ] 每个优化项有预期收益的量化估算？
- [ ] 每个优化项有实施成本和风险评估？
- [ ] 优化项按四象限分类并排了优先级？

### 可追溯性
- [ ] 优化建议可追溯到具体的瓶颈根因？
- [ ] 根因可追溯到 Profiling 数据？
- [ ] SLO 目标可追溯到负载测试计划？

### 表达质量
- [ ] 没有模糊量词（"很多"、"较快"、"明显提升"）？
- [ ] 没有缺少数据支撑的结论？
- [ ] 表格代替了可以表格化的段落？
