# 负载测试计划原则

本文档定义了负载测试计划阶段必须遵循的原则。基于行业最佳实践（Google SRE、Brendan Gregg 方法论、ISTQB 性能测试指南）。

---

## 1. 五阶段递进测试模型

负载测试按五个阶段递进执行，每阶段有独立的验证目标：

### Baseline（基线测试）
- **目的**：建立系统在正常负载下的性能基线
- **负载**：日常平均并发的 50%-100%
- **关注**：P50/P95/P99 延迟、吞吐量、资源利用率
- **产出**：基线报告，作为后续测试的对比基准

### Load（负载测试）
- **目的**：验证系统在预期峰值负载下是否满足 SLO
- **负载**：预期峰值并发的 100%
- **关注**：SLO 达标率、错误率、资源利用率趋势
- **产出**：SLO 达标评估

### Stress（压力测试）
- **目的**：找到系统的性能拐点和崩溃点
- **负载**：从预期峰值逐步加压至系统崩溃
- **关注**：性能拐点、优雅降级行为、错误类型
- **产出**：系统容量上限和降级表现

### Spike（峰值测试）
- **目的**：验证系统对突发流量的应对能力
- **负载**：瞬间从低负载跳至峰值的 200%-500%
- **关注**：自动扩缩容响应时间、请求排队行为、熔断触发
- **产出**：弹性伸缩评估

### Soak（浸泡测试）
- **目的**：发现长时间运行下的内存泄漏和资源耗尽问题
- **负载**：预期负载的 70%-80%，持续 4-24 小时
- **关注**：内存趋势、连接池泄漏、GC 频率变化、日志磁盘增长
- **产出**：长期稳定性评估

## 2. 工作负载建模

### 流量模型设计
- **开放模型**（Open Model）：新用户以固定速率到达，不受系统响应影响——适用于公网 API
- **闭合模型**（Closed Model）：固定并发用户数，用户等待响应后再发下一请求——适用于内部系统
- 根据真实场景选择模型，错误的模型会导致测试结果偏差 30%-300%

### 场景权重分配
- 从生产日志中提取 Top 10 API 调用比例
- 区分读/写操作比例（典型 Web 应用约 80:20）
- 包含关联操作链（如：登录 → 浏览 → 加购 → 下单 → 支付）
- 加入后台任务的影响（定时任务、消息消费、数据同步）

### 测试数据策略
- 使用脱敏的生产数据或等价的合成数据
- 数据量级必须与生产一致（10 万条和 1 亿条的查询性能完全不同）
- 预热缓存后再测试（除非目的是测缓存穿透）
- 避免所有请求命中同一条数据（热点数据偏斜）

## 3. SLI/SLO/SLA 定义体系

### SLI（服务水平指标）
选择能直接反映用户体验的指标：

| 类别 | 常用 SLI | 测量方式 |
|------|---------|---------|
| 可用性 | 成功请求占比 | (总请求 - 5xx 错误) / 总请求 |
| 延迟 | 请求响应时间 | P50 / P95 / P99 百分位 |
| 吞吐量 | 每秒处理请求数（RPS） | 固定时间窗口内的请求计数 |
| 错误率 | 业务错误占比 | 业务错误请求 / 总请求 |
| 饱和度 | 资源利用率 | CPU / 内存 / 连接池使用率 |

### SLO（服务水平目标）
- SLO 必须可量化、可测量、有时间窗口
- 格式：`[SLI] [目标值] [时间窗口] [测量条件]`
- 示例：API 响应延迟 P99 < 200ms，30 天滚动窗口，排除定期维护时段
- 留出错误预算（Error Budget）：99.9% 可用性 = 每月允许 43 分钟不可用

### SLA（服务水平协议）
- SLA 是对外承诺，SLO 是内部目标
- SLA 阈值应宽于 SLO（如 SLO = 99.95%，SLA = 99.9%）
- SLA 必须包含违约后果和补偿条款

## 4. 测试环境管控

### 环境仿真度
- 硬件配置：与生产保持相同规格或等比缩放（明确缩放比例）
- 网络拓扑：模拟真实的网络延迟和带宽限制
- 中间件版本：与生产完全一致（数据库、缓存、消息队列版本号）
- 数据量级：与生产保持同数量级

### 环境隔离
- 测试环境与生产环境完全隔离
- 外部依赖使用 Mock 或 Stub（标注 Mock 行为与真实行为的差异）
- 明确记录测试环境与生产环境的已知差异

## 5. 测试工具选型指南

| 工具 | 适用场景 | 脚本语言 | 分布式支持 |
|------|---------|---------|-----------|
| k6 (Grafana) | API/微服务，开发者友好 | JavaScript | 原生支持 |
| Gatling | 高并发模拟，CI/CD 集成 | Scala/Java | 原生支持 |
| JMeter | 协议丰富，GUI 驱动 | XML/Groovy | 原生支持 |
| Locust | Python 生态，灵活定制 | Python | 原生支持 |
| Artillery | Serverless/Node.js | YAML/JS | 云原生 |
| wrk/wrk2 | HTTP 基准快速验证 | Lua | 单机 |

**选型原则**：
- 优先选团队已有经验的工具
- CI/CD 集成能力是关键考量
- 分布式负载生成能力决定测试规模上限

## 6. 结果分析与异常识别

### 关键指标分析维度
- **延迟分布**：不看均值看百分位（P50 正常但 P99 飙升说明有长尾问题）
- **吞吐量曲线**：随并发增加是否线性增长？拐点在哪？
- **错误率变化**：错误类型分布（超时 vs 拒绝 vs 业务错误）
- **资源关联**：将性能指标与 CPU/内存/磁盘/网络利用率做时间轴对齐

### 常见异常模式
- **线性恶化**：延迟随并发线性增长——资源争用
- **阶梯跳变**：延迟在某个并发数突然跳升——触发了阈值（如连接池耗尽）
- **周期性波动**：性能周期性下降——GC、定时任务、日志轮转
- **渐进退化**：长时间运行后缓慢恶化——内存泄漏、连接泄漏
