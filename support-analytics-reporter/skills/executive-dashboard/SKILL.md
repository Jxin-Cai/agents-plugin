# Executive Dashboard — 高管仪表盘设计

设计面向高管的业务仪表盘，包含 KPI 层级结构、核心 SQL 查询和可视化布局。

## 加载引用

Read skills/executive-dashboard/references/executive-dashboard-principles.md
Read skills/executive-dashboard/references/dashboard-sql-patterns.md

## 强制执行规则

- 所有用户交互使用中文
- SQL 必须标注目标数据库类型（MySQL / PostgreSQL / BigQuery）
- 每个 KPI 必须有明确的计算公式和数据来源
- 仪表盘设计必须考虑移动端适配

## 前置条件

- 已明确报告受众（CEO / CFO / COO / CMO 等）
- 已确认数据库类型和可用表结构
- 已了解业务核心指标定义

## Step 1: 明确受众和决策场景

分析仪表盘使用者的决策需求：

1. **受众角色** — 确认主要查看者（C-Level / VP / Director）
2. **决策场景** — 该仪表盘支撑什么决策（预算分配、战略调整、运营优化）
3. **查看频率** — 实时 / 每日 / 每周 / 每月
4. **关键问题** — 受众最关心的 3-5 个业务问题

使用 AskUserQuestion 确认：
- "请确认仪表盘的目标受众和核心决策场景，我将据此设计 KPI 层级结构。"

## Step 2: 设计 KPI 层级结构

按层级组织业务指标：

### 北极星指标（1 个）
- 最核心的业务健康度指标
- 示例：月度经常性收入（MRR）、月活跃用户（MAU）

### 一级指标（3-5 个）
- 直接影响北极星指标的关键驱动因素
- 示例：新增收入、留存率、客单价、获客成本

### 二级指标（每个一级下 2-3 个）
- 可诊断一级指标变化原因的细分指标
- 示例：各渠道新增、各产品线收入、各群体留存

对每个指标定义：
- 计算公式
- 数据来源表
- 更新频率
- 正常范围和告警阈值

使用 AskUserQuestion 确认：
- "KPI 层级结构设计如上，层级划分是否覆盖核心业务维度？是否需要增减指标？"

**⏸️ 等待用户确认后进入 Step 3。**

## Step 3: 编写核心 SQL 查询

为每个 KPI 编写生产级 SQL：

1. **月度核心指标汇总** — 使用 CTE 计算各指标当月值
2. **增长率计算** — 同比（YoY）和环比（MoM）
3. **趋势数据** — 最近 12 个月的月度趋势
4. **异常检测** — 标记偏离均值 2 个标准差以上的数据点

SQL 规范：
- 使用 CTE 提升可读性
- 添加中文注释说明业务逻辑
- 参数化日期范围
- 考虑大数据量下的查询性能

将所有 SQL 文件保存到 `dashboards/sql/` 目录。

使用 AskUserQuestion 确认：
- "核心 SQL 查询已编写完成，是否需要调整查询逻辑或补充其他指标？"

**⏸️ 等待用户确认后进入 Step 4。**

## Step 4: 设计仪表盘布局

设计仪表盘的可视化布局：

1. **顶部概览栏** — 北极星指标 + 一级指标卡片（含同环比箭头）
2. **趋势区域** — 核心指标的时间序列折线图
3. **构成分析** — 按维度（产品/渠道/地区）的占比图
4. **明细表格** — 支持下钻的数据明细

输出布局设计文档，包含：
- 每个图表的类型、数据源、交互行为
- 筛选器设计（时间范围、维度筛选）
- 钻取路径（从汇总到明细的导航）

使用 AskUserQuestion 确认：
- "仪表盘布局设计如上，信息层次和交互路径是否满足决策需求？"

**⏸️ 等待用户确认后进入 Step 5 输出产出物。**

## Step 5: 输出产出物

在 `dashboards/` 目录下生成：

```
dashboards/
├── dashboard-design.md       # 仪表盘设计文档（布局 + 交互说明）
├── kpi-hierarchy.md          # KPI 层级定义文档
└── sql/
    ├── monthly-metrics.sql   # 月度核心指标
    ├── growth-rates.sql      # 增长率计算
    ├── trend-analysis.sql    # 趋势分析
    └── anomaly-detection.sql # 异常检测
```

## 成功指标

- 所有 SQL 查询语法正确，可在目标数据库直接执行
- KPI 层级完整覆盖业务核心维度
- 仪表盘布局清晰，信息层次分明
- 设计文档可直接交付给 BI 开发团队实施

## 失败指标

- SQL 查询存在语法错误或性能问题
- KPI 定义模糊，缺少计算公式
- 仪表盘信息过载，无法快速定位关键指标

<IMPORTANT>
你在设计高管仪表盘，不是数据报表。高管需要的是：一眼看懂业务健康度，快速定位问题，支撑决策。
1. 每个元素都必须服务于决策，移除一切装饰性内容
2. KPI 必须有明确的计算公式、数据来源表和告警阈值
3. SQL 除以可能为零的值时必须使用 NULLIF(x, 0) 防除零
4. 仪表盘信息密度遵循 5 秒规则——用户 5 秒内抓住核心信息
</IMPORTANT>
