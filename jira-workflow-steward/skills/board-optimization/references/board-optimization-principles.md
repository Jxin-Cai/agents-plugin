# 看板优化原则

本文档定义了 Jira 看板优化阶段必须遵循的原则。

---

## 1. 看板类型选择

### Scrum Board
- **适用场景**：固定迭代节奏、Sprint 计划驱动的团队
- **核心特征**：Sprint 边界、速率（Velocity）跟踪、燃尽图
- **列映射**：列对应 Sprint 内的工作状态
- **关键配置**：Sprint 容量规划、完成定义（DoD）

### Kanban Board
- **适用场景**：持续交付、无固定迭代节奏的团队
- **核心特征**：WIP 限制、持续流动、周期时间跟踪
- **列映射**：列对应价值流的各个阶段
- **关键配置**：WIP 限制、列策略（进入/退出条件）

### Scrumban Board
- **适用场景**：需要 Sprint 结构但也重视流量管理的团队
- **核心特征**：Sprint 计划 + WIP 限制 + 持续改进
- **适合过渡**：从 Scrum 向 Kanban 渐进转型的团队

### 选择决策树
```
团队有固定迭代周期？
├── 是 → 团队规模 > 8 人？
│   ├── 是 → 考虑 SAFe 多层看板
│   └── 否 → Scrum Board
└── 否 → 工作项可预测性高？
    ├── 是 → Kanban Board
    └── 否 → Scrumban Board
```

## 2. 列（Column）配置

### 列设计原则
- **数量**：5-7 列为佳，绝不超过 10 列
- **映射**：每列必须对应工作流中的一个或多个状态
- **流动性**：从左到右代表工作从开始到完成的流向
- **可见性**：列名自解释，看一眼就知道工作处于什么阶段

### 列与状态映射
- 一列可以包含多个状态（如"开发"列包含"编码中"和"自测中"）
- 一个状态只能属于一列
- 避免出现"隐藏列"（状态存在但在看板上不可见）

### 常见列配置

#### 软件开发看板
```
Backlog | Ready | In Dev | In Review | In QA | Done
```

#### 带缓冲区的看板
```
Backlog | Ready | Doing → Done | Review → Done | QA → Done | Released
```
"→ Done"子列表示该阶段已完成、等待下一阶段拉取

#### 运维/支持看板
```
New | Triaged | Investigating | In Progress | Resolved | Closed
```

## 3. WIP 限制

### WIP 限制的价值
- **减少上下文切换**：人同时做 3 件事的效率低于专注做 1 件事
- **暴露瓶颈**：哪列经常达到上限，哪里就是瓶颈
- **提高完成率**：停止开始新工作，专注完成已开始的工作
- **缩短前置时间**：Little's Law——前置时间 = WIP / 吞吐量

### WIP 限制设置方法
- **起始值**：每列 WIP = 团队成员数 × 1.5（向上取整）
- **调优**：观察 2-4 周，哪列经常堆积就降低其 WIP 限制
- **瓶颈列**：WIP 限制不要设太高，让问题暴露出来
- **缓冲列**：输出缓冲区（如"待评审"）可以设稍高的 WIP

### WIP 违规处理
- WIP 超限时：团队必须先完成在制品，再拉取新工作
- 紧急插入：允许打破 WIP 限制，但必须标记为紧急且记录原因
- 定期复盘：每次回顾会检查 WIP 违规次数和原因

## 4. 泳道（Swimlane）配置

### 泳道类型
- **按优先级**：紧急 / 高 / 中 / 低——紧急泳道在最上方
- **按人员**：每个团队成员一条泳道——适合小团队
- **按工作类型**：功能 / Bug / 技术债务——区分工作类型分布
- **按项目/模块**：多项目团队按项目划分
- **按 Epic**：大颗粒度的功能追踪

### 泳道选择建议
| 团队场景 | 推荐泳道 | 原因 |
|---------|---------|------|
| 频繁有紧急插入 | 按优先级 | 紧急事项一目了然 |
| 关注个人负载 | 按人员 | 直观看到每人并行数 |
| Bug 比例不确定 | 按工作类型 | 监控 Bug 占比趋势 |
| 多项目并行 | 按项目 | 区分不同项目的进度 |

### 紧急泳道
- 始终保留一条"紧急"泳道在最顶部
- 紧急泳道的 WIP 限制 = 1-2
- 紧急泳道中的卡片必须有明确的升级人

## 5. 卡片（Card）配置

### 卡片显示信息
必须显示：
- 问题键（Issue Key）
- 标题
- 经办人头像
- 优先级图标
- 问题类型图标

建议显示：
- 故事点/估算
- 标签
- 到期日（如有）
- 停留天数（在当前状态的时间）

### 卡片颜色编码
| 颜色 | 含义 |
|------|------|
| 红色 | 超过 SLA 或被阻塞 |
| 黄色 | 接近 SLA 或高优先级 |
| 绿色 | 正常流转 |
| 灰色 | 低优先级或暂停 |

### 卡片老化指示
- 卡片在同一列停留超过 N 天变色提醒
- N 的设置参考团队平均周期时间
- 帮助团队快速识别"僵尸卡片"

## 6. 度量与仪表盘

### 核心度量指标

#### 前置时间（Lead Time）
- 定义：从 Issue 创建到关闭的总时间
- 用途：衡量客户等待时间
- 目标：持续缩短，波动减小

#### 周期时间（Cycle Time）
- 定义：从 Issue 开始处理到完成的时间
- 用途：衡量团队处理效率
- 目标：稳定且可预测

#### 吞吐量（Throughput）
- 定义：单位时间内完成的 Issue 数量
- 用途：衡量团队产出能力
- 目标：稳定或持续提升

#### 累积流图（Cumulative Flow Diagram, CFD）
- 定义：各状态的 Issue 数量随时间的累积变化
- 用途：可视化瓶颈、发现趋势
- 看点：带宽收窄表示瓶颈，面积膨胀表示 WIP 增长

### 仪表盘配置建议
- **团队日常看板**：CFD + 周期时间分布 + WIP 监控
- **管理层仪表盘**：吞吐量趋势 + SLA 达成率 + Bug 趋势
- **回顾会仪表盘**：周期时间变化 + WIP 违规次数 + 阻塞原因分布

### 度量反模式
- 不要用度量来考核个人——度量是发现系统问题，不是评价个人
- 不要追求所有指标同时优化——选择 1-2 个当前最重要的
- 不要在没有上下文的情况下对比不同团队的度量

---

## 7. 过滤器与快速视图

### 常用过滤器
- **我的工作**：经办人 = 当前用户
- **阻塞中**：有阻塞标记的 Issue
- **即将到期**：到期日在 3 天内
- **无人认领**：经办人为空且状态为"待办"
- **僵尸卡片**：最后更新超过 14 天

### 快速筛选（Quick Filters）
- 按 Sprint 筛选
- 按经办人筛选
- 按问题类型筛选（只看 Bug / 只看 Story）
- 按标签筛选
- 按组件筛选
