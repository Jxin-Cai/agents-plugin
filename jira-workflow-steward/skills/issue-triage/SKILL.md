## 强制执行规则

- 🛑 **绝不** 在没有了解团队分类需求的情况下生成分类标准
- 📋 你是 **引导者（Facilitator）**，不是规则制定者
- ✅ 始终用中文与用户沟通
- ✅ 严重度与优先级必须分开定义，绝不混为一谈
- 🎯 分类标准必须具体到可判定，避免"根据情况判断"的模糊描述
- 🔄 每个分类维度确定后向用户展示，等待确认
- ⏸️ 展示菜单后 **停下来等用户输入**
- 💾 用户确认后才保存
- 🚫 不到用户确认，不进入下一步

## Step 1: 问题类型梳理

加载工作流设计产出或询问用户当前使用的问题类型。

### 从需求平台采样真实数据（如已配置）

若 `.requirement-mgmt/config.yaml` 存在，先从真实数据入手：

- 使用 `/req-search` 按问题类型分组查询（如 Jira: `project = PROJ ORDER BY issuetype`），统计各类型数量和占比
- 识别实际在用 vs 形同虚设的问题类型
- 抽取每种类型的典型 issue（使用 `/req-fetch`），作为后续定义"典型场景"和"不是什么"的真实案例

将采样结果作为讨论起点展示给用户，比从零回忆更高效。

向用户逐一确认问题类型清单：

### 对每个问题类型明确
```
问题类型：{名称}
定义：{一句话说明什么是这个类型}
典型场景：{2-3 个具体例子}
不是什么：{容易混淆的情况}
工作流：{关联的工作流名称}
```

### 关键判定问题
- "你们团队目前有哪些问题类型？哪些实际在用，哪些形同虚设？"
- "Bug 和改进（Improvement）怎么区分？团队有共识吗？"
- "有没有技术债务的跟踪需求？"
- "运维事件和 Bug 是分开管理还是混在一起？"

**⏸️ 等待用户确认后继续。**

## Step 2: 严重度标准定制

基于团队业务场景定制严重度标准：

### 对每个严重度级别
```
级别：S1-S4
名称：{团队习惯的名称}
定义：{不超过两句话}
判定条件：
  - 影响范围：{全部用户 / 部分用户 / 个别用户}
  - 功能影响：{完全不可用 / 部分可用 / 体验下降}
  - 数据影响：{数据丢失 / 数据错误 / 无数据影响}
  - 安全影响：{有 / 无}
典型案例：{2-3 个贴近团队业务的具体例子}
```

### 关键提问
- "你们业务中，什么情况属于'天塌了'级别？举个例子？"
- "什么情况严重但还能扛一扛？"
- "有没有实际发生过的 Bug 让你觉得当时分级不对？"

向用户展示定制后的严重度矩阵，用团队真实案例验证。

**⏸️ 等待用户确认后继续。**

## Step 3: 优先级标准与 SLA

### 优先级定义
对每个优先级级别定义：
```
级别：P0-P4
名称：{团队习惯的名称}
定义：{处理时机}
响应 SLA：{首次响应的时间目标}
解决 SLA：{解决问题的时间目标}
升级规则：{超过 SLA 后怎么办}
```

### 严重度-优先级交叉矩阵
引导用户建立自己的交叉矩阵：
- "S1 的 Bug 一定是 P0 吗？有没有例外情况？"
- "S3 的 Bug 在什么情况下会被提升到 P1？"
- "你们的 SLA 目标是怎样的？现在能做到吗？"

向用户展示完整的交叉矩阵和 SLA 表格。

**⏸️ 等待用户确认后继续。**

## Step 4: 分诊流程设计

基于团队规模和节奏设计分诊流程：

### 分诊会配置
- 频率和时长
- 参与角色
- 议程流程
- 决策规则（意见不一致时谁拍板）

### 自动化分诊规则
- 新建 Issue 的自动分类建议
- 基于组件的自动经办人分配
- 未分类 Issue 的超时提醒
- 重复 Issue 的自动检测

### 信息完整性检查
- Bug 报告模板定制
- 必填字段清单
- 信息不完整时的处理流程

**⏸️ 等待用户确认后继续。**

## Step 5: 标签与组件规范

### 标签体系
- 建议的标签清单（基于团队业务场景）
- 标签命名规范
- 标签使用场景

### 组件划分
- 基于项目架构的组件清单
- 每个组件的默认负责人
- 组件与代码仓库的映射

向用户展示标签和组件规范。

**⏸️ 等待用户确认后继续。**

## Step 6: 保存产出

将完整的分类标准保存到 `{任务目录}/triage/triage-{日期}.md`，包含：
- 问题类型定义表
- 严重度标准（含团队案例）
- 优先级标准与 SLA
- 严重度-优先级交叉矩阵
- 分诊流程说明
- Bug 报告模板
- 标签与组件规范

## Step 7: 菜单

使用 `AskUserQuestion` 工具向用户展示以下选项（不要用文本菜单让用户输入序号）：

产出摘要：定义了 [N] 种问题类型、[4] 级严重度、[5] 级优先级。分诊流程 [频率]。SLA 已配置。

- **进入看板优化（推荐）** — 基于工作流和分诊标准优化看板配置
- **调整分类标准** — 修改某个维度的定义
- **回到工作流设计** — 如果分诊过程中发现工作流需要调整

**⏸️ 停下来等待用户选择。不要自动执行。**

## 成功/失败指标

### ✅ 成功
- 问题类型有明确的定义和边界，不存在"我不知道该选哪个"的情况
- 严重度标准使用团队真实案例验证过
- 严重度与优先级严格分离
- 优先级有明确的 SLA 目标
- 交叉矩阵与团队实际判断习惯一致
- 分诊流程有明确的频率、角色和决策规则
- Bug 报告模板包含必填信息
- 标签和组件数量可控，命名规范
- 所有标准向用户展示并获得确认

### ❌ 失败
- 严重度和优先级混为一谈
- 分类标准太笼统（如"根据影响程度判断"）
- 没有用团队案例验证标准的可操作性
- SLA 目标不切实际或根本没有设置
- 分诊流程没有明确谁来拍板
- Bug 报告模板要求过多或过少的信息
- 标签数量失控或命名混乱
- 替用户制定标准而不是引导团队达成共识

<IMPORTANT>
本技能完成后，展示菜单并等待用户选择下一步。不要自动执行后续技能。
严重度与优先级必须分开定义，严禁在同一个维度中混用影响范围和处理顺序。
每个严重度级别必须包含至少 2 个贴近团队业务的真实案例作为判定基准。
SLA 数值必须具体到小时/天，禁止只写"尽快处理"或"按情况"。
分诊流程必须指定决策拍板人，禁止出现"团队讨论决定"的模糊表述。
</IMPORTANT>
