# 问题分类原则

本文档定义了 Jira 问题分类和分诊阶段必须遵循的原则。

---

## 1. 问题类型体系

Jira 的问题类型（Issue Type）是分类的基础，必须有清晰的定义和边界。

### 标准问题类型
- **Epic**：大粒度功能集合，跨多个 Sprint，用于战略层面跟踪
- **Story（用户故事）**：从用户视角描述的功能需求，可在一个 Sprint 内交付
- **Task（任务）**：非用户故事的工作项（技术任务、流程改进、调研等）
- **Bug（缺陷）**：已有功能的异常行为，与预期结果不符
- **Sub-task（子任务）**：Story/Task/Bug 的分解项，用于细化跟踪

### 扩展问题类型（按需启用）
- **技术债务（Tech Debt）**：已知的代码/架构问题，需计划修复
- **改进（Improvement）**：对现有功能的优化，非 Bug 修复
- **事件（Incident）**：生产环境的服务中断或故障
- **变更请求（Change Request）**：需要审批的基础设施或配置变更
- **Spike（调研）**：需要研究后才能估算的不确定性工作

### 分类判定规则
- 如果用户能使用且结果不对 → **Bug**
- 如果用户不能使用新功能 → **Story**
- 如果是现有功能更好用 → **Improvement**
- 如果是代码质量问题但不影响功能 → **Tech Debt**
- 如果是不确定能不能做 → **Spike**

## 2. 严重度（Severity）标准

严重度描述问题的影响范围和程度，是**客观事实**，不随业务优先级变化。

### 四级严重度矩阵

| 级别 | 名称 | 定义 | 典型场景 |
|------|------|------|---------|
| S1 | 致命（Critical） | 系统崩溃、数据丢失、安全漏洞，无变通方案 | 生产数据库不可用；支付接口泄露用户信息 |
| S2 | 严重（Major） | 核心功能不可用或严重受损，变通方案代价大 | 用户无法登录但可用备用入口；订单提交间歇性失败 |
| S3 | 一般（Moderate） | 功能部分受损，存在可接受的变通方案 | 报表导出格式错误但数据正确；搜索结果排序不正确 |
| S4 | 轻微（Minor） | 外观问题、文案错误、体验不佳，不影响功能 | 按钮对齐偏移；错别字；颜色不符合设计稿 |

### 严重度判定要素
- **影响范围**：影响所有用户 / 部分用户 / 个别用户
- **功能影响**：完全不可用 / 部分可用 / 体验下降
- **数据影响**：数据丢失 / 数据错误 / 无数据影响
- **变通方案**：无 / 有但代价高 / 有且可接受
- **安全影响**：有安全风险 / 无安全风险

## 3. 优先级（Priority）标准

优先级描述处理顺序，是**业务决策**，由产品负责人或分诊会确定。

### 五级优先级

| 级别 | 名称 | 定义 | 响应 SLA | 解决 SLA |
|------|------|------|---------|---------|
| P0 | 紧急（Emergency） | 立即处理，一切工作让路 | 15 分钟 | 4 小时 |
| P1 | 高（High） | 当前 Sprint 必须解决 | 2 小时 | 24 小时 |
| P2 | 中（Medium） | 下个 Sprint 规划 | 1 工作日 | 1-2 周 |
| P3 | 低（Low） | 资源允许时处理 | 3 工作日 | 按排期 |
| P4 | 最低（Backlog） | 记录备查，无时间承诺 | 无 | 无 |

### 严重度-优先级交叉矩阵

|  | S1 致命 | S2 严重 | S3 一般 | S4 轻微 |
|--|---------|---------|---------|---------|
| 核心功能 | P0 | P1 | P2 | P3 |
| 次要功能 | P1 | P2 | P3 | P4 |
| 边缘功能 | P1 | P2 | P3 | P4 |

此矩阵仅作为建议基线，最终优先级由分诊会基于业务上下文决定。

## 4. 分诊流程

### 分诊会（Triage Meeting）
- **频率**：每日一次（高频团队）或每周两次（稳定团队）
- **时长**：15-30 分钟，严格控制
- **参与者**：产品负责人、技术负责人、QA 负责人
- **输入**：所有新建的、未分类的 Issue
- **输出**：每个 Issue 有明确的类型、严重度、优先级、经办人

### 分诊流程步骤
1. **信息完整性检查**：Issue 描述是否清晰？能否复现？有无截图/日志？
2. **重复检查**：是否已有相同或类似的 Issue？
3. **类型判定**：Bug / Story / Task / Tech Debt？
4. **严重度评估**：影响范围、功能影响、数据影响、安全影响
5. **优先级决定**：基于严重度和业务上下文
6. **分配经办人**：谁来处理？
7. **设置目标版本**：在哪个 Sprint/版本解决？

### 分诊质量标准
- 未分类 Issue 的最大停留时间不超过 2 个工作日
- 每个 Issue 必须有明确的类型和优先级
- P0/P1 Issue 必须在分诊会当场分配经办人
- 信息不完整的 Issue 退回给报告人补充，不猜测

## 5. Bug 报告模板

### 必填信息
```
**环境**：[生产/预发布/测试/开发] + [浏览器/设备/OS]
**复现步骤**：
1. ...
2. ...
3. ...
**预期结果**：...
**实际结果**：...
**发生频率**：[每次/间歇性/仅一次]
```

### 可选但建议填写
- 截图或录屏
- 错误日志/控制台输出
- 影响用户数量估算
- 是否有变通方案

### 信息不完整的处理
- 无法复现的 Bug：标记为"待补充信息"，退回报告人
- 超过 5 个工作日未补充信息：标记为"无法复现"并关闭
- 关闭的 Bug 如果再次出现，重新打开并提升优先级

## 6. 标签与组件体系

### 标签（Label）使用规范
- 标签用于跨项目的横向分类（如 `performance`、`security`、`ux`）
- 标签数量控制在 20 个以内，避免标签泛滥
- 建立标签命名规范（全小写、连字符分隔）
- 定期清理无用标签

### 组件（Component）使用规范
- 组件用于项目内的模块划分（如 `auth-service`、`payment-gateway`）
- 每个组件指定默认负责人
- 新建 Issue 时可自动按组件分配给模块负责人
- 组件与代码仓库/模块对应，保持一致性
