# 分诊流程原则

---

## 1. 分诊流程

### 分诊会配置
- **频率**：每日一次（高频）或每周两次（稳定）
- **时长**：15-30 分钟
- **参与者**：产品负责人、技术负责人、QA 负责人
- **输入**：所有新建的、未分类的 Issue
- **输出**：每个 Issue 有明确的类型、严重度、优先级、经办人

### 分诊步骤
1. 信息完整性检查（描述清晰？可复现？有截图/日志？）
2. 重复检查（是否已有相同/类似 Issue）
3. 类型判定（Bug / Story / Task / Tech Debt）
4. 严重度评估（影响范围、功能/数据/安全影响）
5. 优先级决定（基于严重度和业务上下文）
6. 分配经办人
7. 设置目标版本（Sprint/版本）

### 质量标准
- 未分类 Issue 最大停留 2 个工作日
- 每个 Issue 必须有明确类型和优先级
- P0/P1 必须当场分配经办人
- 信息不完整退回报告人，不猜测

---

## 2. Bug 报告模板

必填：环境（生产/预发/测试/开发 + 浏览器/设备/OS）、复现步骤、预期结果、实际结果、发生频率
可选：截图/录屏、错误日志、影响用户数、变通方案

处理规则：
- 无法复现 -> 标记"待补充信息"退回
- 5 工作日未补充 -> 标记"无法复现"关闭
- 关闭后再次出现 -> 重新打开并提升优先级

---

## 3. 标签与组件体系

### 标签规范
- 用于跨项目横向分类（performance、security、ux）
- 数量不超过 20，全小写、连字符分隔
- 定期清理无用标签

### 组件规范
- 用于项目内模块划分（auth-service、payment-gateway）
- 每个组件指定默认负责人
- 新建 Issue 按组件自动分配
- 组件与代码仓库保持一致
