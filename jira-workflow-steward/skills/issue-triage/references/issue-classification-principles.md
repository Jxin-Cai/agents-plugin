# 问题分类原则

---

## 1. 问题类型体系

### 标准问题类型
- **Epic**：大粒度功能集合，跨多个 Sprint
- **Story**：用户视角的功能需求，一个 Sprint 内交付
- **Task**：非用户故事的工作项（技术任务、调研等）
- **Bug**：已有功能的异常行为
- **Sub-task**：Story/Task/Bug 的分解项

### 扩展类型（按需启用）
Tech Debt / Improvement / Incident / Change Request / Spike

### 分类判定

| 场景 | 类型 |
|------|------|
| 用户能用但结果不对 | Bug |
| 用户不能使用新功能 | Story |
| 现有功能更好用 | Improvement |
| 代码质量不影响功能 | Tech Debt |
| 不确定能不能做 | Spike |

---

## 2. 严重度（Severity）标准

严重度描述影响范围和程度，是**客观事实**，不随业务优先级变化。

| 级别 | 名称 | 定义 | 典型场景 |
|------|------|------|---------|
| S1 | 致命 | 系统崩溃/数据丢失/安全漏洞，无变通 | 生产 DB 不可用；支付泄露 |
| S2 | 严重 | 核心功能不可用，变通代价大 | 登录不可用但有备用入口 |
| S3 | 一般 | 功能部分受损，有可接受变通 | 报表格式错但数据正确 |
| S4 | 轻微 | 外观/文案问题，不影响功能 | 按钮偏移；错别字 |

判定要素：影响范围、功能影响、数据影响、变通方案、安全影响

---

## 3. 优先级（Priority）标准

优先级描述处理顺序，是**业务决策**，由产品负责人或分诊会确定。

| 级别 | 名称 | 响应 SLA | 解决 SLA |
|------|------|---------|---------|
| P0 | 紧急 | 15 分钟 | 4 小时 |
| P1 | 高 | 2 小时 | 24 小时 |
| P2 | 中 | 1 工作日 | 1-2 周 |
| P3 | 低 | 3 工作日 | 按排期 |
| P4 | 最低 | 无 | 无 |

### 严重度-优先级交叉矩阵

|  | S1 致命 | S2 严重 | S3 一般 | S4 轻微 |
|--|---------|---------|---------|---------|
| 核心功能 | P0 | P1 | P2 | P3 |
| 次要功能 | P1 | P2 | P3 | P4 |
| 边缘功能 | P1 | P2 | P3 | P4 |

此矩阵仅作建议基线，最终优先级由分诊会基于业务上下文决定。
