# 工作流设计原则

本文档定义了 Jira 工作流设计阶段必须遵循的原则。

---

## 1. 状态设计原则

工作流的状态是团队工作可视化的基础，必须精心设计。

### 状态最小化
- 理想状态数量为 5-7 个，绝不超过 10 个
- 每个状态必须代表一个真实的、可观测的工作阶段
- 如果两个状态之间没有显式的交接动作或等待，合并它们
- 避免"万能状态"（如"处理中"涵盖编码、测试、部署所有阶段）

### 状态命名规范
- 使用动词+名词形式（如"等待评审"而非"评审"）
- 名称必须自解释，新人看到就能理解含义
- 避免歧义词："Pending"（等什么？）、"In Progress"（在做什么？）
- 推荐格式：`待{动作}` / `{动作}中` / `已{动作}`（如"待评审"/"开发中"/"已部署"）

### 状态分类
- **待办态（To Do Category）**：工作尚未开始——待规划、待开发
- **进行态（In Progress Category）**：工作正在进行——开发中、评审中、测试中
- **完成态（Done Category）**：工作已结束——已完成、已关闭、已取消

---

## 2. 转换规则设计

转换（Transition）是状态之间的路径，定义了工作如何流动。

### 转换条件（Conditions）
- **角色限制**：谁可以触发这个转换？（如只有测试人员可以将"测试中"转为"已通过"）
- **字段条件**：触发前哪些字段必须有值？（如转到"开发中"时必须有经办人）
- **前置状态**：只能从特定状态转换过来（禁止跳跃式流转）

### 转换验证器（Validators）
- 必填字段验证：转换前确保关键字段已填写
- 工时验证：转到"完成"前确保记录了工时
- 评论验证：拒绝/退回时必须填写原因

### 转换后置动作（Post Functions）
- 自动分配经办人
- 自动更新字段值（如设置解决结果）
- 触发通知
- 触发 Webhook 或自动化规则

### 反模式
- 避免"从任意状态到任意状态"的全连接图——这不是工作流，是混乱
- 避免单向线性流——现实中工作会被退回，必须有回退路径
- 避免过多的转换按钮——经办人面对 8 个按钮会犯选择困难症

## 3. 工作流模板库

根据团队类型选择基础模板，在此基础上定制。

### 软件开发团队（Scrum）
```
待办 → 待开发 → 开发中 → 待评审 → 评审中 → 待测试 → 测试中 → 待发布 → 已完成
```
简化版：`待办 → 开发中 → 评审中 → 测试中 → 已完成`

### 软件开发团队（Kanban）
```
Backlog → Ready → In Progress → In Review → Done
```
关键：每列必须有 WIP 限制

### Bug 修复流程
```
新建 → 已确认 → 修复中 → 待验证 → 已关闭
        ↘ 不修复/重复/无法复现 → 已关闭
```

### 运维/事件响应
```
告警触发 → 已确认 → 调查中 → 修复中 → 已恢复 → 事后复盘 → 已关闭
```

### 变更请求
```
已提交 → 待评估 → 已批准/已拒绝 → 实施中 → 已验证 → 已关闭
```

## 4. 字段方案设计

工作流与字段方案配合使用，确保每个阶段有正确的信息。

### 必填字段策略
- 创建时：标题、类型、优先级
- 开始开发时：经办人、估算工时
- 完成时：解决结果、实际工时
- 原则：**在需要信息的时刻才要求填写**，不要在创建时要求填 20 个字段

### 自定义字段控制
- 自定义字段数量不超过项目实际需要的——每个多余字段都是维护负担
- 定期清理不再使用的自定义字段
- 使用字段配置方案控制不同问题类型的可见字段

---

## 5. 工作流方案与共享

### 工作流方案（Workflow Scheme）
- 同类项目使用相同的工作流方案，减少维护成本
- 不同问题类型可以绑定不同工作流（Bug 和 Story 的流程通常不同）
- 变更工作流方案会影响所有关联项目，变更前充分评估

### 工作流演进策略
- 从简单开始，在实践中发现不足再迭代
- 每次回顾会评估工作流是否合理
- 每次只改一个变量，观察效果后再改下一个
- 记录每次变更的原因和预期效果

---

## 6. 自动化规则

### 高价值自动化场景
- PR 合并后自动将 Issue 流转到"待测试"
- Issue 超过 N 天无更新，自动提醒经办人
- 子任务全部完成后，自动流转父任务
- 新建 Bug 自动分配给对应模块负责人
- Sprint 结束时未完成的 Issue 自动退回 Backlog

### 自动化设计原则
- 自动化规则必须可追踪（谁触发了、什么时候、做了什么）
- 自动化不应该替代人的判断（如自动关闭 Bug 需谨慎）
- 每条自动化规则都要有失败时的处理方式
