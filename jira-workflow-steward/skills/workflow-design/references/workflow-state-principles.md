# 工作流状态与转换原则

---

## 1. 状态设计原则

### 状态最小化
- 理想 5-7 个，绝不超过 10 个
- 每个状态代表真实可观测的工作阶段
- 无显式交接或等待的两个状态应合并
- 避免万能状态（如"处理中"涵盖所有阶段）

### 命名规范
- 格式：`待{动作}` / `{动作}中` / `已{动作}`
- 必须自解释，新人看到能理解
- 避免歧义词：Pending（等什么？）、In Progress（做什么？）

### 状态分类

| 类别 | 含义 | 示例 |
|------|------|------|
| 待办态 | 工作未开始 | 待规划、待开发 |
| 进行态 | 工作进行中 | 开发中、评审中、测试中 |
| 完成态 | 工作已结束 | 已完成、已关闭、已取消 |

---

## 2. 转换规则设计

| 规则类型 | 说明 |
|---------|------|
| 条件 | 角色限制（谁可触发）、字段条件（必要字段有值）、前置状态（禁止跳跃） |
| 验证器 | 必填字段验证、工时验证、退回必须填原因 |
| 后置动作 | 自动分配经办人、更新字段、触发通知/Webhook |

反模式：
- 避免全连接图（任意到任意）——不是工作流，是混乱
- 避免纯单向线性流——现实中工作会被退回，必须有回退路径
- 避免过多转换按钮（> 4 个导致选择困难）

---

## 3. 工作流模板库

| 团队类型 | 工作流 |
|---------|--------|
| Scrum 开发 | 待办 -> 开发中 -> 评审中 -> 测试中 -> 已完成 |
| Kanban 开发 | Backlog -> Ready -> In Progress -> In Review -> Done（每列有 WIP） |
| Bug 修复 | 新建 -> 已确认 -> 修复中 -> 待验证 -> 已关闭（含不修复/重复/无法复现分支） |
| 运维事件 | 告警 -> 已确认 -> 调查中 -> 修复中 -> 已恢复 -> 复盘 -> 已关闭 |
| 变更请求 | 已提交 -> 待评估 -> 已批准/已拒绝 -> 实施中 -> 已验证 -> 已关闭 |
