# 集成测试计划原则

本文档定义了集成测试计划阶段必须遵循的原则。

---

## 1. 集成测试分层策略

集成测试不是"把所有服务启动起来跑一遍"。必须分层，逐步扩大集成范围。

### 窄集成测试（Narrow Integration Test）
- 范围：单个服务 + 其直接依赖（数据库、缓存、消息队列）
- 方式：用真实的依赖（Testcontainers / 嵌入式 DB），Mock 外部服务
- 目的：验证数据库查询、缓存策略、消息发送是否正确
- 速度：秒级，可在 CI 中频繁运行

### 宽集成测试（Broad Integration Test）
- 范围：多个服务协作完成一个业务流程
- 方式：用 Docker Compose / K8s 测试环境，真实服务间通信
- 目的：验证服务间的请求-响应、事件传递、数据一致性
- 速度：分钟级，在关键分支或发布前运行

### 端到端契约验证（E2E Contract Verification）
- 范围：完整业务流程跨多个服务
- 方式：在类生产环境中执行，关注关键路径
- 目的：最终确认"整个链路是通的"
- 速度：较慢，通常在发布前或定时运行

## 2. 测试数据管理

### 黄金法则
- 测试数据自给自足——每个测试自己创建需要的数据，不依赖共享数据
- 测试结束后清理——不留"垃圾数据"污染下次运行
- 测试之间相互隔离——并行运行不冲突

### 数据策略
| 策略 | 适用场景 | 优势 | 劣势 |
|------|---------|------|------|
| 工厂模式（Factory） | 单元/窄集成测试 | 灵活、可控 | 需要维护工厂代码 |
| Fixture/Seed | 宽集成测试 | 一致性高 | 变更成本高 |
| Snapshot | 性能基准测试 | 真实数据分布 | 数据脱敏成本 |
| 动态生成 | 契约测试 | Matcher 驱动 | 覆盖有限 |

### 数据隔离技术
- 数据库级别：每个测试用独立 Schema 或独立数据库实例（Testcontainers）
- 租户级别：用唯一的租户 ID 隔离
- 事务级别：测试在事务中运行，结束后回滚

## 3. Mock 与 Stub 策略

### 何时 Mock、何时用真实服务

| 场景 | 使用 Mock | 使用真实服务 |
|------|----------|------------|
| 外部第三方 API（支付、短信） | ✅ 必须 Mock | ❌ 不可控 |
| 团队内部其他服务 | 契约测试时 Mock | 集成测试时用真实服务 |
| 数据库 | ❌ 尽量用真实 | ✅ Testcontainers |
| 缓存（Redis） | ❌ 尽量用真实 | ✅ Testcontainers |
| 消息队列（Kafka） | 契约测试时 Mock | ✅ Testcontainers |

### Mock 工具选型
| 工具 | 适用协议 | 特点 |
|------|---------|------|
| WireMock | HTTP/REST | 强大的请求匹配、录制回放 |
| MockServer | HTTP/HTTPS | 支持前向代理、动态响应 |
| Prism | OpenAPI | 基于 API 规格自动生成 Mock |
| Testcontainers | 任意 | 真实中间件容器化 |

### Mock 准确性保证
- Mock 的行为必须与契约一致——契约变更时 Mock 同步更新
- 定期用真实服务验证 Mock 的行为是否仍然准确
- Pact 的 Provider 验证就是"验证 Mock 是否还准确"的机制

## 4. 集成测试用例设计

### 用例分类
1. **正向流程测试**：核心业务路径（如 下单 -> 支付 -> 发货）
2. **异常流程测试**：服务不可用、超时、返回错误码
3. **边界条件测试**：空数据、超大数据、并发操作
4. **降级策略测试**：依赖不可用时的降级行为
5. **数据一致性测试**：跨服务操作后数据是否最终一致

### 用例模板
```
用例名称：[业务场景描述]
前置条件：[需要准备的数据和服务状态]
触发操作：[发起的 API 调用或事件]
验证点：
  - 响应：[状态码、Body 关键字段]
  - 数据库：[数据变更是否正确]
  - 事件：[是否发出了预期的消息/事件]
  - 副作用：[通知、日志、指标]
清理操作：[测试后的数据清理]
```

## 5. CI/CD 集成策略

### 测试阶段编排
```
代码提交
  ↓
单元测试 + 契约测试（消费者端）       ← 快速反馈，< 2 分钟
  ↓
窄集成测试（Testcontainers）          ← 中速，< 5 分钟
  ↓
契约验证（提供者端）+ can-i-deploy    ← 部署前关卡
  ↓
宽集成测试（测试环境）                 ← 发布前，< 15 分钟
  ↓
部署到预发布环境
  ↓
冒烟测试 + 健康检查                    ← 部署后验证
```

### 失败策略
- 单元测试/契约测试失败：阻断流水线，必须修复
- 窄集成测试失败：阻断流水线，检查依赖变更
- 宽集成测试失败：阻断发布，但不阻断开发分支合并
- 冒烟测试失败：触发自动回滚

## 6. 环境管理

### 环境类型
| 环境 | 用途 | 数据 | 外部依赖 |
|------|------|------|---------|
| 本地开发 | 开发者自测 | Testcontainers | Mock |
| CI 环境 | 持续集成 | 临时容器 | Mock |
| 集成测试环境 | 宽集成测试 | 种子数据 | 沙箱/Mock |
| 预发布（Staging） | 发布前验证 | 脱敏生产数据 | 沙箱 |
| 生产 | 真实运行 | 生产数据 | 真实服务 |

### 环境一致性
- 使用 Infrastructure as Code（Terraform / Helm）保证环境配置一致
- 容器化所有服务和依赖，减少"在我机器上能跑"问题
- 环境配置与代码版本绑定，避免配置漂移
