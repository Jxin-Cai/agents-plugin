# API 健康检查原则

本文档定义了 API 健康检查设计阶段必须遵循的原则。

---

## 1. 健康检查端点设计

### 分级健康检查

健康检查不只是返回 `{"status": "ok"}`。必须分级，服务于不同消费者。

| 级别 | 端点 | 消费者 | 内容 |
|------|------|--------|------|
| **Liveness** | `/health/live` | K8s Liveness Probe | 进程是否存活——不检查依赖 |
| **Readiness** | `/health/ready` | K8s Readiness Probe / 负载均衡 | 能否接受流量——检查核心依赖 |
| **Startup** | `/health/startup` | K8s Startup Probe | 初始化是否完成——冷启动检查 |
| **详细状态** | `/health/detail` | 运维/监控系统 | 所有依赖的详细状态 |

### 响应格式标准

遵循 RFC Health Check Response（draft-inadarei-api-health-check）：

```json
{
  "status": "pass",
  "version": "1.2.3",
  "releaseId": "abc123",
  "serviceId": "order-service",
  "description": "订单服务健康状态",
  "checks": {
    "database:postgresql": [
      {
        "componentType": "datastore",
        "status": "pass",
        "time": "2026-04-06T10:00:00Z",
        "output": "连接池: 5/20 活跃"
      }
    ],
    "cache:redis": [
      {
        "componentType": "datastore",
        "status": "pass",
        "time": "2026-04-06T10:00:00Z",
        "output": "延迟: 2ms"
      }
    ],
    "upstream:payment-service": [
      {
        "componentType": "component",
        "status": "warn",
        "time": "2026-04-06T10:00:00Z",
        "output": "P95 延迟: 800ms（阈值: 500ms）"
      }
    ]
  }
}
```

### 状态定义
| 状态 | 含义 | HTTP 状态码 |
|------|------|-----------|
| `pass` | 健康 | 200 |
| `warn` | 可用但有退化 | 200 |
| `fail` | 不健康 | 503 |

## 2. 依赖健康检查策略

### 检查分类

| 依赖类型 | 检查方式 | 超时 | 失败影响 |
|---------|---------|------|---------|
| 数据库 | 连接池状态 + 简单查询（如 `SELECT 1`） | 3s | Readiness = fail |
| 缓存（Redis） | PING + 读写测试 | 2s | 可降级运行 |
| 消息队列 | 连接状态 + 生产者确认 | 3s | Readiness = fail |
| 上游服务 | 调用其 `/health/live` | 5s | 视重要性决定 |
| 文件系统 | 读写权限检查 | 2s | 视功能依赖决定 |

### 检查频率

- Liveness：每 10 秒（K8s 默认）
- Readiness：每 5-10 秒
- 详细状态：每 30 秒（供 Prometheus 抓取）
- 告警系统：每 1 分钟

### 失败容忍策略
- **连续失败阈值**：连续 N 次失败才判定为不健康（避免瞬时抖动误判）
- **超时处理**：检查超时等同于失败，不阻塞其他检查
- **并行检查**：所有依赖检查并行执行，总时间 <= 最慢的单个检查
- **熔断机制**：依赖长时间不健康时，跳过检查直接标记为 fail，避免资源浪费

## 3. SLI/SLO 定义

### 关键 SLI（Service Level Indicator）

| SLI | 计算方式 | 典型值 |
|-----|---------|--------|
| 可用性 | 成功请求数 / 总请求数 | 99.9% |
| 延迟 P50 | 50 百分位响应时间 | < 100ms |
| 延迟 P95 | 95 百分位响应时间 | < 500ms |
| 延迟 P99 | 99 百分位响应时间 | < 1000ms |
| 错误率 | 5xx 响应数 / 总请求数 | < 0.1% |
| 饱和度 | CPU/内存/连接池使用率 | < 80% |

### SLO 制定原则
- SLO 必须与业务价值挂钩——不是越高越好，99.999% 的成本远高于 99.9%
- 用 Error Budget（错误预算）管理：SLO = 99.9% 意味着每月允许 43 分钟不可用
- SLO 分级：核心接口 vs 非核心接口可以有不同的 SLO
- 定期回顾：每月/每季度基于实际数据调整 SLO

## 4. 告警策略

### 告警分级

| 级别 | 触发条件 | 通知方式 | 响应时间 |
|------|---------|---------|---------|
| **P0-Critical** | 服务完全不可用 / 数据丢失风险 | 电话 + 短信 + IM | 立即 |
| **P1-High** | 核心功能受损 / SLO 即将突破 | IM + 邮件 | 15 分钟 |
| **P2-Medium** | 非核心功能异常 / 性能退化 | IM | 1 小时 |
| **P3-Low** | 预警信号 / 趋势异常 | 邮件 / Dashboard | 工作时间内 |

### 告警设计原则
- **告警必须可操作**：收到告警后有明确的排查步骤
- **避免告警疲劳**：不要每次请求失败都告警——使用聚合和抑制
- **多窗口告警**：结合短窗口（5 分钟）和长窗口（1 小时）判断
- **告警与 Runbook 绑定**：每个告警规则关联处理手册
- **自动恢复检测**：告警触发后自动检测是否恢复，发送恢复通知

### 告警规则模板
```
告警名称：[服务名]-[指标]-[级别]
触发条件：[指标] [操作符] [阈值] 持续 [时长]
通知渠道：[电话/短信/IM/邮件]
抑制规则：[更高级别告警触发时抑制此告警]
Runbook：[处理手册链接]
```

## 5. 合成监控（Synthetic Monitoring）

### 概念
主动地、持续地从外部探测 API 的可用性和性能——不等用户报告，提前发现问题。

### 监控场景

| 场景 | 频率 | 内容 |
|------|------|------|
| 可用性探测 | 每 1 分钟 | 关键接口 HTTP 200 检查 |
| 功能验证 | 每 5 分钟 | 核心业务流程端到端执行 |
| 性能基准 | 每 15 分钟 | 响应时间是否在 SLO 范围内 |
| SSL 证书检查 | 每天 | 证书过期时间 |
| DNS 解析 | 每 5 分钟 | 域名解析是否正常 |

### 多地域探测
- 从多个地域发起探测，区分"某地域故障"和"全局故障"
- 至少覆盖：用户主要分布地域 + 服务部署地域
- 地域间结果不一致时，标记为地域性问题

## 6. 可观测性三大支柱

### Metrics（指标）
- 使用 RED 方法：Rate（请求速率）、Errors（错误率）、Duration（延迟）
- 使用 USE 方法（资源级）：Utilization（利用率）、Saturation（饱和度）、Errors（错误）
- 推荐：Prometheus + Grafana

### Logs（日志）
- 结构化日志（JSON 格式），包含 traceId、spanId
- 日志级别合理：ERROR = 需要人工介入，WARN = 值得关注，INFO = 关键业务事件
- 推荐：ELK / Loki + Grafana

### Traces（追踪）
- 分布式追踪覆盖所有服务间调用
- 标注关键 Span（数据库查询、外部调用、队列发送）
- 推荐：Jaeger / Zipkin / OpenTelemetry
