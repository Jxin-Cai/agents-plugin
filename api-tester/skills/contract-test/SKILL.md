# 契约测试

用户传入的参数：`$ARGUMENTS`

---

## 加载引用

使用 Read 工具加载以下引用文件，严格遵守其中所有规则：

- `references/contract-test-principles.md` — 契约测试原则（消费者驱动、分层策略、版本管理、多协议支持、反模式）

## 强制执行规则

- ✅ 始终用中文与用户沟通
- 🎯 契约只包含消费者实际使用的字段——绝不过度规约
- 🔄 每个交互都要确认 Provider State
- 📐 使用 Matcher 而非精确值——保持契约灵活性
- ⏸️ 用户确认后才保存，不到确认不进入下一步

加载以下上下文（如果存在）：

## Step 1: 识别服务拓扑

引导用户梳理服务间关系：

1. **列出相关服务**：哪些服务参与此次测试？
2. **识别消费者-提供者关系**：谁调用谁？用什么协议？
3. **绘制依赖图**：

```
[消费者A] --REST--> [提供者X]
[消费者A] --gRPC--> [提供者Y]
[消费者B] --REST--> [提供者X]
[提供者X] --Kafka--> [消费者C]
```

4. **标注 API 类型**：REST / GraphQL / gRPC / 异步消息

**如果项目中已有 OpenAPI/Swagger/Proto 文件：**
- 扫描并提取已有的 API 定义
- 向用户确认："我发现了这些 API 定义，对吗？"

**⏸️ 等待用户确认后继续。**

## Step 2: 定义契约交互

对每一对消费者-提供者关系，逐一定义契约交互：

### 对每个交互追问：

| 追问 | 目标 |
|------|------|
| "消费者从这个接口需要哪些字段？" | 确定最小契约范围 |
| "调用前需要什么前置条件（Provider State）？" | 定义测试数据状态 |
| "正常响应的状态码和结构是什么？" | 定义正向路径契约 |
| "参数非法时返回什么？" | 定义 400 错误契约 |
| "资源不存在时返回什么？" | 定义 404 错误契约 |
| "未授权时返回什么？" | 定义 401/403 错误契约 |

### 契约交互模板

对每个交互，生成结构化描述：

```markdown
### 交互：[消费者] 获取 [资源]

**Provider State：** [前置条件]

**请求：**
- 方法：GET
- 路径：/api/v1/resources/{id}
- Headers：Authorization: Bearer {token}（Matcher: 非空字符串）

**预期响应（200）：**
- Status: 200
- Body:
  - id: Matcher.integer()
  - name: Matcher.string()
  - status: Matcher.term(generate: "active", regex: "active|inactive")

**预期响应（404）：**
- Status: 404
- Body:
  - error: Matcher.string()
  - message: Matcher.string()
```

**每定义完一个交互，立即向用户展示，确认后再进入下一个。**

## Step 3: 三条链路契约覆盖

对每个交互，检查三条链路的契约覆盖：

```
交互：[名称]
├── 正向：[200/201 成功响应契约] ✅/❌
├── 异常：[400/401/404/500 错误响应契约] ✅/❌
└── 逆向：[DELETE/撤销操作的契约] ✅/❌（如适用）
```

向用户报告覆盖情况，标记缺失的契约。

## Step 4: 制定验证策略

为用户制定契约验证的落地方案：

1. **工具选型建议**：根据技术栈推荐 Pact / Spring Cloud Contract / Dredd
2. **CI/CD 集成方案**：
   - 消费者测试在哪个阶段运行
   - 提供者验证在哪个阶段运行
   - `can-i-deploy` 检查点
3. **契约管理方案**：
   - Pact Broker 部署建议
   - 版本标签策略
   - Pending/WIP Pacts 配置

向用户展示方案，等待确认。

**⏸️ 等待用户确认后继续。**

## Step 5: 保存产出

将契约测试方案保存到 `{工作目录}/contracts/contract-{日期}.md`，包含：
- 服务拓扑图
- 所有契约交互定义
- 三条链路覆盖状态
- 验证策略和 CI/CD 集成方案

## Step 6: 菜单

使用 `AskUserQuestion` 工具向用户展示以下选项（不要用文本菜单让用户输入序号）：

产出摘要：[N] 对消费者-提供者关系，[M] 个契约交互。三条链路覆盖：正向 [a]，异常 [b]，逆向 [c]。

- **进入集成测试计划（推荐）** — 基于契约制定集成测试策略和用例
- **补充更多契约** — 如果还有遗漏的交互
- **直接进入健康检查** — 如果集成测试已有方案

**⏸️ 停下来等待用户选择。不要自动执行。**

## 自检清单

| 维度 | 合格标准 |
|------|---------|
| 拓扑完整 | 所有消费者-提供者关系已识别并绘制 |
| Matcher | 每个交互用 Matcher 而非精确值 |
| Provider State | 每个交互定义了前置状态 |
| 三条链路 | 正向/异常/逆向契约均已覆盖 |
| CI/CD | 验证策略含 can-i-deploy 检查 |
| 最小契约 | 只包含消费者实际使用的字段 |
