# 障碍清除原则

本文档定义了障碍清除阶段必须遵循的原则。

---

## 1. 阻塞分类框架

阻塞不是一个模糊的概念。精确分类是有效解决的前提。

### 技术阻塞
- 技术方案设计难题（架构决策、技术选型）
- 环境问题（开发/测试/预发布环境不可用或不稳定）
- 工具链问题（CI/CD 故障、构建工具异常）
- 性能瓶颈（发现了无法接受的性能问题）

### 人员阻塞
- 等待特定人员的代码审查或技术决策
- 关键知识持有者不可用（请假、离职、被其他任务占用）
- 跨时区沟通延迟
- 干系人不响应或决策拖延

### 依赖阻塞
- 等待其他团队交付 API/SDK/服务
- 第三方供应商延迟
- 上游数据不可用或质量不达标
- 共享服务（基础设施、安全审查）排队

### 流程阻塞
- 审批流程过长（安全审查、合规审批、发布审批）
- 过于严格的变更管理流程
- 不清晰的 Definition of Done
- 跨团队协作流程缺失

### 资源阻塞
- 硬件资源不足（服务器、测试设备）
- 软件许可证不够
- 测试数据不可用
- 预算限制

### 需求阻塞
- 需求描述模糊导致无法开发
- 业务规则冲突或缺失
- 验收标准不明确
- 优先级不清晰

---

## 2. 根因分析方法

### 5 Whys 追问法
- 对每个阻塞连续追问"为什么"，直到找到根本原因
- 通常需要 3-5 层追问
- **关键原则**：每一层的回答必须基于事实，不是猜测
- **常见陷阱**：过早停止（只到表面原因）、归咎于人而非系统

### 鱼骨图分析法
当阻塞原因复杂时，从六个维度分析：
- **人员**：技能不足、沟通不畅、人手不够
- **方法**：流程不合理、规范缺失、最佳实践未采纳
- **机器**：工具/环境问题、基础设施不足
- **材料**：需求质量、数据质量、文档质量
- **度量**：指标缺失、反馈延迟、度量方式不当
- **环境**：组织文化、跨团队关系、市场压力

### 系统性问题判定
- 同类阻塞在 3 个月内出现 ≥ 3 次 → 系统性问题
- 不同阻塞指向同一根因 → 结构性问题
- 解决后很快复发 → 治标不治本
- 跨多个团队出现类似阻塞 → 组织级问题

## 3. 升级路径与 SLA

### 升级时间线
| 阻塞等待时长 | 升级动作 |
|-------------|---------|
| 0-4 小时 | 团队内自行解决（蜂群攻关） |
| 4-24 小时 | 团队 lead 介入协调 |
| 24-48 小时 | Scrum Master / 项目经理升级到管理层 |
| 48-72 小时 | 管理层级联升级，启动专项解决 |
| > 72 小时 | 红色警报，可能需要调整项目计划 |

### 有效升级的要素
一个有效的升级沟通必须包含：
1. **阻塞描述**：简明扼要，一两句话说清
2. **影响范围**：影响多少人/工作项/关键路径
3. **已等待时长**：用事实说话，不用情绪
4. **已尝试的方案**：说明团队已经做了什么
5. **需要的帮助**：具体请求，不是笼统的"帮忙看看"
6. **建议方案**：如果有的话

### 升级不是告状
- 升级是寻求帮助，不是推卸责任
- 升级时描述事实和影响，不归咎个人
- 升级后主动跟进，不是"交出去就不管了"

## 4. 蜂群攻关（Swarming）

当高优先级阻塞出现时，集中团队力量快速解决。

### 触发条件
- 阻塞影响关键路径
- 阻塞影响 ≥ 3 人的工作
- 常规方法 4 小时内无法解决

### 蜂群攻关流程
1. **召集**：通知相关人员，明确问题描述（5 分钟）
2. **诊断**：集体分析问题，共享各自的观察（15 分钟）
3. **方案**：快速讨论 2-3 个可能的解决方向（10 分钟）
4. **执行**：选择最有可能的方向，分工执行（时间视问题复杂度）
5. **验证**：确认问题解决，记录经验教训（10 分钟）

### 蜂群攻关纪律
- 不在蜂群会中讨论"谁的错"——只讨论"怎么解"
- 蜂群有时间盒：1-2 小时内看不到进展就升级
- 结束后做 5 分钟回顾：这类问题如何预防

## 5. 依赖管理

### 依赖可视化
- 使用依赖矩阵标注团队间的依赖关系
- 每个依赖标注：提供方、消费方、预期交付日期、当前状态
- 高风险依赖（在关键路径上 + 交付日期不确定）用红色标注

### 依赖风险缓解
| 策略 | 适用场景 | 操作 |
|------|---------|------|
| 前置沟通 | 所有已知依赖 | 迭代规划时与依赖方确认交付时间 |
| Mock/Stub | 等待 API 或服务 | 基于契约先行开发，后续集成 |
| 缓冲计划 | 高风险依赖 | 在计划中预留缓冲时间 |
| 备选方案 | 依赖方交付不确定 | 准备 Plan B（自建/替代方案） |
| Scrum of Scrums | 多团队协作 | 每日/每周跨团队同步阻塞和依赖 |

### 依赖 SLA
- 与依赖方约定响应时间（如"收到请求后 24 小时内回复"）
- SLA 违约时自动触发升级
- 定期回顾依赖 SLA 的达成率

---

## 6. 持续改进闭环

### 阻塞回顾
每个迭代结束时回顾本迭代的阻塞：
- 本迭代出现了多少个阻塞？
- 平均解决时间是多少？趋势如何？
- 哪些是新出现的？哪些是重复出现的？
- 重复出现的阻塞是否已有系统性解决方案？

### 预防性措施
- **技术阻塞预防**：架构决策前置、技术 Spike、环境自动化
- **人员阻塞预防**：知识共享、结对编程、轮岗制度
- **依赖阻塞预防**：依赖前置识别、契约优先开发、缓冲计划
- **流程阻塞预防**：简化审批流程、自动化合规检查、清晰的 DoD
