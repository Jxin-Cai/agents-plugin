# 障碍清除原则

---

## 1. 阻塞分类框架

| 类型 | 典型场景 |
|------|---------|
| 技术 | 架构决策难题、环境不可用、CI/CD 故障、性能瓶颈 |
| 人员 | 等待代码审查/技术决策、关键人员不可用、跨时区延迟、干系人不响应 |
| 依赖 | 等待其他团队交付、第三方供应商延迟、上游数据不可用、共享服务排队 |
| 流程 | 审批流程过长、变更管理过严、DoD 不清晰、跨团队协作流程缺失 |
| 资源 | 硬件不足、许可证不够、测试数据不可用、预算限制 |
| 需求 | 需求描述模糊、业务规则冲突、验收标准不明确、优先级不清晰 |

---

## 2. 根因分析方法

### 5 Whys 追问法
- 对每个阻塞连续追问"为什么"，通常需要 3-5 层
- 每一层回答必须基于事实，不是猜测
- 常见陷阱：过早停止（只到表面原因）、归咎于人而非系统

### 鱼骨图六维度

人员（技能/沟通）、方法（流程/规范）、机器（工具/基础设施）、材料（需求/数据质量）、度量（指标/反馈）、环境（组织文化/市场压力）

### 系统性问题判定

| 信号 | 判定 |
|------|------|
| 同类阻塞 3 个月内出现 >= 3 次 | 系统性问题 |
| 不同阻塞指向同一根因 | 结构性问题 |
| 解决后很快复发 | 治标不治本 |
| 跨多个团队出现 | 组织级问题 |

## 3. 升级路径与 SLA

| 等待时长 | 升级动作 |
|---------|---------|
| 0-4 小时 | 团队内自行解决（蜂群攻关） |
| 4-24 小时 | 团队 lead 介入协调 |
| 24-48 小时 | SM/PM 升级到管理层 |
| 48-72 小时 | 管理层级联升级，启动专项 |
| > 72 小时 | 红色警报，调整项目计划 |

### 有效升级六要素

阻塞描述（一两句话） -> 影响范围（人数/工作项） -> 已等待时长 -> 已尝试方案 -> 需要的帮助（具体请求） -> 建议方案

---

## 4. 蜂群攻关

**触发**：阻塞影响关键路径 / 影响 >= 3 人 / 常规方法 4 小时无解

| 阶段 | 动作 | 时间盒 |
|------|------|-------|
| 召集 | 通知相关人员，明确问题 | 5 分钟 |
| 诊断 | 集体分析，共享观察 | 15 分钟 |
| 方案 | 讨论 2-3 个方向 | 10 分钟 |
| 执行 | 选定方向，分工执行 | 视复杂度 |
| 验证 | 确认解决，记录教训 | 10 分钟 |

纪律：不讨论"谁的错"；1-2 小时无进展就升级；结束后 5 分钟复盘预防策略。

---

## 5. 依赖管理

| 策略 | 适用场景 | 操作 |
|------|---------|------|
| 前置沟通 | 所有已知依赖 | 迭代规划时确认交付时间 |
| Mock/Stub | 等待 API/服务 | 基于契约先行开发 |
| 缓冲计划 | 高风险依赖 | 预留缓冲时间 |
| 备选方案 | 交付不确定 | 准备 Plan B |
| SoS | 多团队协作 | 每日/每周跨团队同步 |

依赖 SLA：与依赖方约定响应时间，违约时自动触发升级。

---

## 6. 持续改进

每个迭代结束回顾阻塞：数量、平均解决时间、趋势、重复出现的阻塞是否已有系统性方案。

预防措施：技术阻塞（架构决策前置、技术 Spike）、人员阻塞（知识共享、结对编程）、依赖阻塞（依赖前置识别、契约优先）、流程阻塞（简化审批、自动化合规检查）。
