## Step 1: 确定审查范围

如果 `$ARGUMENTS` 非空，以此作为审查目标的初始输入。

向用户确认审查范围：

- **目标**：审查哪些组件/页面？（文件路径或目录）
- **深度**：快速扫描（仅顶层结构）还是深度审查（逐文件分析）？
- **关注点**：是否有特定关注点？（如"状态管理混乱"、"组件太大"、"Props 透传过多"）

使用 Read 工具和 Glob 工具扫描目标目录，列出组件清单和文件结构树。

**⏸️ 等待用户确认后继续。**

## Step 2: 组件结构分析

逐个读取目标组件代码，从以下维度分析：

#### 2a. 组件层级与职责

- 组件是否遵循 Atomic Design 层级？（Atom / Molecule / Organism）
- 每个组件是否单一职责？超过 200 行的组件是否需要拆分？
- 展示逻辑（UI）和业务逻辑是否分离？
- 是否存在"上帝组件"（God Component）——承担了太多职责？

#### 2b. Props 接口设计

- Props 是否有 TypeScript 类型定义？
- 是否存在 Props 透传（Prop Drilling）超过 2 层？
- 是否有未使用的 Props？
- 默认值是否合理？必选/可选区分是否清晰？
- 回调函数的命名是否一致？（on + 动词，如 `onChange`、`onSubmit`）

#### 2c. 状态管理

- 状态是否就近管理？有无不必要的状态提升？
- 是否存在派生状态未用 useMemo / computed 处理？
- 全局状态是否只存放真正需要跨组件共享的数据？
- 服务端状态（API 数据）和客户端状态（UI 状态）是否分离？

#### 2d. 可复用性与组合

- 是否有重复的组件逻辑可以抽取为 Hook / Composable？
- 组件是否支持 children / slots 进行内容组合？
- 是否存在硬编码的业务逻辑导致组件无法复用？

**每个维度分析完后向用户展示发现，使用表格汇总问题。**

## Step 3: 可访问性快检

快速检查组件的可访问性：

- 语义化 HTML：是否使用了正确的标签？（`<button>` 而非 `<div onClick>`）
- ARIA 属性：交互组件是否有适当的 `role`、`aria-label`？
- 键盘导航：焦点管理是否正确？Tab 顺序是否合理？
- 颜色对比度：是否依赖颜色传达信息？

## Step 4: 问题汇总与分级

将所有发现整理为分级报告：

```markdown
## 组件架构审查报告

### Critical（必须修复）
- [ ] {文件路径}:{行号} — {问题描述} — {修复建议}

### Warning（建议修复）
- [ ] {文件路径}:{行号} — {问题描述} — {修复建议}

### Info（可选优化）
- [ ] {文件路径}:{行号} — {问题描述} — {优化建议}

### 亮点
- {做得好的地方，给予正向反馈}
```

向用户展示报告，逐条确认是否同意。
