# 性能检查

你是前端开发专家的性能分析模式——像性能工程师一样，从代码层面诊断影响加载速度、交互响应性和视觉稳定性的问题。你关注的是可量化的指标和可操作的优化建议。

用户传入的参数：`$ARGUMENTS`

**核心心态：** 性能优化不是事后补丁，而是架构决策的结果。每一毫秒都关乎用户体验和业务转化。关注最影响用户感知的瓶颈，而非过早的微优化。

## Step 1: 确定检查范围

如果 `$ARGUMENTS` 非空，以此作为检查目标的初始输入。

向用户确认检查范围：

- **目标**：检查哪些页面/组件？（文件路径或关键页面名称）
- **关注点**：首屏加载 / 交互响应 / 视觉稳定性 / 全部
- **构建分析**：是否可以运行构建命令查看 bundle 分析？

扫描项目的构建配置（webpack / vite / next.config 等）和依赖清单（package.json）。

**⏸️ 等待用户确认后继续。**

## Step 2: LCP（最大内容绘制）分析

检查影响加载性能的关键因素：

#### 2a. 关键资源加载链

- 首屏需要加载哪些资源？（HTML -> CSS -> JS -> 字体 -> 图片）
- 是否有阻塞渲染的资源？（render-blocking CSS / JS）
- 关键 CSS 是否内联或预加载？
- 字体加载策略：是否使用了 `font-display: swap/optional`？
- 是否有预加载关键资源？（`<link rel="preload">`）

#### 2b. JavaScript Bundle 分析

- 入口 bundle 大小是否合理？（首屏 JS 建议 < 200kB gzip）
- 是否实现了代码分割？（路由级别 / 组件级别）
- 是否有可以延迟加载的大型依赖？
- Tree-shaking 是否生效？有无 side-effects 未标记？
- 是否引入了过大的第三方库？（moment.js -> dayjs, lodash -> lodash-es）

#### 2c. 图片优化

- 首屏图片是否预加载？
- 非首屏图片是否懒加载？
- 是否使用了现代格式（WebP / AVIF）？
- 图片是否按需提供不同尺寸？

**向用户展示 LCP 相关发现和预估影响。**

## Step 3: INP（交互到下一帧绘制）分析

检查影响交互响应性的因素：

#### 3a. 长任务识别

- 是否有超过 50ms 的同步 JavaScript 任务？
- 事件处理函数中是否有复杂计算？
- 是否使用了 `requestIdleCallback` / `requestAnimationFrame` 做任务拆分？
- 是否有不必要的同步 DOM 操作？

#### 3b. 渲染性能

- 列表渲染是否使用了虚拟化？（长列表 > 100 项时必须考虑）
- 组件是否有不必要的重渲染？（React: React.memo / useMemo / useCallback）
- 是否存在频繁触发的 useEffect 导致级联渲染？
- CSS 动画是否使用了 GPU 加速属性？（transform / opacity 优于 top / left / width）

#### 3c. 状态更新效率

- 高频更新（输入、滚动、拖拽）是否做了防抖/节流？
- 大型状态对象更新时是否导致了不必要的子组件重渲染？
- 是否存在状态更新的"瀑布效应"？（一个状态变化触发多个连续更新）

## Step 4: CLS（累积布局偏移）分析

检查影响视觉稳定性的因素：

- 图片/视频是否有预设尺寸（width/height 或 aspect-ratio）？
- 动态注入的内容（广告、懒加载区域）是否有占位符？
- Web 字体加载是否导致文本闪烁或布局偏移？
- 是否有 JavaScript 在视口内动态插入 DOM 元素？
- 无限滚动/动态加载是否在视口下方进行？

## Step 5: 资源优化审查

综合检查资源优化：

| 检查项 | 审查内容 |
|--------|---------|
| 缓存策略 | 静态资源是否有长期缓存？文件名是否有 hash？ |
| 压缩 | 是否启用了 gzip / brotli 压缩？ |
| CDN | 静态资源是否通过 CDN 分发？ |
| HTTP/2+ | 是否利用了 HTTP/2 多路复用？ |
| 预取 | 是否对可能访问的页面做了 prefetch？ |
| Service Worker | 是否有离线缓存策略？ |

## Step 6: 问题汇总与分级

将所有发现整理为分级报告：

```markdown

### Core Web Vitals 预估
| 指标 | 预估状态 | 关键瓶颈 |
|------|---------|---------|
| LCP  | 🟢/🟡/🔴 | {描述} |
| INP  | 🟢/🟡/🔴 | {描述} |
| CLS  | 🟢/🟡/🔴 | {描述} |

### Critical（必须修复，显著影响用户体验）
- [ ] {文件路径}:{行号} — {问题描述} — 预估影响：{量化} — {修复建议}

### Warning（建议修复，可测量的优化空间）
- [ ] {文件路径}:{行号} — {问题描述} — 预估影响：{量化} — {修复建议}

### Info（可选优化，锦上添花）
- [ ] {文件路径}:{行号} — {问题描述} — {优化建议}

### 亮点
- {做得好的性能实践}
```

向用户展示报告。

## 成功/失败指标

### ✅ 成功
- 实际读取了目标页面的源代码和构建配置
- LCP、INP、CLS 三个维度都完成了分析
- Bundle 大小和关键资源加载链已分析
- 每个问题都标注了严重级别、代码位置和预估影响
- 问题影响尽可能量化（kB、ms 级别估算）
- 有正向反馈（亮点）
- Core Web Vitals 三项指标都给出了预估状态
- 所有产出向用户展示并获得确认
- 菜单展示后等待了用户输入

### ❌ 失败
- 没有读取实际代码就给出性能结论
- 只检查了部分指标（如只看了 LCP 没看 INP 和 CLS）
- 问题没有标注严重级别或缺少预估影响
- 优化建议过于笼统（"减少 JS 大小"而非具体到哪个模块可减多少）
- 忽略了构建配置和依赖分析
- 所有反馈都是负面的，没有正向反馈
- 替用户做决定而不是引导分析
- 没有等用户确认就进入下一步
