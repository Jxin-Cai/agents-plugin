# 辅助技术测试原则

本文档定义了辅助技术测试阶段必须遵循的原则。用这些原则确保测试的真实性和全面性。

---

## 1. 屏幕阅读器测试方法

### 核心理念

屏幕阅读器将视觉界面转化为线性的语音/盲文输出。测试时必须理解这种"线性化"如何改变用户体验：
- 视觉布局中的空间关系（左侧导航、右侧内容）在屏幕阅读器中消失
- 用户只能感知当前焦点位置的内容，无法"扫视"整个页面
- 上下文切换（模态框、页面跳转）如果无语音提示，用户会迷失

### 测试操作基础

#### VoiceOver (macOS)
- 开启/关闭：`Cmd + F5`
- 朗读当前项：`VO + A`（VO = Ctrl + Option）
- 下一项：`VO + 右箭头`
- 激活链接/按钮：`VO + Space`
- 标题导航：`VO + Cmd + H`
- 表单控件：`VO + Cmd + J`
- 路标（Landmark）：`VO + Cmd + L`

#### NVDA (Windows)
- 开启/关闭：`Ctrl + Alt + N`
- 停止朗读：`Ctrl`
- 下一项：`↓`
- 标题导航：`H`
- 链接导航：`K`
- 表单模式切换：`Enter`（进入）/ `Esc`（退出）
- 元素列表：`NVDA + F7`

### 关键测试维度

1. **信息获取**：用户能否获取页面上的所有关键信息？
2. **任务完成**：用户能否完成核心业务流程？
3. **效率**：是否需要过多步骤才能完成简单任务？
4. **错误恢复**：出错时用户能否知道错在哪、如何修复？
5. **方向感**：用户在任何时刻是否知道自己在哪里？

## 2. 键盘导航测试方法

### 测试标准快捷键

| 按键 | 功能 | 检查点 |
|------|------|--------|
| `Tab` | 移到下一个可交互元素 | 顺序是否符合逻辑？是否有遗漏？ |
| `Shift + Tab` | 移到上一个可交互元素 | 能否回退？ |
| `Enter` | 激活链接/按钮 | 行为是否与鼠标点击一致？ |
| `Space` | 激活按钮/复选框 | 与 Enter 是否都能用？ |
| `Esc` | 关闭弹窗/下拉 | 焦点回到触发元素？ |
| `Arrow Keys` | 菜单项/单选/标签切换 | 组内导航是否流畅？ |
| `Home/End` | 移到首/末项 | 长列表中是否支持？ |

### 焦点管理规则

- **模态框打开**：焦点必须移入模态框内，Tab 循环限制在模态框内
- **模态框关闭**：焦点必须返回到触发元素
- **页面路由切换（SPA）**：焦点必须移到新内容的主区域或页面标题
- **内容动态加载**：加载完成后焦点应移到新内容或保持在触发元素
- **删除操作**：被删除元素后焦点应移到合理的下一项

### 常见键盘陷阱

- 富文本编辑器内 Tab 被用于缩进，无法 Tab 出去
- iframe 内容捕获焦点
- 自定义下拉菜单只响应鼠标
- 日期选择器无法用键盘操作
- 拖放排序功能无键盘替代

## 3. 视觉辅助测试方法

### 放大测试

**WCAG 1.4.4 要求**：文本可放大至 200% 而不丢失内容或功能。

测试步骤：
1. 浏览器缩放至 200%（`Ctrl/Cmd + +`）
2. 检查所有页面内容是否通过响应式重排适配
3. 确认无水平滚动条（单维度滚动）
4. 确认文字、按钮、表单仍然可读可操作
5. 确认弹出层/工具提示没有被截断

**WCAG 1.4.10 要求**（AA）：内容可在 320px 宽度重排而不需水平滚动（等效于 400% 桌面缩放）。

### 颜色与对比度

- **正文文本**：对比度 >= 4.5:1（WCAG 1.4.3 AA）
- **大文本**（18pt 或 14pt 粗体）：对比度 >= 3:1
- **UI 组件和图形**：对比度 >= 3:1（WCAG 1.4.11 AA）
- **非文本对比度**：按钮边框、输入框边框、图标需与背景有足够对比
- **焦点指示器**：焦点轮廓与周围内容的对比度 >= 3:1

### 文本间距调整（WCAG 1.4.12）

注入以下 CSS 后，内容不应丢失或重叠：

```css
* {
  line-height: 1.5 !important;
  letter-spacing: 0.12em !important;
  word-spacing: 0.16em !important;
}
p {
  margin-bottom: 2em !important;
}
```

## 4. 辅助技术兼容性矩阵

### 推荐测试优先级

根据 WebAIM 屏幕阅读器调查和市场份额数据，推荐以下测试优先级：

**Tier 1（必测）：**
- NVDA + Firefox（Windows）— 免费且使用率最高
- VoiceOver + Safari（macOS/iOS）— Apple 生态的唯一选择
- 键盘导航（无 AT）— 覆盖运动障碍用户

**Tier 2（推荐）：**
- JAWS + Chrome（Windows）— 企业环境最常用
- TalkBack + Chrome（Android）— Android 用户覆盖
- 浏览器缩放 200%（桌面）— 低视力用户

**Tier 3（可选）：**
- 高对比度模式（Windows）
- Narrator + Edge（Windows）
- 语音控制（Voice Control / Dragon）

### 已知兼容性差异

不同屏幕阅读器对同一 HTML/ARIA 的解读可能不同：
- `aria-label` 在 VoiceOver 和 NVDA 中的朗读优先级不同
- `role="application"` 在 JAWS 中会改变键盘行为
- `aria-live="polite"` 的延迟时间在不同 AT 中不一致
- SVG 的无障碍支持在不同 AT 中差异较大

## 5. 任务流测试法

### 核心理念

辅助技术测试不应只检查孤立的页面元素，而应模拟真实用户的完整任务流程。一个按钮可能单独测试通过，但在真实使用场景中因为焦点管理问题导致用户无法到达它。

### 任务流设计原则

1. **从用户目标出发**：用户想完成什么？（注册、购买、搜索）
2. **覆盖关键路径**：核心业务流程必须全部覆盖
3. **包含错误路径**：提交无效表单、操作失败等场景
4. **限制步骤数量**：每个任务流 3-10 步，太长则拆分
5. **记录每一步**：操作、期望结果、实际结果、是否通过

### 评分标准

对每个任务流，按以下标准评分：

| 等级 | 含义 |
|------|------|
| ✅ 通过 | 用户可以独立、高效地完成任务 |
| ⚠️ 困难 | 用户可以完成但需要额外努力或困惑 |
| ❌ 阻断 | 用户无法完成任务 |
