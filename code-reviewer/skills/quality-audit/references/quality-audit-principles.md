# 质量审计原则

> 基于 Google Engineering Practices、Clean Code、SonarQube 质量模型

---

## 1. 代码质量六维度模型

### 可靠性（Reliability）

- 错误处理完整性：所有可失败操作有处理？异常是否被"吞掉"？
- 空值安全：空指针/undefined 风险？可选值正确处理？
- 边界条件：整数溢出、数组越界、除零、空集合？
- 并发安全：共享状态竞态条件？锁粒度？
- 资源泄漏：连接、句柄、内存是否正确释放？

### 可维护性（Maintainability）

- 命名质量：变量/函数/类名自解释？有误导性命名？
- 函数长度：>30 行需关注，>50 行应拆分
- 参数数量：>3 个需关注
- 注释质量：解释"为什么"而非"是什么"？有过时注释？

### 复杂度（Complexity）

- 圈复杂度：单函数 >10 需关注，>20 必须重构
- 认知复杂度：嵌套 >3 层需关注
- 继承深度：>3 层需警惕
- 过度抽象：不必要的接口/工厂/策略模式？

### 重复度（Duplication）

- 克隆代码：连续 6 行以上相同/相似代码
- 结构重复：不同位置相同逻辑模式
- 跨文件重复：多文件相似实现

### 耦合与内聚（Coupling & Cohesion）

- 传入耦合 Ca：多少模块依赖此模块？（过高 = 修改影响大）
- 传出耦合 Ce：依赖多少其他模块？（过高 = 依赖过多）
- 不稳定性 I = Ce/(Ca+Ce)：趋近 1 = 不稳定，趋近 0 = 稳定
- 循环依赖：模块间是否有循环？

### 可测试性（Testability）

- 测试覆盖：关键路径有测试？分支覆盖充分？
- 测试质量：测试是否真的验证行为？有无"假"测试？
- 可测试设计：依赖可注入？硬编码依赖？

## 2. 质量等级评定

| 等级 | 含义 | 行动 |
|------|------|------|
| **A** | 优秀，符合最佳实践 | 保持 |
| **B** | 良好，小的改进空间 | 可选改进 |
| **C** | 合格，存在明显问题 | 应当改进 |
| **D** | 较差，影响日常开发 | 必须改进 |
| **E** | 严重，几乎无法维护 | 需大规模重构 |

综合评级取各维度最低等级。任一维度 D/E，综合评级不得高于 C。

## 3. 代码坏味道速查表

| 严重度 | 坏味道 | 阈值 |
|--------|--------|------|
| **Blocker** | 上帝类 | 单文件 >500 行 |
| **Blocker** | 深度嵌套 | >4 层 if/for/while/try |
| **Blocker** | 魔法数字/字符串 | 硬编码散布 |
| **Blocker** | 重复代码块 | 连续 >10 行克隆 |
| **Major** | 长函数 | >50 行 |
| **Major** | 长参数列表 | >4 个参数 |
| **Major** | Feature Envy | 大量使用其他类数据 |
| **Major** | 过时注释 | 注释与代码不一致 |
| **Minor** | 不必要注释 | 重复代码内容 |
| **Minor** | 命名风格不一致 | 混用不同约定 |
| **Minor** | TODO/FIXME 堆积 | 大量未处理待办 |

## 4. 度量指标参考值

| 指标 | 良好 | 需关注 | 需行动 |
|------|------|--------|--------|
| 圈复杂度（函数级） | ≤10 | 11-20 | >20 |
| 认知复杂度（函数级） | ≤15 | 16-25 | >25 |
| 函数行数 | ≤30 | 31-50 | >50 |
| 文件行数 | ≤300 | 301-500 | >500 |
| 函数参数数 | ≤3 | 4-5 | >5 |
| 嵌套深度 | ≤3 | 4 | >4 |
| 代码重复率 | <3% | 3-5% | >5% |
