# 重构建议原则

> 基于 Martin Fowler《重构》、Clean Code、refactoring.guru

---

## 1. 重构决策框架

每个重构建议必须评估三个维度：

| 维度 | 评估要点 |
|------|---------|
| **必要性 Why** | 是否在热点区域？当前状态是否导致 Bug/性能/安全风险？新成员理解需多久？稳定不改的代码不必重构 |
| **收益 What** | 可读性提升？可维护性提升？可测试性提升？性能提升（可读性优先）？ |
| **风险 Risk** | 回归风险和测试覆盖？影响范围（文件/模块数）？接口兼容性？能否增量进行？ |

---

## 2. 重构模式目录

### 简化函数类

| 手法 | 适用场景 | 要点 |
|------|---------|------|
| 提取函数 | 函数过长、代码块有独立含义 | 命名表达意图 |
| 内联函数 | 函数体与名字一样清晰 | 消除不必要间接层 |
| 引入解释性变量 | 复杂表达式难理解 | 命名良好的变量替换子表达式 |
| 分解条件表达式 | if-else 链过长/条件过复杂 | 条件和分支体提取为独立函数 |
| 卫语句取代嵌套 | 嵌套层次过深 | 提前返回减少嵌套 |

### 简化数据类

| 手法 | 适用场景 | 要点 |
|------|---------|------|
| 引入参数对象 | 多参数总一起出现 | 封装为对象 |
| 对象取代数据泥团 | 多字段总一起使用 | 提取为值对象 |
| 常量取代魔法数字 | 硬编码数字/字符串 | 提取为命名常量 |

### 简化对象关系类

| 手法 | 适用场景 | 要点 |
|------|---------|------|
| 搬移方法 | 方法更多使用其他类数据 | 移到数据所在类 |
| 提取类 | 类承担过多职责 | 拆分为多个类 |
| 多态取代条件 | 基于类型的 switch/if | 继承或策略模式 |
| 引入空对象 | 大量空值检查 | 空对象模式替代 null 检查 |

### 架构级

| 手法 | 适用场景 | 要点 |
|------|---------|------|
| 分层拆分 | 业务与基础设施混合 | 按职责拆分层次 |
| 引入门面 | 需与多子系统交互 | 统一简化接口 |
| 消除循环依赖 | 模块循环依赖 | 引入接口/中介者 |
| 绞杀者模式 | 渐进替换遗留系统 | 新功能新架构，旧功能逐步迁移 |

---

## 3. 安全网评估

每个重构建议必须附带：

| 评估项 | 要点 |
|--------|------|
| 测试覆盖 | 目标代码有自动化测试？覆盖要重构的行为？需新增/修改测试？ |
| 增量策略 | 可分步执行？每步可独立验证？可用 Feature Flag？回滚方案？ |
| 验证方法 | 如何验证行为不变？性能影响？接口兼容性？ |

---

## 4. 优先级矩阵

| | 高业务影响 | 低业务影响 |
|---|---|---|
| **低风险** | **立即做** — 收益高风险低 | **顺便做** — 改文件时顺带 |
| **高风险** | **计划做** — 需专项任务 + 充分测试 | **记录** — 技术债，暂不行动 |

---

## 5. 反模式

| 反模式 | 正确做法 |
|--------|---------|
| 大爆炸重构 | 增量进行 |
| 重构无测试代码 | 先补充测试 |
| 紧迫交付期重构 | 在非关键路径进行 |
| 追求完美 | 够用就好 |
| 重构 + 加功能混合 | 分开提交 |
| 无度量重构 | 重构前后对比数据 |
