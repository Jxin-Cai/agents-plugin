# 重构建议原则

本文档定义了重构建议阶段必须遵循的原则。基于 Martin Fowler《重构》、Robert C. Martin《Clean Code》、refactoring.guru 重构目录和行业最佳实践。

---

## 1. 重构决策框架

在提出重构建议前，必须评估三个维度：

### 必要性（Why）
- **业务影响**：这段代码是否在频繁修改的热点区域？
- **风险程度**：当前状态是否会导致 Bug、性能问题或安全漏洞？
- **理解负担**：新成员理解这段代码需要多长时间？
- **决策依据**：如果代码稳定且不需要修改，即使不完美也不必重构

### 收益（What）
- **可读性提升**：重构后代码是否更容易理解？
- **可维护性提升**：重构后修改和扩展是否更容易？
- **可测试性提升**：重构后是否更容易编写和维护测试？
- **性能提升**：重构后是否消除了性能瓶颈？（注意：可读性优先于性能优化）

### 风险（Risk）
- **回归风险**：重构是否可能引入新 Bug？有没有测试覆盖？
- **影响范围**：重构涉及多少文件？多少模块？
- **依赖影响**：重构是否会破坏其他模块的接口？
- **缓解措施**：是否可以增量重构？是否有足够的测试保护？

## 2. 重构模式目录

按问题类型分类的常用重构手法：

### 简化函数类

| 重构手法 | 适用场景 | 操作要点 |
|---------|---------|---------|
| **提取函数（Extract Method）** | 函数过长、代码块有独立含义 | 抽取代码块为独立函数，命名表达意图 |
| **内联函数（Inline Method）** | 函数体与名字一样清晰 | 用函数体替换调用处，消除不必要的间接层 |
| **引入解释性变量（Introduce Explaining Variable）** | 复杂表达式难以理解 | 用命名良好的变量替换子表达式 |
| **分解条件表达式（Decompose Conditional）** | if-else 链过长或条件过复杂 | 将条件判断和分支体提取为独立函数 |
| **合并条件表达式（Consolidate Conditional）** | 多个条件产生相同结果 | 合并为单个条件表达式 |
| **以卫语句取代嵌套（Replace Nested Conditionals with Guard Clauses）** | 嵌套层次过深 | 用提前返回减少嵌套 |

### 简化数据类

| 重构手法 | 适用场景 | 操作要点 |
|---------|---------|---------|
| **引入参数对象（Introduce Parameter Object）** | 多个参数总是一起出现 | 将相关参数封装为对象 |
| **以对象取代数据泥团（Replace Data Clumps with Object）** | 多个字段总是一起使用 | 提取为值对象 |
| **以常量取代魔法数字（Replace Magic Number with Constant）** | 代码中有硬编码的数字/字符串 | 提取为命名常量 |
| **封装字段（Encapsulate Field）** | 公开字段直接被外部访问 | 通过 getter/setter 或方法封装 |

### 简化对象关系类

| 重构手法 | 适用场景 | 操作要点 |
|---------|---------|---------|
| **搬移方法（Move Method）** | 方法更多使用其他类的数据 | 移动到数据所在的类 |
| **提取类（Extract Class）** | 类承担了过多职责 | 拆分为两个或更多类 |
| **内联类（Inline Class）** | 类太小，没有独立存在的价值 | 合并到使用它的类中 |
| **以多态取代条件（Replace Conditional with Polymorphism）** | 基于类型的 switch/if 分支 | 用继承或策略模式替换 |
| **引入空对象（Introduce Null Object）** | 大量空值检查分散在代码中 | 用空对象模式替代 null 检查 |

### 架构级重构

| 重构手法 | 适用场景 | 操作要点 |
|---------|---------|---------|
| **分层拆分（Extract Layer）** | 业务逻辑与基础设施代码混合 | 按职责拆分为不同层次 |
| **引入门面（Introduce Facade）** | 客户端需要与多个子系统交互 | 提供简化的统一接口 |
| **消除循环依赖（Break Dependency Cycle）** | 模块之间存在循环依赖 | 引入接口或中介者打破循环 |
| **陌生人模式（Strangler Fig Pattern）** | 需要渐进式替换遗留系统 | 新功能用新架构，旧功能逐步迁移 |

## 3. 重构安全网

每个重构建议必须附带安全网评估：

### 测试覆盖
- 目标代码是否有自动化测试？
- 测试是否覆盖了要重构的行为？
- 重构后是否需要新增/修改测试？

### 增量策略
- 是否可以分步执行？（每步可独立验证）
- 是否可以用 Feature Flag 保护？
- 回滚方案是什么？

### 验证方法
- 重构后如何验证行为不变？
- 性能是否会受影响？如何度量？
- 接口兼容性如何保证？

## 4. 重构优先级矩阵

| | 高业务影响 | 低业务影响 |
|---|---|---|
| **低风险** | **立即做** — 收益高、风险低 | **顺便做** — 修改该文件时顺带重构 |
| **高风险** | **计划做** — 需要专项任务和充分测试 | **记录** — 记录为技术债，暂不行动 |

---

## 5. 重构反模式（不要这样做）

- **大爆炸重构**：一次性重构整个系统 → 应该增量进行
- **重构没有测试的代码**：没有安全网的重构 → 先补充测试
- **在紧迫的交付周期中重构**：重构需要时间和空间 → 在非关键路径上进行
- **追求完美**：无限优化已经足够好的代码 → 够用就好
- **重构的同时加新功能**：两件事混在一起 → 分开提交
- **没有度量的重构**：不知道改进了多少 → 重构前后要有对比数据
