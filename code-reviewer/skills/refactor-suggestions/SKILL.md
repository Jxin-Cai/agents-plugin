# 重构建议

以手艺人视角，识别代码粗糙之处并提供精确打磨方案。在收益和风险之间找最佳平衡。

用户传入的参数：`$ARGUMENTS`

---

## Step 0: 前置条件

1. 确定工作目录：检查 `_code-review/` 下最近的日期目录，若无则创建
2. 存在 `meta/review-state.md` 时 Read 并确认当前阶段
3. Read `context/scope.md`（如存在）获取审查范围
4. 加载已有安全审查、质量审计产出（如存在）
5. 确定目标代码，重点关注质量审计中标记的问题代码

---

## Step 1: 坏味道识别与分类

Read `references/refactor-suggestions-principles.md`

1. 从质量审计产出入手（如存在）——标记的 Blocker 和 Major 问题
2. 补充扫描——检查遗漏的坏味道
3. 每个坏味道记录：类型名称 / 位置（文件:行号范围）/ 度量数值 / 影响说明

用 `AskUserQuestion` 展示坏味道清单（按严重程度排序），确认范围。

---

## Step 2: 重构方案设计

针对每个坏味道设计方案：

| 字段 | 要求 |
|------|------|
| 重构手法 | 从 principles 的模式目录中匹配 |
| 操作步骤 | 分步骤描述，具体到代码级别 |
| 预期效果 | 重构后代码样貌（可含伪代码） |
| 前置条件 | 执行前需要先做什么 |
| 必要性 | 为什么要做 |
| 收益 | 做了改善什么 |
| 风险 | 可能引入什么问题 |

每设计完 2-3 个方案后展示，收集用户反馈。

---

## Step 3: 安全网评估

对每个方案评估：

| 评估项 | 内容 |
|--------|------|
| 测试覆盖 | 有自动化测试？覆盖率？ |
| 增量策略 | 能否分步执行？每步可独立验证？ |
| 回滚方案 | 失败如何回退？ |
| 验证方法 | 如何验证行为不变？ |

无测试覆盖的代码，先建议补充测试再重构。

---

## Step 4: 优先级排序

按 principles 的优先级矩阵分四类：

1. **立即做**（高业务影响 + 低风险）——列具体操作步骤
2. **顺便做**（低业务影响 + 低风险）——标注"改文件时顺带"
3. **计划做**（高业务影响 + 高风险）——列前置准备
4. **记录**（低业务影响 + 高风险）——技术债，暂不行动

---

## Step 5: 生成重构报告

保存到 `{工作目录}/refactoring/refactor-report-{日期}.md`。

更新 `meta/review-state.md`（重构建议阶段 = done）。

---

## Step 6: 门控确认

使用 `AskUserQuestion` 展示：

> 共 [N] 个重构建议——立即做 [a]、顺便做 [b]、计划做 [c]、记录 [d]。

选项：生成综合审查报告 / 开始执行重构 / 深入某个方案 / 结束审查

---

<IMPORTANT>
## 质量硬门控

- 绝不在没有阅读代码的情况下提出重构建议
- 不建议重构稳定且不需要修改的代码
- 每个建议必须有具体手法、步骤和代码示例，禁止"需要重构"的空泛描述
- 无测试覆盖的代码必须先建议补测试，再建议重构
- 不到用户确认，不进入下一步
- 不确定时声明不确定，禁止猜测影响范围
</IMPORTANT>
