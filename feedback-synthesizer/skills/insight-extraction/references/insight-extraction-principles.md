# 洞察提取原则

本文档定义了洞察提取阶段必须遵循的原则。用这些原则确保洞察可操作、有数据支撑、指向明确的产品决策。

---

## 1. 洞察公式

一条合格的洞察必须同时包含三个要素，缺一不可：

### 公式：洞察 = 数据发现 + 业务解读 + 行动建议

- **数据发现**（What）：客观描述数据中的规律或异常。必须引用具体数据——反馈数量、比例、趋势、来源
- **业务解读**（So What）：解释这个数据发现对用户、产品或业务意味着什么。连接数据与业务价值
- **行动建议**（Now What）：基于解读，提出具体可执行的改进方向。必须具体到可以分配给某个团队执行

### 质量检验
| 要素 | 合格示例 | 不合格示例 |
|------|---------|-----------|
| 数据发现 | "65% 的负面反馈集中在结账流程，主要抱怨'步骤太多'（42 条）和'加载慢'（28 条）" | "用户对结账不满意" |
| 业务解读 | "结账流程的高摩擦可能是购物车放弃率从 30% 上升到 45% 的主要原因" | "体验不好会影响转化" |
| 行动建议 | "将结账从 5 步缩减为 3 步，合并地址和支付信息页，预期降低放弃率 10-15%" | "优化结账流程" |

## 2. 影响-费力矩阵（Impact-Effort Matrix）

所有行动建议必须经过影响-费力评估，避免"什么都重要"的优先级瘫痪：

### 四象限定义
```
高影响 ┌──────────┬──────────┐
       │ 🟢 速赢   │ 🔵 战略   │
       │ 立即执行  │ 规划排期  │
       ├──────────┼──────────┤
       │ 🟡 填充   │ ⚪ 暂缓   │
       │ 顺便做   │ 不投入   │
低影响 └──────────┴──────────┘
       低费力      高费力
```

### 评估维度
**影响评估**（用户/业务价值）：
- 影响多少用户？（覆盖面）
- 对核心指标（留存/满意度/收入）的影响有多大？（深度）
- 不处理会恶化吗？（紧迫性）

**费力评估**（实现成本）：
- 需要多少开发资源？（人力）
- 技术实现复杂度？（难度）
- 跨团队协作程度？（协调成本）
- 有没有风险或不确定性？（风险）

### 评估原则
- 影响和费力的评估必须与用户确认，不可自行判断
- 倾向保守评估影响、诚实评估费力，避免过度乐观
- "速赢"象限的行动不应超过总数的 1/3（如果都是速赢，说明评估标准太松）

## 3. 根因分析方法

表面反馈往往只是症状，需要深挖到结构性根因：

### 5 Why 法
- 对每个重要的负面主题，连续追问"为什么"直到触及根因
- 通常 3-5 层追问即可到达根因
- 根因通常是流程缺陷、架构限制、资源不足或认知盲区

### 根因分类
| 根因类型 | 特征 | 示例 |
|---------|------|------|
| 产品设计缺陷 | 功能逻辑或交互设计有问题 | 信息架构混乱导致用户找不到功能 |
| 技术限制 | 当前技术架构无法满足需求 | 单体架构导致性能瓶颈 |
| 流程缺陷 | 用户完成任务的路径不合理 | 结账流程步骤过多 |
| 资源不足 | 缺乏投入导致体验劣化 | 搜索算法长期未优化 |
| 认知盲区 | 团队未意识到某个问题 | 从未测试过弱网环境 |
| 优先级错位 | 在低价值事项上投入过多 | 过度优化已经很好的功能 |

### 根因验证
- 根因分析产出的是假设，不是定论
- 必须向用户标明："这是基于反馈数据的推断"
- 列出验证根因所需的额外数据或实验

## 4. 机会解决方案树（Opportunity Solution Tree）

使用 Teresa Torres 的机会解决方案树框架，将洞察转化为结构化的行动路线：

### 框架结构
```
期望成果（Desired Outcome）
├── 机会 1（Opportunity）
│   ├── 解决方案 A
│   └── 解决方案 B
├── 机会 2
│   ├── 解决方案 C
│   └── 解决方案 D
└── 机会 3
    └── 解决方案 E
```

### 应用规则
- **期望成果**：从分析目的出发，明确要改善什么指标（如"将 NPS 从 30 提升到 50"）
- **机会**：从洞察中识别的改进机会（如"减少结账摩擦"）
- **解决方案**：每个机会至少列出 2 个可能的解决方案，避免锁定在第一个想到的方案
- **假设验证**：每个解决方案标注核心假设和最小验证实验

## 5. 决策建议框架

最终的决策建议必须清晰分层，便于不同层级的决策者使用：

### 分层结构
- **执行摘要**（给高管，30 秒能看完）：3 句话概括核心发现和建议
- **立即行动项**（给执行团队，本周启动）：速赢项，明确负责人和预期
- **短期规划项**（给产品经理，1-3 个月）：战略项目，需要评估和排期
- **持续监控项**（给数据团队）：需要持续跟踪的指标和趋势
- **开放问题**（给研究团队）：需要进一步调研的未解问题

### 建议质量标准
- 每条建议必须可分配（谁来做？）
- 每条建议必须可衡量（做完怎么知道成功？）
- 每条建议必须有时间预期（多久能看到效果？）
- 避免"万金油"建议（如"提升用户体验"——太笼统，无法执行）

---

## 6. 反洞察陷阱

以下是洞察提取中常见的误判模式，必须警惕：

### 常见陷阱
| 陷阱 | 描述 | 应对 |
|------|------|------|
| 确认偏误 | 只关注支持预设结论的数据 | 主动寻找反面证据 |
| 频率偏误 | 高频反馈 = 高优先级 | 同时考虑影响深度和用户价值 |
| 近因偏误 | 过度关注最近的反馈 | 区分趋势和波动 |
| 生存者偏差 | 只分析活跃用户的声音 | 关注沉默用户和流失用户 |
| 过度拟合 | 从少量数据中提取过多结论 | 标明样本量和置信度 |
| 伪相关 | 将相关性当作因果性 | 标明是假设，需要验证 |
