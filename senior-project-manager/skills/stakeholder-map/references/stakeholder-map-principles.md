# 干系人管理原则

本文档定义了干系人识别与管理阶段必须遵循的原则。基于 PMBOK 第七版干系人绩效域和 Mendelow 权力-利益矩阵方法论。

---

## 1. Mendelow 权力-利益矩阵

由 Aubrey Mendelow（1991）提出的干系人分类框架，是项目管理中最广泛使用的干系人分析工具。

### 四象限策略

#### 密切管理（Manage Closely）— 高权力 + 高利益
- 这些人是项目成败的关键决定者
- **沟通策略**：高频、深度、双向沟通
- **参与方式**：邀请参与关键决策，定期一对一汇报
- **风险**：如果他们不满意，项目可能被叫停或方向大改
- **典型角色**：项目发起人、产品负责人、关键业务方负责人

#### 保持满意（Keep Satisfied）— 高权力 + 低利益
- 这些人有能力影响项目但目前不太关注
- **沟通策略**：定期简报，不过度打扰，关键节点主动汇报
- **参与方式**：里程碑汇报，问题升级通道
- **风险**：突然关注时如果发现问题，可能强力干预
- **典型角色**：高管、CTO、其他部门总监

#### 保持知情（Keep Informed）— 低权力 + 高利益
- 这些人非常关心项目但影响力有限
- **沟通策略**：定期信息共享，收集反馈
- **参与方式**：通报进展，听取意见，维护参与感
- **风险**：感觉被忽视可能通过非正式渠道制造障碍
- **典型角色**：直接用户、一线开发人员、测试团队

#### 持续监控（Monitor）— 低权力 + 低利益
- 这些人与项目关系较远
- **沟通策略**：最小信息量，有变化时通知
- **参与方式**：通过公共渠道（周报、看板）获取信息
- **风险**：权力或利益可能随项目发展而变化
- **典型角色**：其他项目团队、行政支持人员

### 动态评估

权力-利益矩阵不是静态的：
- 干系人的权力和利益可能随项目阶段变化
- 新的干系人可能在项目中途出现
- 建议每个里程碑重新评估一次

## 2. 干系人识别五圈层模型

由内到外系统性扫描，确保不遗漏：

### 第一圈层：核心执行团队
直接参与项目交付的人员。他们的日常工作与项目直接相关。
- 项目经理、技术 Lead、开发人员、测试人员、设计师
- 兼职成员、借调人员

### 第二圈层：直接管理层
对项目有直接管理权或审批权的人员。
- 项目发起人（Sponsor）、部门负责人、预算审批人
- 项目管理办公室（PMO）

### 第三圈层：内部协作方
不直接在项目中但有接口依赖的团队。
- 运维团队、安全团队、DBA、架构组
- 兄弟项目、上下游系统团队
- HR（招聘需求）、采购（设备/服务）

### 第四圈层：外部协作方
组织外部的参与方。
- 外部供应商、SaaS 服务提供商
- 外包团队、咨询顾问
- 客户代表、最终用户代表

### 第五圈层：间接影响者
不直接参与但能影响项目的人员或群体。
- C-level 高管、董事会成员
- 监管机构、审计方
- 竞争对手动态（间接影响决策）
- 社区/公众（面向用户的产品）

## 3. 干系人画像要素

对关键干系人（密切管理 + 保持满意象限）建立深度画像：

### 必填要素
- **姓名/角色**：谁？
- **权力来源**：审批权、资源调配权、技术决策权、组织影响力？
- **利益诉求**：项目成功对 TA 意味着什么？
- **立场**：支持者（Champion）、中立者（Neutral）、反对者（Blocker）？
- **顾虑**：最担心什么？

### 进阶要素
- **影响方式**：通过什么渠道影响项目？
- **沟通偏好**：邮件、面对面、即时消息、正式会议？
- **决策风格**：数据驱动、直觉驱动、共识驱动？
- **关系网络**：与哪些其他干系人关系密切？
- **历史经验**：以前参与类似项目的经验和印象？

### 立场转化策略

| 当前立场 | 策略 |
|---------|------|
| 反对者 → 中立者 | 理解顾虑、消除威胁感、展示对 TA 的价值 |
| 中立者 → 支持者 | 增加参与感、展示进展、建立信任 |
| 支持者 → 拥护者 | 赋予角色、公开认可、让 TA 成为项目代言人 |

## 4. RACI 矩阵原则

### 定义
- **R（Responsible）**：执行者——谁做这件事？可以有多个
- **A（Accountable）**：负责人——谁最终负责？每项有且仅有一个
- **C（Consulted）**：咨询者——谁需要被征求意见？双向沟通
- **I（Informed）**：知会者——谁需要被告知结果？单向通知

### 常见问题
- **一项有多个 A**：责任分散，没人真正负责。必须精简到一个
- **某人全是 R**：过载风险。检查是否可以委托
- **某人没有任何字母**：可能是不必要的干系人，或者被遗漏了角色
- **没有 C 的行**：决策可能缺乏输入。检查是否需要专家意见

### 建立 RACI 的步骤
1. 列出项目关键活动/决策/交付物
2. 列出所有干系人
3. 为每个交叉点分配 R/A/C/I
4. 检查每行有且仅有一个 A
5. 检查每列的负载均衡
6. 与干系人确认并达成共识

## 5. 冲突管理框架

干系人之间的利益冲突是项目管理中的常态，需要有准备的处理机制。

### 常见冲突类型
- **优先级冲突**：不同干系人对项目优先级有不同期望
- **资源冲突**：多个项目/团队争夺同一资源
- **范围冲突**：对项目边界的理解不一致
- **技术路线冲突**：对实现方案有分歧

### 冲突升级路径
1. **项目经理协调**：大多数冲突应在项目层面解决
2. **项目发起人仲裁**：项目经理无法协调时升级
3. **管理层决策**：影响多个项目或部门时
4. **治理委员会裁决**：涉及战略方向时

### 处理原则
- 聚焦利益（Interest），而非立场（Position）
- 用数据和事实支撑讨论
- 寻找双赢方案
- 记录决策及其理由，避免反复争论
