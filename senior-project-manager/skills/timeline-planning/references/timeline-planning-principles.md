# 时间线规划原则

本文档定义了项目时间线规划阶段必须遵循的原则。基于 PMBOK 第七版规划绩效域、关键路径法（CPM）和工作分解结构（WBS）方法论。

---

## 1. 工作分解结构（WBS）方法论

WBS（Work Breakdown Structure）是项目管理的基石，将项目范围逐层分解为可管理的工作单元。

### 分解原则

#### 100% 规则
WBS 最重要的原则：子项之和必须等于父项的全部范围。
- 不多：不包含超出父项范围的工作
- 不少：不遗漏任何属于父项范围的工作
- 在每个层级都适用

#### 分解粒度标准
- **工作包**（WBS 最底层）应该能被单个人或小组在 2-10 人天内完成
- 能够合理估算工期和成本
- 能够分配明确的责任人
- 能够追踪完成状态

#### 分解方法
- **按阶段分解**：启动 → 设计 → 开发 → 测试 → 部署
- **按交付物分解**：前端 → 后端 → 数据库 → 基础设施
- **按功能分解**：用户管理 → 订单系统 → 支付系统
- 可混合使用，但同一层级的分解标准要一致

#### WBS 字典
每个工作包应有以下描述：
- 工作包编号和名称
- 范围描述（做什么、不做什么）
- 交付物
- 验收标准
- 负责人
- 前置依赖

## 2. 关键路径法（CPM）

### 核心概念

**关键路径**是项目网络中从开始到结束的最长路径，决定了项目的最短工期。

#### 正向推算（Forward Pass）
从项目开始向前计算：
- **ES（最早开始）** = 所有前置任务中最大的 EF
- **EF（最早完成）** = ES + 工期

#### 逆向推算（Backward Pass）
从项目结束向后计算：
- **LF（最晚完成）** = 所有后续任务中最小的 LS
- **LS（最晚开始）** = LF - 工期

#### 浮动时间（Float/Slack）
- **总浮动** = LS - ES = LF - EF
- 浮动时间 = 0 的任务在关键路径上
- 浮动时间 > 0 的任务可以延迟而不影响总工期

### 依赖关系类型

| 类型 | 含义 | 频率 | 示例 |
|------|------|------|------|
| FS（完成-开始） | A 完成后 B 开始 | 最常见（~90%） | 设计完成 → 开发开始 |
| SS（开始-开始） | A 开始后 B 开始 | 较常见 | 编码开始 → 代码评审开始 |
| FF（完成-完成） | A 完成后 B 完成 | 偶尔 | 测试完成 → 修复完成 |
| SF（开始-完成） | A 开始后 B 完成 | 极少 | 新系统上线 → 旧系统退役 |

### 提前量与延迟量
- **提前量（Lead）**：允许后续任务提前开始（如 FS-2d 表示可提前 2 天开始）
- **延迟量（Lag）**：强制等待（如混凝土浇筑后 FS+3d 等待凝固）

## 3. 工期估算技术

### 三点估算法（PERT）

最推荐的估算方法，能量化不确定性：

```
加权估算（TE） = (O + 4M + P) / 6
标准差（σ） = (P - O) / 6

O = 乐观估算（最好情况）
M = 最可能估算（正常情况）
P = 悲观估算（最坏情况）
```

- 68% 的概率实际工期在 TE ± 1σ 范围内
- 95% 的概率实际工期在 TE ± 2σ 范围内
- 99.7% 的概率实际工期在 TE ± 3σ 范围内

### 其他估算方法

| 方法 | 适用场景 | 准确度 |
|------|---------|--------|
| **类比估算** | 有类似项目历史数据 | 中等 |
| **参数估算** | 有明确的效率参数（如每天多少行代码） | 较高 |
| **自下而上估算** | WBS 已分解完成 | 最高 |
| **专家判断** | 新领域无历史数据 | 取决于专家 |

### 估算偏差修正

常见的估算偏差及修正方法：
- **乐观偏差**：开发人员通常低估 20-30%。修正：使用三点估算
- **帕金森定律**：工作会膨胀到填满可用时间。修正：设置明确的验收标准
- **学习曲线**：新技术/新团队需要额外时间。修正：前几个迭代加 30-50% 缓冲
- **多任务切换**：上下文切换成本约 20-40%。修正：尽量减少并行任务

## 4. 缓冲管理（关键链法）

### 缓冲类型

#### 项目缓冲（Project Buffer）
- 放置在关键路径末尾
- 大小：关键路径总工期的 15-25%（视风险水平调整）
- 保护项目截止日期

#### 汇入缓冲（Feeding Buffer）
- 放置在非关键路径汇入关键路径的节点前
- 大小：该非关键路径总工期的 25-50%
- 防止非关键路径延迟影响关键路径

#### 资源缓冲（Resource Buffer）
- 在关键路径上资源变更的节点前设置预警
- 确保关键资源按时到位

### 缓冲消耗监控

```
缓冲消耗率 = 已消耗缓冲 / 总缓冲
项目完成率 = 已完成任务工期 / 关键路径总工期

健康区（绿色）：缓冲消耗率 < 项目完成率 × 1/3
警告区（黄色）：缓冲消耗率 在 1/3 到 2/3 之间
危险区（红色）：缓冲消耗率 > 项目完成率 × 2/3
```

## 5. 里程碑设置原则

### 里程碑类型

| 类型 | 用途 | 示例 |
|------|------|------|
| **阶段里程碑** | 标记阶段完成 | 设计评审通过、开发完成 |
| **交付里程碑** | 标记关键交付物 | MVP 交付、Beta 版本发布 |
| **决策里程碑** | 标记 Go/No-Go 决策点 | 技术方案评审、上线决策 |
| **外部里程碑** | 标记外部依赖到位 | 第三方 API 就绪、许可证获批 |

### 里程碑设置原则
- 间隔不超过 2 周（保持可见性和控制感）
- 每个里程碑有明确的交付物和验收标准
- 里程碑名称使用"完成态"描述（"设计评审通过"而非"设计评审"）
- 关键路径上的里程碑重点关注

### 里程碑评审清单
每个里程碑评审时检查：
- 交付物是否满足验收标准？
- 风险登记册是否需要更新？
- 时间线偏差是否在可接受范围？
- 干系人是否满意当前进展？
- 是否需要调整后续计划？

## 6. 甘特图最佳实践

### 信息呈现
- 清晰的任务层级（WBS 编号）
- 任务条形图显示工期和时间位置
- 依赖关系用箭头线连接
- 关键路径用红色突出显示
- 里程碑用菱形标记
- 当前日期线（Today Line）
- 进度填充（实际 vs 计划）

### 文本甘特图规范
在 Markdown 环境中用表格呈现甘特图：
- 横轴：时间（周/天）
- 纵轴：任务列表（按 WBS 编号排列）
- 关键路径任务标注 ★
- 里程碑标注 ◆
- 进度偏差标注 ▲（超前）或 ▼（滞后）

### 更新频率
- 甘特图应至少每周更新一次
- 关键路径任务每日追踪
- 偏差超过 10% 时触发预警
