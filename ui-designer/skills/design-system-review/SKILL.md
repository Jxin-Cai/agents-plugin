## Step 1: 识别设计系统资产

向用户收集设计系统信息：

- **设计系统位置**：项目中是否有组件库/设计系统？路径在哪？（如 `src/components/`、`src/design-system/`）
- **Token 定义**：颜色、字体、间距等设计变量定义在哪？（如 CSS 变量、Tailwind config、Theme 文件）
- **UI 框架**：使用了什么 UI 框架？（如 Ant Design、Material UI、自建组件库）
- **设计规范**：是否有 Figma/Sketch 设计规范文档？

**如果用户提供了项目路径：**
- 扫描项目结构，自动识别组件目录、Token 定义文件、配置文件
- 向用户确认识别结果

**⏸️ 等待用户确认后继续。**

## Step 2: 组件清单审查

扫描项目中的组件，建立组件清单并检查一致性：

### 2a. 组件清单
- 列出所有 UI 组件（按钮、输入框、卡片、弹窗、导航等）
- 标注每个组件的变体（variants）和状态（states）
- 识别重复或近似重复的组件

### 2b. 组件一致性检查

| 检查项 | 说明 | 结果 |
|--------|------|------|
| 命名规范 | 组件命名是否遵循统一约定（PascalCase/kebab-case） | ✅/❌ |
| 变体完整性 | 按钮是否有 primary/secondary/danger/disabled 等必要变体 | ✅/❌ |
| 状态覆盖 | 是否定义了 hover/focus/active/disabled/loading/error 状态 | ✅/❌ |
| Props API | 同类组件的 Props 命名和类型是否一致 | ✅/❌ |
| 重复组件 | 是否存在功能重叠的组件（如两种不同的 Modal） | ✅/❌ |

**向用户展示组件清单和一致性检查结果，询问是否有遗漏。**

**⏸️ 等待用户确认后继续。**

## Step 3: Token 使用审查

检查设计 Token（颜色、字体、间距等）的定义和使用：

### 3a. Token 定义检查
- Token 是否集中定义（而非硬编码分散在各处）？
- Token 命名是否有语义化层次（如 `color-primary` 而非 `blue-500`）？
- Token 层级是否合理（全局 Token -> 语义 Token -> 组件 Token）？

### 3b. Token 使用一致性
- 搜索硬编码的颜色值（`#xxx`、`rgb()`），标记未使用 Token 的地方
- 搜索硬编码的像素值，标记未使用间距 Token 的地方
- 搜索硬编码的字体设置，标记未使用排版 Token 的地方

### 3c. Token 覆盖度

```
Token 使用报告：
├── 颜色：[N]% 使用 Token / [M] 处硬编码
├── 间距：[N]% 使用 Token / [M] 处硬编码
├── 字体：[N]% 使用 Token / [M] 处硬编码
└── 其他：[说明]
```

**向用户展示 Token 审查结果。**

## Step 4: 代码-设计一致性检查

如果有设计规范（Figma 等）或设计系统文档，检查代码实现的偏差：

| 维度 | 检查内容 | 偏差情况 |
|------|----------|----------|
| 颜色 | 代码中使用的颜色是否与规范定义一致 | {偏差描述} |
| 字体比例 | 字号/行高/字重是否与排版规范匹配 | {偏差描述} |
| 间距 | 组件间距、内边距是否与规范一致 | {偏差描述} |
| 圆角 | border-radius 是否与规范一致 | {偏差描述} |
| 阴影 | box-shadow 是否与规范一致 | {偏差描述} |
| 动画 | 过渡时长和曲线是否与规范一致 | {偏差描述} |

**如果没有明确的设计规范，基于代码自身的一致性做检查。**

## Step 5: 文档与治理检查

| 检查项 | 说明 | 结果 |
|--------|------|------|
| 组件使用指南 | 每个组件是否有使用说明和示例 | ✅/❌/部分 |
| Do's & Don'ts | 是否有正确和错误的使用示例 | ✅/❌ |
| 组件状态标记 | 是否标记了稳定/测试/废弃状态 | ✅/❌ |
| 版本管理 | 设计系统是否有版本号和变更日志 | ✅/❌ |
| 贡献流程 | 是否有新增/修改组件的标准流程 | ✅/❌ |

|------|------|------|

| Token 规范性 | {A/B/C/D} | {一句话说明} |
| 代码-设计一致性 | {A/B/C/D} | {一句话说明} |
| 文档完整性 | {A/B/C/D} | {一句话说明} |

### 最高优先修复项（Top 3）
1. {问题描述} — {影响范围} — {建议}
2. ...

- {建议2}

## 成功指标
- 组件清单完整（含变体、状态覆盖、重复组件检测）
- Token 使用审查完成（硬编码值已标记，覆盖度已量化）
- 健康度评分有代码证据支撑，给出 Top 3 优先修复建议
- 所有产出向用户展示并获得确认

<IMPORTANT>
本技能完成后，展示菜单并等待用户选择下一步。不要自动执行后续技能。
每条评审意见必须引用具体文件路径和行号作为代码证据，禁止仅凭印象下结论。
Token 覆盖度必须量化（百分比 + 硬编码处数），不接受"大部分使用了 Token"等模糊描述。
健康度评分（A/B/C/D）必须有检查数据支撑，不能凭感觉打分。
</IMPORTANT>
