# 原型反馈原则

本文档定义了原型反馈阶段必须遵循的原则。用这些原则评估交互流程和用户体验完整性。

---

## 1. 认知走查法（Cognitive Walkthrough）

认知走查是一种以任务为中心的可用性评估方法，模拟新用户首次使用界面的认知过程。

### 核心四问
在用户完成任务的每一步，问四个问题：

1. **用户是否会尝试正确的操作？**
   - 用户的目标和界面提供的操作是否匹配？
   - 界面是否暗示了正确的下一步？
   - 用户的心智模型是否与系统模型一致？

2. **用户是否能发现操作入口？**
   - 操作按钮/链接是否在用户的视线范围内？
   - 标签/图标是否足够直观？
   - 是否被其他元素遮挡或淹没？

3. **用户是否能将操作与目标关联？**
   - 操作的标签文字是否与用户的任务目标匹配？
   - 如：用户想"发送邀请"，按钮写的是"发送邀请"还是"提交"？

4. **用户是否能理解操作后的反馈？**
   - 操作完成后是否有即时反馈？
   - 反馈是否清晰告知成功/失败？
   - 用户是否知道下一步该做什么？

### 阻塞点分类
| 类型 | 说明 | 严重程度 |
|------|------|----------|
| 认知阻塞 | 用户不知道下一步该做什么 | 高 |
| 发现阻塞 | 用户找不到操作入口 | 高 |
| 理解阻塞 | 用户不理解操作标签的含义 | 中 |
| 反馈阻塞 | 用户不确定操作是否成功 | 中 |
| 信心阻塞 | 用户害怕操作的后果 | 低-中 |

## 2. 任务流分析

任务流分析评估用户完成目标的路径效率和完整性。

### 任务效率度量
- **步骤数**：完成任务需要多少步？能否减少？
- **决策点**：用户需要做几次选择？选择是否过多？（Hick 定律：选项越多，决策越慢）
- **信息输入**：用户需要输入多少信息？能否自动填充或减少？
- **页面跳转**：完成任务需要跨几个页面？能否在一个页面内完成？

### Hick 定律应用
选择反应时间 = a + b * log2(n)
- n = 选项数量
- 实践：每组选项控制在 5-7 个以内
- 选项过多时使用分类、搜索或渐进式披露

### Fitts 定律应用
点击时间 = a + b * log2(D/W + 1)
- D = 距离，W = 目标宽度
- 实践：
  - 频繁操作的按钮放大、放近
  - CTA 按钮在拇指热区（移动端）
  - 相关操作靠近放置
  - 危险操作远离常用操作

### 三次点击原则
用户应能在三次点击内到达任何目标页面。如果超过三次：
- 评估导航结构是否过深
- 考虑添加快捷入口
- 评估是否需要重组信息架构

## 3. 信息架构评估框架

信息架构（IA）决定了内容如何被组织、标记和发现。

### 组织系统
| 模式 | 适用场景 | 示例 |
|------|----------|------|
| 字母序 | 大量同质内容 | 联系人列表 |
| 时间序 | 事件、活动 | 订单历史 |
| 空间序 | 地理相关 | 门店列表 |
| 主题分类 | 内容有明确类别 | 商品分类 |
| 任务分类 | 以用户行为为导向 | 操作菜单 |
| 受众分类 | 不同用户群 | "我是商家/我是买家" |

### 导航模式评估
- **全局导航**：是否始终可见？是否覆盖所有主要功能？
- **本地导航**：当前区域内的子导航是否清晰？
- **上下文导航**：相关内容的交叉链接是否充分？
- **面包屑**：层级路径是否可追溯？

### 标签系统
- 导航标签是否使用用户语言（而非系统术语）？
- 标签是否互斥（同一内容不应出现在两个标签下）？
- 标签是否稳定（不因上下文变化）？

## 4. 交互设计模式与状态完整性

### 五种页面状态
每个页面/组件都需要考虑五种状态的设计：

1. **空状态（Empty State）**
   - 初次使用、无数据时的展示
   - 必须包含：说明文字 + 引导操作（如"创建你的第一个项目"）
   - 禁止：空白页面或仅显示"暂无数据"

2. **加载状态（Loading State）**
   - 数据获取中的展示
   - 推荐：骨架屏（Skeleton）优于 Spinner
   - 长时间加载（>3s）需要进度指示或预估时间

3. **部分数据状态（Partial State）**
   - 只有少量数据时的展示
   - 布局是否合理？是否显得"空旷"？
   - 是否有引导用户补充数据的提示？

4. **完整数据状态（Ideal State）**
   - 正常使用时的最佳展示
   - 数据量大时是否有分页/虚拟滚动？
   - 是否有排序/筛选/搜索能力？

5. **错误状态（Error State）**
   - 出错时的展示和恢复路径
   - 错误信息是否明确指出原因和修复方式？
   - 是否提供重试/刷新/联系支持等恢复操作？

### 操作反馈矩阵
| 操作类型 | 成功反馈 | 失败反馈 | 进行中反馈 |
|----------|----------|----------|-----------|
| 创建 | Toast/跳转到新项目 | 行内错误提示 | 按钮 Loading |
| 更新 | Toast"已保存" | 行内错误标注 | 保存指示器 |
| 删除 | Toast + 撤销选项 | Toast 错误提示 | 按钮 Loading |
| 提交 | 成功页/确认弹窗 | 行内错误汇总 | 全页 Loading |
| 搜索 | 结果列表 | 空结果 + 建议 | Skeleton |

## 5. 用户旅程映射方法

### 旅程映射要素
- **阶段（Phases）**：用户达成目标的主要步骤
- **行为（Actions）**：每个阶段用户执行的具体操作
- **触点（Touchpoints）**：用户与界面交互的具体元素
- **情绪（Emotions）**：用户在每个触点的情感状态
- **痛点（Pain Points）**：用户遇到的困难或沮丧
- **机会（Opportunities）**：改进体验的可能方向

### 情绪曲线分析
- 标注每个触点的情绪等级（+2 到 -2）
- 关注"情绪低谷"——这些是最高优先级的改进点
- 关注"情绪断崖"——情绪突然下降的地方，通常对应体验缺陷
- 目标：消除低谷，让情绪曲线保持在中性以上

### 关键时刻（Moments of Truth）
- **首次印象**：用户第一次看到界面时的感受
- **首次成功**：用户第一次完成核心任务的体验
- **首次失败**：用户第一次遇到错误时系统的响应
- **再次回访**：用户第二次使用时是否比第一次更顺畅

## 6. 渐进式披露原则

渐进式披露（Progressive Disclosure）通过分层展示信息来降低认知负荷。

### 应用策略
- **默认简单**：首屏只展示最常用的选项，高级选项放在"更多"中
- **按需展开**：点击"高级设置"后展开详细选项
- **上下文触发**：仅在相关条件满足时展示额外选项
- **分步引导**：复杂流程拆分为多步向导（Wizard）

### 何时使用
- 选项或信息量超过 7 个（Miller 定律）
- 目标用户包含新手
- 80% 的用户只使用 20% 的功能
- 页面信息密度过高
