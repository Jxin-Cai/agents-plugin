# 交互审计原则

本文档定义了交互设计审计阶段必须遵循的原则。综合 Nielsen、Shneiderman、Norman 三大框架，用这些原则系统评估交互设计质量。

---

## 1. Nielsen 十大可用性启发式

Jakob Nielsen（1994）提出的可用性启发式评估框架，是交互审计的基线标准：

### H1: 系统状态可见性（Visibility of System Status）
- 系统应始终在合理的时间内通过适当的反馈让用户知道正在发生什么
- 检查项：加载状态、进度指示、操作成功/失败反馈、当前位置指示
- 常见问题：提交后无反馈、长操作无进度条、不知道当前在哪个步骤

### H2: 系统与现实世界的匹配（Match Between System and the Real World）
- 系统应使用用户的语言，采用用户熟悉的词汇、短语和概念
- 检查项：术语是否来自用户领域、信息排列是否符合自然逻辑、图标是否符合直觉
- 常见问题：使用技术术语、违反自然排序、图标含义不明

### H3: 用户控制与自由（User Control and Freedom）
- 用户经常会误操作，需要明确的"紧急出口"来退出不想要的状态
- 检查项：撤销/重做、返回/取消、保存草稿、确认对话框
- 常见问题：不可逆操作无确认、没有返回按钮、表单误关数据丢失

### H4: 一致性与标准（Consistency and Standards）
- 用户不应该纠结不同的词汇、情况或操作是否意味着同一件事
- 检查项：同一操作在不同页面的表现、术语统一性、视觉一致性、交互模式一致性
- 常见问题：同一操作不同名称、相似按钮不同样式、平台惯例不一致

### H5: 错误预防（Error Prevention）
- 好的设计首先防止问题发生，比好的错误消息更重要
- 检查项：输入约束、操作前确认、智能默认值、实时验证
- 常见问题：允许提交无效数据、危险操作无确认、没有输入格式提示

### H6: 识别而非记忆（Recognition Rather Than Recall）
- 最小化用户的记忆负担，将对象、操作和选项可视化
- 检查项：最近使用、搜索建议、上下文帮助、操作历史
- 常见问题：需要记住之前页面的信息、表单无占位提示、缺少搜索历史

### H7: 灵活性与使用效率（Flexibility and Efficiency of Use）
- 快捷方式对新手透明但可加速专家用户的操作
- 检查项：键盘快捷键、自定义工作流、批量操作、高级搜索
- 常见问题：无快捷操作、批量操作缺失、无法自定义常用功能

### H8: 美学与极简设计（Aesthetic and Minimalist Design）
- 界面不应包含无关或很少需要的信息
- 检查项：信息密度、视觉噪音、空白使用、重点突出
- 常见问题：页面信息过载、视觉层次不清、重要操作被淹没

### H9: 帮助用户识别、诊断和恢复错误（Help Users Recognize, Diagnose, and Recover from Errors）
- 错误消息应用平实语言表达、精确指出问题、建设性地提出解决方案
- 检查项：错误消息的清晰度、是否指出问题原因、是否提供修复建议
- 常见问题：技术性错误代码、模糊的错误描述、没有修复指引

### H10: 帮助与文档（Help and Documentation）
- 最好不需要任何文档就能使用，但如需要则应易于搜索、聚焦用户任务
- 检查项：上下文帮助、新手引导、常见问题、搜索功能
- 常见问题：没有帮助文档、帮助文档难找、内容过时

## 2. Shneiderman 八条黄金规则

Ben Shneiderman 提出的界面设计八条黄金规则，作为 Nielsen 启发式的补充维度：

| # | 规则 | 审计关注点 |
|---|------|-----------|
| 1 | 追求一致性 | 操作序列、术语、视觉布局在同类场景中是否一致 |
| 2 | 为常用操作提供快捷方式 | 高频操作是否有缩写、快捷键、宏命令 |
| 3 | 提供信息性反馈 | 每个操作是否有适当的系统反馈 |
| 4 | 设计封闭的操作序列 | 操作是否有明确的开始、中间和结束（操作闭环） |
| 5 | 提供简单的错误处理 | 系统是否防止严重错误，错误时是否有简单恢复方式 |
| 6 | 允许轻松撤销操作 | 操作是否可逆？单步撤销和多步撤销 |
| 7 | 支持内部控制点 | 用户是否感觉自己在控制系统（而不是被系统控制） |
| 8 | 减少短期记忆负担 | 信息是否被适当组织，减少用户需要同时记住的项目数 |

## 3. 认知工程原则

基于 Don Norman 和 Gerhardt-Powals 的认知工程原则：

### 认知负荷管理
- **Miller 定律**：工作记忆容量 7±2 项，一次展示的选项不超过这个范围
- **Hick 定律**：决策时间随选项数量对数增长，减少选项加快决策
- **接近律**：相关信息空间上靠近，减少视觉搜索成本
- **格式塔原则**：利用视觉分组减少认知负担

### 心理模型适配
- 系统的概念模型是否匹配用户的心理模型？
- 隐喻使用是否恰当？（拉伸不当的隐喻比没有隐喻更糟）
- 操作是否符合用户在现实世界中的经验？

## 4. 审计方法论

### 启发式评估流程
1. **独立评估**：每位评估者独立遍历界面，对照启发式清单标注问题
2. **严重程度评级**：每个问题标注严重程度（0-4 级）
3. **汇总合并**：合并所有评估者的发现，去除重复
4. **优先排序**：按严重程度 x 频率排序

### 严重程度量表
| 等级 | 定义 | 处理优先级 |
|------|------|-----------|
| 0 | 不认为是可用性问题 | 忽略 |
| 1 | 仅装饰性问题，低优先级修复 | 有空再修 |
| 2 | 轻微可用性问题，低优先级修复 | 计划修复 |
| 3 | 严重可用性问题，高优先级修复 | 优先修复 |
| 4 | 灾难性问题，必须在发布前修复 | 立即修复 |

### 认知走查法
对每个关键任务的每一步，问四个问题：
1. 用户是否会尝试去完成正确的效果？（目标明确性）
2. 用户是否能注意到正确的操作入口？（可见性）
3. 用户是否能将操作入口与目标关联？（可理解性）
4. 如果用户执行了正确操作，是否能看到进展反馈？（反馈性）

## 5. 无障碍审计维度

WCAG 2.1 AA 级合规是交互设计的底线标准：

### POUR 四原则
| 原则 | 含义 | 关键检查项 |
|------|------|-----------|
| Perceivable（可感知） | 信息可被用户感知 | 图片有 alt 文本、颜色对比度 ≥ 4.5:1、视频有字幕 |
| Operable（可操作） | 界面组件可被操作 | 键盘可达、无键盘陷阱、足够的操作目标尺寸 |
| Understandable（可理解） | 信息和操作可被理解 | 语言清晰、一致的导航、输入错误有建议 |
| Robust（健壮） | 内容可被多种技术解读 | 语义化 HTML、ARIA 标记正确、兼容辅助技术 |

## 6. 审计报告格式

### 问题记录模板
```
## 问题 #N: [问题标题]

- **违反启发式**: H[编号] - [启发式名称]
- **严重程度**: [0-4]
- **位置**: [页面/功能/步骤]
- **问题描述**: [具体描述，包含当前行为]
- **影响**: [对用户的影响]
- **建议修复**: [具体的改进方案]
- **参考标准**: [对应的行业最佳实践]
```

### 审计总结模板
```
## 审计总结

- 评估范围：[描述]
- 发现问题总数：[N]
- 严重程度分布：4级[n]个 / 3级[n]个 / 2级[n]个 / 1级[n]个
- 违反最多的启发式：[列出 Top 3]
- 整体可用性评分：[基于问题严重程度和密度的综合评估]
```
