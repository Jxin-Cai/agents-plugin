# 用户流程分析原则

本文档定义了用户流程分析阶段必须遵循的原则。用这些原则指导流程映射、摩擦点识别和流程优化。

---

## 1. 流程类型体系

不同分析目的对应不同的流程表达方式：

### 任务流（Task Flow）
- 单一路径、无决策分支
- 描述一个特定用户完成一个特定任务的线性步骤
- 适用场景：理解某个操作的基本步骤序列
- 示例：已注册用户登录 → 输入密码 → 进入首页

### 用户流（User Flow）
- 多路径、有决策分支
- 从用户入口开始，映射用户可能经过的所有路径
- 适用场景：识别用户在决策点上的不同走向
- 符号约定：矩形=页面/屏幕，菱形=决策点，椭圆=起点/终点，箭头=流向

### 线框流（Wireflow）
- 结合线框图和流程图
- 每个节点是简化的页面布局，箭头连接操作触发
- 适用场景：向开发和设计团队沟通页面间的跳转逻辑

### 客户旅程地图（Customer Journey Map）
- 超越产品边界，覆盖用户的完整体验链
- 包含情绪曲线、接触点、痛点和机会点
- 适用场景：理解用户在多渠道、多触点下的全局体验

## 2. 流程映射方法论

### 入口-目标映射法
1. 列出所有用户入口点（首页、深链、推送、搜索引擎、分享链接）
2. 列出所有用户目标（核心任务完成、转化、信息获取）
3. 映射从每个入口到每个目标的最短路径
4. 识别路径中的共享节点（Hub 页面）和关键决策点

### 任务分析法
1. 识别用户的核心任务（JTBD 框架：用户"雇佣"产品来完成什么工作？）
2. 将每个核心任务分解为子任务
3. 每个子任务分解为操作步骤
4. 记录每个步骤的前置条件和后置状态

### Happy Path 优先法
1. 先映射理想路径（Happy Path）——一切顺利时的最短路径
2. 在理想路径上标注每个决策点
3. 从决策点延伸出替代路径（Alternative Path）
4. 从替代路径延伸出异常路径（Exception Path）
5. 确保每条路径都有终点（不允许死胡同）

## 3. 摩擦点识别框架

摩擦点是用户在完成任务路径上遇到的阻力。按严重程度分级：

### 阻断性摩擦（Blocker）
- 用户完全无法继续，流程被终止
- 示例：必填信息不清楚、加载失败无提示、死链
- 标注：🔴

### 延迟性摩擦（Delay）
- 用户可以继续，但需要额外时间或操作
- 示例：页面加载慢、需要切换到其他应用获取信息、表单字段过多
- 标注：🟡

### 困惑性摩擦（Confusion）
- 用户不确定下一步该做什么
- 示例：标签含义不明、操作按钮不显眼、缺少进度指示
- 标注：🟠

### 烦躁性摩擦（Annoyance）
- 用户能完成任务但体验不愉快
- 示例：重复输入信息、不必要的确认弹窗、广告打断
- 标注：⚪

### 摩擦点检测清单
对流程中的每个步骤，检查：
- 用户是否清楚当前在哪？（系统状态可见性）
- 用户是否知道下一步做什么？（操作引导）
- 当前步骤是否有多余操作？（步骤精简度）
- 如果出错能否轻松恢复？（容错机制）
- 等待时间是否可接受？（响应速度）

## 4. 流程优化原则

### 步骤最小化
- 删除所有不产生用户价值的步骤
- 合并可以同时完成的步骤
- 将可选步骤延后（不阻断主路径）
- 目标：用户感觉"比预期少了一步"

### 决策简化
- 减少每个决策点的选项数量（Hick's Law：选项越多决策越慢）
- 提供智能默认值
- 渐进式呈现选项（先核心、后高级）
- 对高频选择提供快捷通道

### 断裂点消除
断裂点是用户从一个流程跳到另一个流程（或跳出产品）的地方：
- 上下文丢失：跳转后用户忘了之前在做什么
- 渠道切换：从 App 跳到浏览器、从线上跳到线下
- 状态丢失：已填写的信息需要重新输入
- 消除策略：保持上下文连续性、支持跨渠道状态保持

### 错误恢复设计
- 每个可能出错的步骤都有恢复路径
- 错误信息明确告知"出了什么问题"和"如何修复"
- 避免用户回到流程起点重新开始
- 支持断点续传（保存中间状态）

---

## 5. 流程度量指标

| 指标 | 定义 | 优化方向 |
|------|------|---------|
| 任务完成率 | 成功完成目标的用户比例 | 越高越好 |
| 任务完成时间 | 从开始到完成的平均时间 | 越短越好 |
| 步骤数 | 完成任务需要的操作步骤 | 越少越好 |
| 错误率 | 流程中触发错误的比例 | 越低越好 |
| 回退率 | 用户在流程中返回上一步的比例 | 高回退率提示困惑 |
| 放弃率 | 用户未完成就离开的比例 | 放弃集中的步骤是优化重点 |
| 首次成功率 | 不需要纠错就完成任务的比例 | 越高越好 |

---

## 6. 跨角色与跨渠道流程

### 多角色协作流程
- 映射不同角色在同一业务流程中的职责和交互
- 使用泳道图（Swimlane Diagram）区分角色
- 关注角色切换点：信息是否完整传递？

### 跨渠道流程
- 用户可能在多个渠道间切换（Web / App / 小程序 / 线下）
- 每个渠道切换点是潜在的断裂点
- 确保关键状态在渠道间同步
