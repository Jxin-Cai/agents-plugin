# Sprint 规划原则

本文档定义了 Sprint 规划阶段必须遵循的原则。

---

## 1. Sprint 目标设定

Sprint 目标是整个 Sprint 的北极星，所有任务选择和优先级调整都围绕目标展开。

### 好的 Sprint 目标
- **一句话说清**：用一句话描述这个 Sprint 要达成的业务成果
- **结果导向**：描述的是"达成什么"而不是"做哪些事"
- **可验证**：Sprint 结束时能明确判断目标是否达成
- **有价值**：即使个别任务未完成，只要目标达成就是成功的 Sprint

### 反面案例
- "完成 Backlog 里排好的任务" → 这只是任务清单，不是目标
- "做完登录和支付功能" → 这是任务列表，应该是"用户可以完成首次购买流程"
- "尽可能多做" → 没有聚焦，什么都不是优先级

### 目标模板
```
本 Sprint 目标：让 [目标用户] 能够 [完成什么场景]，
验证 [核心假设/业务指标]。
```

## 2. 容量计算

准确的容量计算是 Sprint 规划的基础。过度承诺是 Sprint 失败的首要原因。

### 容量公式
```
Sprint 容量 = 团队人数 × Sprint 天数 × 每日有效时数 × 专注系数
```

### 关键参数

**每日有效时数**
- 标准值：6 小时（8 小时工作日扣除会议、沟通、行政等）
- 调整因素：会议密集期取 5 小时，纯开发周期取 7 小时

**专注系数（Focus Factor）**
- 定义：实际用于 Sprint 任务的时间占比
- 新团队：50-60%（大量沟通、磨合开销）
- 成熟团队：70-80%
- 高效团队：80-85%（几乎不可能超过 85%）

**可用人天调整**
- 减去请假天数
- 减去已知的非 Sprint 工作（值班、面试、培训）
- 减去公司级活动占用
- 新成员入职首个 Sprint 按 50% 计算

### 容量缓冲
- 标准缓冲：15%（应对估算偏差和突发情况）
- 高风险 Sprint（新技术、新成员）：20-25%
- 低风险 Sprint（成熟领域、老团队）：10%

### 关键规则
- **绝不按 100% 容量规划**——这等于假设一切完美，而现实从不完美
- **使用历史速率校准**：如果容量算出 50 点但历史速率是 35 点，取 35 点
- **容量 ≠ 目标**：容量是上限，不是必须达到的目标

## 3. 任务选择策略

### 自上而下填充
1. 按优先级排名从高到低依次选入
2. 每选入一个条目，更新剩余容量
3. 当剩余容量不足以放入下一个条目时，检查是否有更小的高优先级条目可以填入
4. 最终保留 10-15% 容量作为缓冲

### 依赖关系检查
- 被选入的条目是否有未选入的前置依赖？→ 要么一起选入，要么推迟
- 是否有外部依赖在 Sprint 期间可能无法就绪？→ 标注风险
- 条目之间的顺序依赖是否影响并行开发？→ 调整任务分配

### 平衡维度
| 维度 | 检查 |
|------|------|
| 新功能 vs 债务偿还 | 技术债务占比是否在 15-20%？ |
| 前端 vs 后端 | 是否有角色闲置或过载？ |
| 大条目 vs 小条目 | 是否有快速可完成的"速赢"条目？ |
| 学习 vs 交付 | 新技术/新领域的探索是否有合理占比？ |

## 4. 风险识别与应对

### Sprint 常见风险
| 风险类型 | 预警信号 | 应对策略 |
|---------|---------|---------|
| 过度承诺 | 计划点数 > 历史速率 | 砍掉 Could Have 条目 |
| 依赖阻塞 | 外部依赖时间未确认 | 准备替代任务（Plan B） |
| 需求模糊 | 条目有"待确认"标记 | Sprint 前完成澄清或推迟 |
| 关键人员缺席 | 核心开发者请假或被借调 | 提前交叉培训或降低容量 |
| 技术不确定性 | 使用新框架/新技术 | 安排 Spike（技术调研）并增加缓冲 |
| 范围蔓延 | Sprint 中途加需求 | 新增一个必须移出一个 |

### 风险评估矩阵
```
影响程度 × 发生概率 = 风险等级

高影响 × 高概率 = 🔴 必须在规划阶段解决
高影响 × 低概率 = 🟡 准备应急方案
低影响 × 高概率 = 🟡 监控并准备应对
低影响 × 低概率 = 🟢 接受风险
```

## 5. Sprint 计划文档规范

一份好的 Sprint 计划文档应包含以下要素：

### 必备要素
- **Sprint 目标**：一句话描述
- **Sprint 周期**：起止日期
- **团队容量**：可用人天、预估故事点容量
- **选入条目清单**：优先级排序，含估算和负责人
- **依赖关系图**：条目间和外部依赖
- **风险清单**：已识别风险和应对方案
- **缓冲说明**：预留多少缓冲，原因

### 可选要素
- 每日燃尽预期
- 验收标准汇总
- 与 Sprint 目标的映射关系
- 技术债务偿还计划

## 6. Sprint 承诺的心理学

### 承诺 vs 预测
- Sprint 计划是**预测**而非**承诺**——团队尽最大努力完成，但不保证 100% 完成
- 如果每个 Sprint 都 100% 完成，说明团队在低估自己的能力或隐藏了容量
- 健康的完成率：70-90%

### 帕金森定律
- "工作会膨胀到填满所有可用时间"
- 对策：紧凑但不紧绷的规划，留缓冲但不留太多
- Sprint 目标完成后的剩余时间用于技术债务或下个 Sprint 的准备

### 学生综合征
- "截止日期还远，不急"
- 对策：将大条目拆成小任务，设置中间检查点
- 每日站会关注"今天打算完成什么"而非"昨天做了什么"
