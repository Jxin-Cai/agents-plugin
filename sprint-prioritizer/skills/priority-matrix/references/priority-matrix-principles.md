# 优先级矩阵原则

本文档定义了优先级评估阶段必须遵循的原则。

---

## 1. RICE 评分框架

RICE 是一个量化优先级评分模型，适用于产品团队需要数据驱动决策的场景。

### 四个维度

**Reach（触达范围）**
- 定义：在给定时间段内，该功能会影响多少用户/事务
- 计量单位：人数 / 事务数 / 请求数（按季度或 Sprint 周期）
- 关键：使用实际数据（日活、流量），不要凭感觉
- 示例：影响所有日活用户 = 10000，影响 VIP 用户 = 500

**Impact（影响程度）**
- 定义：对每个被影响的用户，改善程度有多大
- 评分量表：3 = 巨大改善，2 = 显著改善，1 = 中等改善，0.5 = 轻微改善，0.25 = 微小改善
- 关键：评估用户体验或业务指标的实际提升，不是技术复杂度

**Confidence（信心水平）**
- 定义：对 Reach 和 Impact 估算的确信程度
- 评分量表：100% = 有数据支撑，80% = 有间接证据，50% = 直觉判断
- 关键：诚实面对不确定性，信心低的条目可以先做验证

**Effort（投入成本）**
- 定义：完成该功能需要的人月数
- 计量单位：人月（person-month）
- 关键：包含设计、开发、测试、部署的完整工作量
- 最小值：0.5 人月（避免除以零或极端值）

### 计算公式
```
RICE Score = (Reach × Impact × Confidence%) / Effort
```

### 使用建议
- 先让团队独立评分，再讨论差异
- 每个维度都要有明确的评分依据，拒绝"我觉得"
- 分数相近的条目（差异 < 20%）视为同一优先级

## 2. WSJF 评分框架

WSJF（加权最短作业优先）是 SAFe 框架的核心排序方法，特别关注延迟成本。

### 三个价值维度

**Business Value（业务价值）**
- 对收入、利润、市场份额的直接贡献
- 使用相对估算（1-10 分），不追求绝对准确
- 问："如果不做这个，对业务的影响有多大？"

**Time Criticality（时间紧迫度）**
- 延迟交付的成本是否随时间增加
- 评分标准：10 = 错过窗口就没价值，1 = 什么时候做都行
- 典型高分场景：合规截止日期、竞品抢先、季节性需求、合同承诺

**Risk Reduction / Opportunity Enablement（风险消除 / 机会赋能）**
- 做这个能降低多少业务或技术风险
- 做这个能开启多少新的可能性
- 评分标准：10 = 消除关键风险或打开战略通道，1 = 无额外收益

### Job Size（作业规模）
- 团队共识的相对工作量（故事点或 T-shirt Size）
- 使用与价值维度相同的尺度（1-10 分）

### 计算公式
```
WSJF = (Business Value + Time Criticality + Risk Reduction) / Job Size
```

### 使用建议
- 特别适合有明确截止日期或时间窗口的场景
- 先评价值维度再评工作量，避免工作量影响价值判断
- 当两个条目 WSJF 分数接近时，优先选择 Job Size 更小的（更快交付价值）

## 3. MoSCoW 分类法

MoSCoW 是一种快速达成共识的定性分类方法，适用于干系人对齐和 MVP 定义。

### 四个分桶

**Must Have（必须有）**
- 没有这个功能，产品/系统无法上线或无法正常运行
- 合规要求、核心业务流程、安全底线
- 检验方法："如果不做，会发生什么？" → 如果答案是"产品不能用"，就是 Must

**Should Have（应该有）**
- 很重要但不是生死攸关
- 去掉后产品能用，但体验或效率显著下降
- 通常是第二轮迭代的高优先级

**Could Have（可以有）**
- 锦上添花，有了更好
- 资源充裕时做，资源紧张时可以推迟
- 通常是差异化竞争点

**Won't Have（这次不做）**
- 明确排除的范围，不是永远不做，而是这个周期不做
- 关键：必须明确列出，避免范围蔓延
- 记录到下次评审时重新考虑

### 使用建议
- 最适合快速决策和干系人沟通
- Must Have 不应超过总条目的 60%（否则说明分类不够严格）
- Won't Have 同样重要——明确说"不做什么"防止范围蔓延
- 可以和 RICE/WSJF 结合使用：先用 MoSCoW 粗分，再用量化框架细排

## 4. 延迟成本（Cost of Delay）

延迟成本是所有优先级决策的底层逻辑——不做或晚做这件事的代价是什么。

### 延迟成本曲线类型
| 类型 | 特征 | 示例 |
|------|------|------|
| 线性递增 | 每延迟一天损失固定金额 | 系统故障导致每天损失收入 |
| 阶梯式 | 到某个节点后突然跳升 | 合规截止日期、合同违约 |
| 峰值衰减 | 窗口期过后价值急速下降 | 节日营销、竞品抢先 |
| 持续恒定 | 什么时候做价值都差不多 | 内部工具优化 |

### 评估问题清单
- "如果推迟一个 Sprint 做这个，会有什么后果？"
- "这个需求有硬性截止日期吗？"
- "竞品是否已经/即将上线类似功能？"
- "推迟后是否会增加后续的开发成本？"

## 5. 多维度交叉验证

单一框架可能有盲点，建议使用多维度交叉验证：

### 推荐组合策略
1. **MoSCoW 粗分** → 先将 Backlog 分为四桶，快速筛除 Won't Have
2. **RICE/WSJF 细排** → 对 Must Have 和 Should Have 做量化排序
3. **延迟成本检验** → 对排名靠前的条目检查是否有时间敏感因素

### 一致性检查
- 如果 RICE 排名高但 MoSCoW 是 Could Have → 可能 Impact 被高估
- 如果 MoSCoW 是 Must Have 但 RICE 分低 → 可能是合规/安全等非用户感知型需求
- 如果 WSJF 排名和 RICE 差异大 → 通常是时间紧迫度的差异，需要关注截止日期

## 6. 优先级决策的常见陷阱

| 陷阱 | 表现 | 应对 |
|------|------|------|
| HiPPO 效应 | 最高薪的人的意见自动成为优先级 | 用量化框架替代拍脑袋 |
| 沉没成本 | "已经做了一半不能浪费" | 只看剩余投入 vs 预期回报 |
| 紧急 vs 重要 | 被紧急事务挤掉重要事务 | 区分 time-critical 和 business-critical |
| 全部都是 P0 | 干系人不愿意做取舍 | 如果全是 P0 就等于没有优先级 |
| 功能偏见 | 只优先考虑新功能，忽略技术债务和 Bug | 将技术债务纳入同一评分体系 |
| 近因偏差 | 最近提出的需求显得更紧急 | 对所有条目统一评分，不因提出时间区别对待 |
