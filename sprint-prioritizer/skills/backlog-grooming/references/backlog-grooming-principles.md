# Backlog 梳理原则

本文档定义了 Backlog 梳理阶段必须遵循的原则。

---

## 1. 就绪定义（Definition of Ready）

每个 Backlog 条目进入 Sprint 前必须满足就绪标准。未达标的条目不得被拉入 Sprint。

### 就绪检查清单
- **用户故事格式**：作为 [角色]，我想 [能力]，以便 [价值]
- **验收标准**：至少 2 条可验证的验收条件
- **估算完成**：团队已给出故事点估算
- **依赖识别**：外部依赖已标注且有明确时间线
- **设计就绪**：需要设计的条目已有设计稿或线框图
- **无阻塞问题**：没有未解决的开放问题阻塞开发

### 就绪度评级
- **绿灯（Ready）**：满足所有就绪标准，可直接进入 Sprint
- **黄灯（Almost Ready）**：缺少 1-2 项非关键标准，Sprint 前可补齐
- **红灯（Not Ready）**：缺少关键标准（如验收标准、估算），需退回梳理

---

## 2. 用户故事拆分原则

大的用户故事（Epic/Feature）需要拆分到可在一个 Sprint 内完成的粒度。

### INVEST 原则
- **I - Independent（独立的）**：故事之间尽量减少依赖
- **N - Negotiable（可协商的）**：细节可以和团队讨论调整
- **V - Valuable（有价值的）**：每个故事独立交付用户可感知的价值
- **E - Estimable（可估算的）**：团队能给出合理的工作量估算
- **S - Small（小的）**：一个 Sprint 内可完成
- **T - Testable（可测试的）**：有明确的验收标准

### 拆分技法
| 技法 | 说明 | 示例 |
|------|------|------|
| 按工作流步骤拆分 | 沿用户操作流程切割 | 注册 → 登录 → 重置密码 |
| 按业务规则拆分 | 每条规则一个故事 | 基础定价 → 折扣规则 → 会员价 |
| 按数据变体拆分 | 按数据类型切割 | 文本搜索 → 图片搜索 → 语音搜索 |
| 按角色拆分 | 按用户角色切割 | 买家视角 → 卖家视角 → 管理员视角 |
| 按操作拆分 (CRUD) | 按增删改查切割 | 创建订单 → 查看订单 → 修改订单 → 取消订单 |
| 简单/复杂拆分 | 先做简单版再增强 | 基础列表 → 排序筛选 → 高级搜索 |

## 3. 估算方法论

### 故事点估算
- 使用斐波那契数列（1, 2, 3, 5, 8, 13, 21）作为估算刻度
- 故事点衡量的是**相对复杂度**，不是绝对工时
- 选择一个团队公认的基准故事（通常 3 点）作为锚点
- 超过 13 点的故事必须拆分

### 估算偏差校正
| 偏差类型 | 表现 | 校正方法 |
|---------|------|---------|
| 锚定效应 | 第一个发言的人影响全组 | 先独立估算，再公开讨论 |
| 乐观偏差 | 总觉得"不难" | 追问"最坏情况需要多久" |
| 从众效应 | 跟着多数人走 | 要求偏差最大的两人解释理由 |
| 经验盲区 | 没做过所以估不准 | 做 Spike（技术调研）后再估 |

## 4. Backlog 健康度指标

### 条目层面
- 用户故事格式完整度（角色 / 能力 / 价值三要素）
- 验收标准覆盖率（有 AC 的条目占比）
- 估算完成率（已估算的条目占比）
- 依赖标注率（已识别依赖的条目占比）

### 整体层面
- Backlog 深度：至少有 2-3 个 Sprint 的已梳理条目
- 就绪比例：绿灯条目占比 >= 60%
- 过期条目：超过 3 个 Sprint 未被选入的条目应审视是否仍然需要
- 大小分布：超过 8 点的条目占比 <= 20%

---

## 5. 技术债务与非功能需求

技术债务和非功能需求（性能、安全、可维护性）必须作为 Backlog 的一部分被显式管理。

### 技术债务处理策略
- **预算制**：每个 Sprint 预留 15-20% 容量处理技术债务
- **搭便车制**：修改相关功能时顺带偿还附近的技术债务
- **专项制**：累积到临界点时安排专项 Sprint 集中偿还

### 技术债务分类
| 类型 | 优先处理条件 |
|------|------------|
| 架构债务 | 阻碍新功能开发、影响系统稳定性 |
| 代码债务 | 频繁导致 Bug、影响开发效率 |
| 测试债务 | 关键路径缺少自动化测试 |
| 文档债务 | 核心模块无文档导致知识断层 |
| 依赖债务 | 使用的库/框架有已知安全漏洞 |
