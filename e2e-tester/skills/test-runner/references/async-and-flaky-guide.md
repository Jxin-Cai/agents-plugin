# 异步验证与 Flaky 治理指南

仅在以下情况读取本文件：
- 剧本包含 `async` 或 `idempotency` oracle
- 执行中出现疑似 flaky 现象（首次失败、重试通过）

---

## 异步验证策略

当剧本涉及异步链路时，执行阶段必须：

1. **识别一致性窗口**：从剧本的 Async Oracle 中读取预期等待时间
2. **智能轮询验证**：使用退避策略（exponential backoff）轮询查询接口，而非固定 sleep
   - 默认策略：初始间隔 500ms，每次翻倍，最大间隔 10s，最多 30s 总等待
   - 剧本可覆盖：使用剧本中声明的 `轮询策略` 参数
3. **时序验证**：当剧本声明了操作间的时序依赖，验证事件发生顺序（A 完成 → B 触发 → C 接收）
4. **异步失败归因**：超时未达成一致性时，区分"真的失败"和"一致性窗口不够长"

### 约束

- **异步不能 sleep 了事** — 必须用轮询+退避策略，固定 sleep 不可接受
- 超时归因必须明确写入报告的失败分析

---

## Flaky 治理

在执行过程中识别和处理 flaky 现象：

### 自动重试
当首次执行结果为 FAIL 且 flaky 嫌疑为 medium/high 时，自动重试一次。

### Flaky 根因分类
对 flaky case 标注根因类型：
| 类型 | 说明 |
|------|------|
| `env_unstable` | 环境波动（网络、服务重启） |
| `timing` | 时序竞争（异步未等够、并发冲突） |
| `data_pollution` | 残留数据干扰 |
| `test_defect` | 测试脚本本身不稳定 |

### Flaky 标记与降级
连续 2 次以上 flaky 的场景在报告中标记为 `⚠️ FLAKY`，建议从阻断降级为告警。

### 约束

- **flaky 不能忽略** — flaky 必须分类归因，不能笼统标记"不稳定"
- flaky 根因分类必须写入报告的 Flaky 观察与治理段
