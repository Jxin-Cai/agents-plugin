# E2E 测试任务澄清

通过结构化引导，把用户的“想测一下”收敛成可执行的测试任务文件。输出的不只是测试范围，而是：测试目标、风险等级、业务边界、用户角色、依赖策略、成功判据、不可接受结果，以及本次可以直接复用的测试资产。

---

## 触发条件

- `/e2e` 流程的 Step 1 调用
- 用户主动描述测试需求但任务定义不清晰

---

## 前置条件

### 风险建模清单

澄清时至少考虑以下维度：

| 维度 | 需要问什么 |
|------|-----------|
| 业务价值 | 这个流程支撑什么核心业务目标？ |
| 失败影响 | 出错会导致收入损失、数据错误、用户流失还是合规问题？ |
| 变更强度 | 最近是否刚改过？是否是高频改动模块？ |
| 使用频率 | 是高频主链路还是低频后台操作？ |
| 角色差异 | 不同角色/权限下行为是否不同？ |
| 外部副作用 | 是否会触发支付、发消息、库存变更、审核、导出？ |
| 异步复杂度 | 是否涉及任务、队列、轮询、回调？ |

### 成功判据标准

好的成功判据：提交订单后，订单列表中出现新订单，状态为“待支付”，库存锁定成功，用户收到确认提示。
差的成功判据：页面显示提交成功、看起来没问题。

---

## 提问规则

1. 所有选择必须使用 `AskUserQuestion`
2. **默认允许用户走 Other 自定义答案**，不要把选项设计成封闭世界
3. 当多个信息可能同时成立时，使用 `multiSelect: true`
4. 当只需要确认一个方向时，使用单选，但仍允许用户自定义补充
5. 如果已有文档可接续，应优先问“沿用哪些已有内容、补哪些缺口”，而不是整份重问

---

## 执行流程

### Step 0: 先找可复用资产，再决定问什么

在追问用户之前，先扫描以下位置：
- `.e2e-tests/asset-catalog.md`
- `.e2e-tests/registry.yaml`
- `.e2e-tests/_shared/datasets/**`
- `.e2e-tests/_shared/mocks/**`
- `.e2e-tests/_shared/helpers/**`
- `.e2e-tests/{domain}/task/task.md`（如存在）
- `.e2e-tests/{domain}/task/index.md`（如存在）

目标不是替用户脑补测试内容，而是识别：
- 是否已有相近业务场景的脚本
- 是否已有可复用的数据集 / mock / helper
- 当前任务是否已有已确认内容，可直接接续
- 哪些信息可以直接继承，哪些信息仍需用户补充

如果找到候选资产或已有任务文件，在后续澄清中优先向用户确认“沿用哪些 / 调整哪些 / 新增哪些”，而不是从零开始重问。

### Step 1: 澄清任务目标与风险

通过 **AskUserQuestion** 优先收集以下关键问题（可分多轮）：

**必收集项**：

| 项目 | 问题 | 说明 |
|------|------|------|
| 被测功能 | 这次要验证的具体业务流程是什么？ | 要追问到起点、终点和关键动作 |
| 测试目标 | 为什么现在要测它？ | 新功能验收 / 回归 / 发布前 / 线上问题复现 |
| 风险影响 | 如果这里出问题，会造成什么业务后果？ | 用于判定风险等级 |
| 成功判据 | 这次怎样才算真的通过？ | 不是“页面正常”，而是业务承诺成立 |
| 不可接受结果 | 哪些结果一出现就应判失败？ | 如重复下单、脏数据、权限越权 |
| 测试边界 | 明确这次不测什么？ | 避免范围失控 |

如果用户同时想修改多个维度，例如“目标 + 风险 + 边界”，应使用多选确认需要一起调整的部分。

### Step 2: 澄清角色、状态与准备前提

继续追问：

| 项目 | 问题 | 说明 |
|------|------|------|
| 用户角色 | 谁在执行这个流程？有哪些角色/权限差异？ | admin / 普通用户 / 审核员等 |
| 数据状态 | 需要什么前置数据状态？ | 已创建订单 / 未支付 / 已实名等 |
| 环境信息 | 在哪个环境测？有无 feature flag？ | 测试 / 预发 / 生产镜像 |
| 外部副作用 | 这个流程会触发什么外部效果？ | 发消息、扣库存、写日志、下载文件 |
| 异步链路 | 是否涉及轮询、任务、消息、回调？ | 决定执行与等待策略 |

当多个前提可并存时，例如“需要多个角色 + 多个前置状态”，应使用 `multiSelect: true`。

### Step 3: 识别服务依赖与复用策略

基于业务流程，识别涉及的服务和外部依赖：

1. **分析调用链** — 从用户描述和已有资产中推断或补全
2. **逐个确认处理策略** — 使用 **AskUserQuestion** 为每个外部依赖确认：
   - **真实联调**
   - **复用现有 mock**
   - **复用现有 fixture / 数据集**
   - **新建资产**
3. **标注关键依赖** — 哪些依赖若不稳定会直接让测试结论失真
4. **只对缺口追问** — 若已有资产已覆盖某项准备，不要重复让用户提供

当一个依赖既可能复用 mock、又可能需要补数据集时，可使用多选收集组合策略，再由后续阶段落实。

### Step 4: 生成或更新测试任务文件

将收集到的信息整理为 `.e2e-tests/{domain}/task/task.md`，结构至少如下：

```markdown
# 当前测试任务

## 基本信息
- **被测流程**: {功能描述}
- **测试目标**: {验收 / 回归 / 发布前 / 问题复现}
- **风险等级**: {High / Medium / Low}
- **应用入口**: {URL}
- **环境**: {环境说明}

## 业务目标
- {为什么现在测}

## 成功判据
- {关键业务结果 1}
- {关键业务结果 2}

## 不可接受结果
- {失败条件 1}
- {失败条件 2}

## 用户角色与权限
- {角色 1}: {权限说明}
- {角色 2}: {权限说明}

## 前置状态
- {前置数据 / 环境状态}

## 依赖与策略
| 服务 | 角色 | 策略 | 资产 / 备注 |
|------|------|------|-------------|
| {service-1} | 核心被测 | real | — |
| {service-2} | 下游依赖 | mock | `.e2e-tests/_shared/mocks/...` |

## 候选可复用资产
### 数据集
- {路径或“无”}

### Mock
- {路径或“无”}

### Helper / 历史脚本
- {路径或“无”}

## 待补充信息
- {仍缺失的信息；如无写“无”}

## Out of Scope
- {本次明确不测的内容}
```

如果文件已存在，应基于已产出内容进行补充、修订或追加，而不是无条件覆盖。

### Step 5: 用户确认

使用 **AskUserQuestion** 向用户确认测试任务文件：
- 选项建议：确认，进入下一步 / 需要调整目标或边界 / 需要补充风险与判据 / 需要继续沿用已有资产 / 其他补充
- 若用户可能同时选择多项调整，使用 `multiSelect: true`

根据用户反馈修改后保存最终版本。

**⏸️ 等待用户确认后结束。**

---

## 约束

1. **澄清阶段必须产出文件** — 输出的是 `task/task.md`，不是随手整理的摘要
2. **风险驱动而不是功能罗列** — 不只问测什么，还要问为什么测、失败影响是什么
3. **必须定义成功与失败** — 没有成功判据和不可接受结果，不得进入后续阶段
4. **角色与状态必须明确** — 用户角色、数据状态、权限差异不清，不得假设
5. **边界必须明确** — 说清本次不测什么，防止范围漂移
6. **依赖策略必须明确** — 涉及多服务时，每个外部依赖必须有明确的处理策略
7. **优先复用，不重复追问** — 已有资产足够时，直接挂到任务文件里；只对缺口使用 `AskUserQuestion`
8. **支持中断接续** — 已有任务文件存在时，默认补充或重审，不擅自重置

<IMPORTANT>
如果成功判据仍停留在 UI 层或描述模糊，要继续追问，不要带着模糊判据进入剧本阶段。
如果 `.e2e-tests/{domain}/task/task.md` 尚未生成，不得宣称澄清完成。
</IMPORTANT>
