# E2E 测试任务澄清

通过结构化引导，把用户的“想测一下”收敛成可执行的测试任务定义。输出的不只是测试范围，而是：测试目标、风险等级、业务边界、用户角色、依赖策略、成功判据和不可接受结果。

---

## 触发条件

- `/e2e` 流程的 Step 1 调用
- 用户主动描述测试需求但任务定义不清晰

---

## 前置条件

### 风险建模清单

澄清时至少考虑以下维度：

| 维度 | 需要问什么 |
|------|-----------|
| 业务价值 | 这个流程支撑什么核心业务目标？ |
| 失败影响 | 出错会导致收入损失、数据错误、用户流失还是合规问题？ |
| 变更强度 | 最近是否刚改过？是否是高频改动模块？ |
| 使用频率 | 是高频主链路还是低频后台操作？ |
| 角色差异 | 不同角色/权限下行为是否不同？ |
| 外部副作用 | 是否会触发支付、发消息、库存变更、审核、导出？ |
| 异步复杂度 | 是否涉及任务、队列、轮询、回调？ |

### 成功判据标准

好的成功判据：提交订单后，订单列表中出现新订单，状态为"待支付"，库存锁定成功，用户收到确认提示。
差的成功判据：页面显示提交成功、看起来没问题。

---

## 执行流程

### Step 1: 澄清任务目标与风险

通过 **AskUserQuestion** 优先收集以下关键问题（可分多轮）：

**必收集项**：

| 项目 | 问题 | 说明 |
|------|------|------|
| 被测功能 | 这次要验证的具体业务流程是什么？ | 要追问到起点、终点和关键动作 |
| 测试目标 | 为什么现在要测它？ | 新功能验收 / 回归 / 发布前 / 线上问题复现 |
| 风险影响 | 如果这里出问题，会造成什么业务后果？ | 用于判定风险等级 |
| 成功判据 | 这次怎样才算真的通过？ | 不是“页面正常”，而是业务承诺成立 |
| 不可接受结果 | 哪些结果一出现就应判失败？ | 如重复下单、脏数据、权限越权 |
| 测试边界 | 明确这次不测什么？ | 避免范围失控 |

### Step 2: 澄清角色、状态与准备前提

继续追问：

| 项目 | 问题 | 说明 |
|------|------|------|
| 用户角色 | 谁在执行这个流程？有哪些角色/权限差异？ | admin / 普通用户 / 审核员等 |
| 数据状态 | 需要什么前置数据状态？ | 已创建订单 / 未支付 / 已实名等 |
| 环境信息 | 在哪个环境测？有无 feature flag？ | 测试 / 预发 / 生产镜像 |
| 外部副作用 | 这个流程会触发什么外部效果？ | 发消息、扣库存、写日志、下载文件 |
| 异步链路 | 是否涉及轮询、任务、消息、回调？ | 决定执行与等待策略 |

### Step 3: 识别服务依赖与处理策略

基于业务流程，识别涉及的服务和外部依赖：

1. **分析调用链** — 从用户描述推断或结合 scan-context 的结果补全
2. **逐个确认处理策略** — 使用 **AskUserQuestion** 为每个外部依赖选择：
   - **真实联调**
   - **Mock 返回**
   - **Fixture 数据**
3. **标注关键依赖** — 哪些依赖若不稳定会直接让测试结论失真

### Step 4: 生成测试任务定义

将收集到的信息整理为结构化定义，向用户展示并确认：

```markdown
# 测试任务定义

## 基本信息
- **被测流程**: {功能描述}
- **测试目标**: {验收 / 回归 / 发布前 / 问题复现}
- **风险等级**: {High / Medium / Low}
- **应用入口**: {URL}

## 业务目标
- {为什么现在测}

## 成功判据
- {关键业务结果 1}
- {关键业务结果 2}

## 不可接受结果
- {失败条件 1}
- {失败条件 2}

## 用户角色与权限
- {角色 1}: {权限说明}
- {角色 2}: {权限说明}

## 依赖与策略
| 服务 | 角色 | 策略 | 备注 |
|------|------|------|------|
| {service-1} | 核心被测 | real | — |
| {service-2} | 支付网关 | mock | 模拟成功/失败两种响应 |

## 前提条件
- {条件1}
- {条件2}

## Out of Scope
- {本次明确不测的内容}
```

### Step 5: 用户确认

使用 **AskUserQuestion** 向用户确认测试任务定义：
- 选项：确认，进入下一步 / 需要调整目标或边界 / 需要补充风险与判据

根据用户反馈修改后，将最终版本传递给后续技能。

**⏸️ 等待用户确认后结束。**

---

## 约束

1. **风险驱动而不是功能罗列** — 不只问测什么，还要问为什么测、失败影响是什么
2. **必须定义成功与失败** — 没有成功判据和不可接受结果，不得进入后续阶段
3. **角色与状态必须明确** — 用户角色、数据状态、权限差异不清，不得假设
4. **边界必须明确** — 说清本次不测什么，防止范围漂移
5. **依赖策略必须明确** — 涉及多服务时，每个外部依赖必须有明确的处理策略

<IMPORTANT>
澄清阶段输出的是“测试任务定义”，不是随手整理的需求摘要。
如果成功判据仍停留在 UI 层或描述模糊，要继续追问，不要带着模糊判据进入剧本阶段。
</IMPORTANT>
