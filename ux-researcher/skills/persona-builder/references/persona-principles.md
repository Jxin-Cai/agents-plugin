# 用户画像构建原则

本文档定义了用户画像构建阶段必须遵循的原则。

---

## 1. JTBD（Jobs-to-Be-Done）框架

### 核心理念
用户不是"购买产品"，而是"雇佣产品来完成某个任务"。理解用户画像的关键不是他们是谁（人口统计），而是他们要完成什么（任务和动机）。

### Job Statement 格式
标准 Job Statement 模板：
> 当我 [情境/触发]，我想要 [动机/行动]，这样我就能 [期望结果/价值]

示例：
- "当我在通勤路上无聊时，我想要浏览有趣的短内容，这样我就能打发时间并获得新知"
- "当我收到客户投诉时，我想要快速找到问题根因，这样我就能在 SLA 内解决问题"

### 三层需求模型

#### 功能需求（Functional Jobs）
用户需要完成的实际任务。这是最表层、最容易观察到的需求。
- 问题："你用这个产品做什么？"
- 关注：任务步骤、频率、场景、工具链

#### 情感需求（Emotional Jobs）
用户在完成任务过程中想要的感受。决定了体验设计的方向。
- 想要的感受：安全、掌控、自信、愉悦、成就感
- 想要避免的感受：焦虑、困惑、挫败、尴尬、失控
- 问题："使用过程中你最在意什么感受？"

#### 社会需求（Social Jobs）
用户希望通过使用产品获得的社会认同。影响品牌定位和传播策略。
- 问题："使用这个产品/方案如何影响别人对你的看法？"
- 关注：专业形象、效率形象、创新者形象、可靠形象

### 雇佣/解雇分析（Hiring/Firing）

| 维度 | 关键问题 |
|------|---------|
| 雇佣触发 | 什么事件/痛点让用户开始寻找解决方案？ |
| 雇佣标准 | 用户用什么标准比较和选择方案？ |
| 习惯引力 | 什么让用户坚持使用现有方案（即使不满意）？ |
| 切换焦虑 | 用户对切换到新方案有什么担忧？ |
| 解雇动因 | 什么会导致用户放弃当前方案？ |
| 推力 vs 拉力 | 推力=现状痛点，拉力=新方案吸引力。两者都需要足够强 |

## 2. 数据驱动画像（Data-Driven Persona）

### 与传统画像的区别

| 维度 | 传统画像 | 数据驱动画像 |
|------|---------|-------------|
| 基础 | 假设和直觉 | 研究数据和行为分析 |
| 核心 | 人口统计 + 虚构故事 | 行为模式 + JTBD |
| 验证 | 很少验证 | 持续用数据验证和更新 |
| 命名 | 虚构人名（"小明"） | 行为标签（"效率型专家"） |
| 风险 | 刻板印象、投射偏差 | 数据不足时标注为假设 |

### 反虚构协议
- **不编造人口统计细节**：除非有数据支撑，不填写具体年龄、收入、教育程度
- **不用刻板印象**：不基于年龄/性别/地域做行为假设
- **不虚构故事**：画像中的场景描述必须来自真实访谈或观察
- **标注数据来源**：每条关键属性标注来源（访谈、测试、数据分析、假设）
- **标注置信度**：高（多源验证）、中（单源数据）、低（假设，待验证）

## 3. 行为变量聚类

### Alan Cooper 的行为变量法
1. 列出所有与产品使用相关的行为变量（维度）
2. 在每个维度上标记所有受访者/用户的位置
3. 寻找跨维度的聚类——多个维度上位置一致的用户群
4. 聚类即画像的基础

### 常见行为变量维度

| 类别 | 变量 | 连续谱 |
|------|------|--------|
| 动机 | 使用目的 | 任务导向 ←→ 探索导向 |
| 能力 | 技能水平 | 新手 ←→ 专家 |
| 频率 | 使用频率 | 偶尔 ←→ 每日 |
| 偏好 | 信息处理 | 快速扫描 ←→ 深度阅读 |
| 决策 | 决策风格 | 独立判断 ←→ 依赖建议 |
| 社交 | 协作程度 | 独立完成 ←→ 团队协作 |
| 价值 | 核心诉求 | 效率/速度 ←→ 品质/精确 |

### 聚类质量标准
- **内部一致性**：同一聚类中的用户在关键变量上表现相似
- **外部区分度**：不同聚类在关键变量上有明显差异
- **实际意义**：聚类差异能转化为不同的设计决策
- **合理数量**：2-4 个主要画像（太多无法聚焦，太少覆盖不够）

## 4. 画像验证与迭代

### 验证方法
1. **回溯验证**：画像能否解释已收集的所有用户数据？
2. **预测验证**：画像能否预测新用户的行为模式？
3. **团队验证**：展示给客服/销售/运营，他们是否认出了这些用户？
4. **数据验证**：画像的行为特征是否与产品使用数据吻合？

### 画像生命周期
- **创建**：基于首轮研究数据
- **验证**：通过后续研究和数据持续验证
- **更新**：当产品或用户群发生重大变化时
- **退役**：当画像不再代表主要用户群时

### 画像使用指南
- 画像是沟通工具，不是约束条件
- 设计讨论中引用画像："效率型专家会怎么看这个设计？"
- 优先为主要画像设计，次要画像做兼容
- 当画像之间需求冲突时，明确优先级

## 5. 画像文档设计

### 信息层次
1. **一眼层**（3 秒理解）：画像名称、核心 Job Statement、一句话描述
2. **概要层**（30 秒理解）：JTBD 三层需求、关键行为特征、痛点和目标
3. **详细层**（3 分钟深读）：使用场景、雇佣/解雇分析、设计暗示

### 设计暗示（Design Implications）
好的画像不只是描述用户，还要指向具体的设计决策：
- "因为这类用户是效率导向的，所以 [功能X] 应该支持快捷键和批量操作"
- "因为这类用户有切换焦虑，所以需要提供从旧工具的数据迁移功能"
- "因为这类用户的情感需求是掌控感，所以不应该使用自动化黑箱"

### 反模式
- **万能画像**：一个画像试图覆盖所有用户 → 什么都没说
- **人口统计堆砌**："28 岁，女，上海，月入 2 万" → 不指向任何设计决策
- **愿望画像**：描述的是"我们希望的用户"而非"真实的用户"
- **一次性画像**：创建后从不更新 → 很快脱离现实
